# vendor-compress — закреплённые копии распаковщиков кэша nixpkgs

Пакеты бинарного кэша nixpkgs лежат сжатыми, причём **двумя способами сразу**. Замер по случайной
выборке путей (2026-08-04): **15 из 22 — `zstd`, 7 — `xz`**. Кэш перешёл на zstd, но старые пути
никуда не делись, поэтому VOID нужны оба — и **на устройстве**, в программе без std и без libc
([[0009-ondevice-packages]], Фаза 8).

| крейт | что делает | апстрим |
|---|---|---|
| `lzma-rs` 0.3.0 | распаковка `.xz` | Guillaume Endignoux, MIT, <https://github.com/gendx/lzma-rs> |
| `ruzstd` 0.8.3 | распаковка `.zst` | Moritz Borcherding, MIT, <https://github.com/KillingSpark/zstd-rs> |
| `twox-hash` 2.1.3 | XXH64 для контрольной суммы кадра zstd | Jake Goulding, MIT, <https://github.com/shepmaster/twox-hash> |

Здесь, а не в `vendor/`, по той же технической причине, что и `vendor-ereb/`: `vendor/` объявлен
подменой источника crates.io, и cargo требует от каждого каталога там реквизитов реестра
(`.cargo-checksum.json`). Эти копии реквизитам реестра соответствовать не могут — подключаются
path-зависимостями.

## lzma-rs — что изменено

| было | стало | почему |
|---|---|---|
| `std` | `no_std` + `alloc` | в программах VOID нет ни std, ни libc |
| `encode/`, `decode/stream.rs` | удалены | сжимать нам нечего, а `stream` глубже всех врос в `std::io` |
| `std::io` | `src/io.rs` — свой шим | вход распаковки у нас слайс, выход `Vec<u8>`; ни файлов, ни дескрипторов |
| крейт `byteorder` | `src/byteorder.rs` | четыре метода чтения целых |
| крейт `crc` | `src/crc.rs` | CRC-32/ISO-HDLC и CRC-64/XZ, таблицы считаются в `const fn` |

**Зависимостей у копии не осталось ни одной** — это осознанно: `byteorder` и в дереве VOID есть,
но он приходит как зависимость сетевого стека, и унификация фич однажды включила бы ему `std`.

Шимы повторяют семантику `std` там, где от неё зависит результат: ёмкость `BufReader` = 8192 (по
ней декодер xz считает, сколько байт попало под CRC заголовка блока), `Take::fill_buf` обрезает по
остатку лимита, `read_exact` при нехватке даёт `UnexpectedEof`.

### Веха 111: распаковка стала потоковой — тело тронуто

До этой вехи правилась только граница копии. Здесь пришлось зайти внутрь, и вот почему.

Апстримный декодер держит **весь распакованный результат в памяти**: `lzma2` копит вывод в
`LzAccumBuffer` и отдаёт его одним куском в `finish()`, а `xz` поверх этого собирает блок во
временный `Vec` и лишь потом пишет в сток. Для файла в 15 МиБ (индекс канала nixpkgs) это значит
15 МиБ кучи разом — программа `pkg` падала на нём с отказом аллокатора, хотя вся дорога вокруг
(загрузка, разбор NAR, укладка в store) потоковая с Вехи 108. С `.nar.xz` настоящего пакета было
бы то же самое, только хуже.

| место | изменение |
|---|---|
| `decode/lzbuffer.rs` | `LzAccumBuffer::flush_keeping(keep)` — отдать в сток всё, кроме последних `keep` байт; `reserve_total` — одно точное расширение вместо удвоений |
| `decode/lzma2.rs` | `decompress_window(…, window)`: после каждого куска слить лишнее; `decompress` сохранён и означает «окно бесконечно», то есть прежнее поведение |
| `decode/xz.rs` | размер словаря читается из свойств фильтра LZMA2 (было `// TODO: properties??`); блок с ОДНИМ фильтром распаковывается прямо в сток, контрольная сумма считается по дороге (`BlockSink`) |

Почему это безопасно: назад LZMA смотрит не дальше словаря, а его размер стоит в заголовке блока —
оставляя ровно словарь, мы держим всё, до чего декодер вправе дотянуться. Цепочка из нескольких
фильтров по-прежнему идёт через буфер (там выход одного — вход другого).

Цена названа честно: при одном фильтре байты уходят потребителю ДО сверки CRC блока — иначе
потоковой распаковки не бывает вообще (так же ведёт себя `xz -dc`). Для VOID это безопасно, потому
что ни один потребитель не делает распакованное видимым до конца: `pkg` привязывает корень дерева
только после сверки NarHash, а индекс канала — после `finish()`.

Место под окно занимается не по заголовку, а когда поток покажет, что он большой: `xz -9` пишет в
заголовок словарь 64 МиБ даже для килобайтного файла, и резервировать по нему значило бы требовать
66 МиБ кучи на распаковку мелочи.

## ruzstd и twox-hash — исходники не тронуты ВООБЩЕ

Приятный контраст с lzma-rs: `ruzstd` объявлен `#![no_std]` сам по себе и носит собственный io-шим
(`src/io_nostd.rs`), а `twox-hash` с `default-features = false` тоже `no_std` и без зависимостей.
Переводить было нечего — **изменены только манифесты**, и ровно в трёх местах:

1. выброшены фичи, которых в VOID не на чем включать (`std`, `dict_builder`, `random`, `serialize`,
   `rustc-dep-of-std`) вместе с их зависимостями (fastrand, rand, serde, rustc-std-workspace-\*);
2. `twox-hash` подключён path-зависимостью на соседнюю копию, а не по версии из crates.io;
3. часть выброшенных фич **объявлена пустыми** — иначе компилятор сыплет «unexpected cfg» на
   нетронутый чужой код, а править чужой код ради тишины — ровно то, чего эти копии избегают.

Фича `hash` оставлена включённой: она даёт проверку контрольной суммы кадра zstd. Причина та же,
по которой в копии lzma-rs оставлен CRC — архив приезжает из чужого кэша по сети, и «расползлось
молча» здесь недопустимо.

## Правило

Править **в апстриме**, сюда переносить осознанно — та же дисциплина, что со smoltcp, rustls и
ereb: подменять границу, а не тело, иначе следующее обновление апстрима превращается в
переписывание. Сборка VOID обязана оставаться оффлайн и воспроизводимой.

## Проверка

`cargo test -p lzma-rs --target x86_64-unknown-linux-gnu` — 27 тестов: контрольные значения CRC из
каталога RevEng, распаковка настоящих `.xz` обеими проверками контейнера, обрезанный и испорченный
архив (фикстуры в `lzma-rs/tests/`). Потоковый путь Вехи 111 они покрывают в том числе тем, что
`corrupted_payload_fails_check` по-прежнему ловит порчу — сумма теперь считается по дороге.

Отдельно потоковость проверена на настоящем индексе канала (5 645 048 Б → 15 408 902 Б): вывод
совпал с `xz -d` **побайтно**, но пришёл 42 порциями вместо одной — то есть в памяти его целиком
не было. Тот же побайтовый результат на пресетах `-0`, `-3`, `-6`, `-9` (словари 256 КиБ … 64 МиБ)
и на килобайтном файле, сжатом `-9`.

Сквозная проверка обоих распаковщиков — на самой VOID, настоящими архивами с `cache.nixos.org`:
`nar-unpack` принимает `.nar.xz` и `.nar.zst` и раскладывает пакет через файловый сервер.
Распакованные размеры совпали с хостовыми `xz -d` / `zstd -d` побайтно.
