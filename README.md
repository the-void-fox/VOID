# VOID

Экспериментальная операционная система: **персистентное, контент-адресуемое,
capability-защищённое пространство объектов** вместо классической пары
«файловая система + процессы». Микроядро на Rust, две архитектуры (RISC-V и
x86_64) из одного дерева исходников, весь userspace — ELF-объекты в собственном
хранилище, исполняемые по криптографическому хэшу содержимого.

Родословная идей: KeyKOS/EROS (персистентность + capability), Nix и git
(контент-адресация, дедупликация, атомарная смена версий как перенос корня).

```
  ╔══════════════════════════════════════════╗
  ║  VOID — Веха 60                          ║
  ║  linux/io.h: MMIO-регистры ядра —        ║
  ║  readl/writel драйвера на VOID           ║
  ╚══════════════════════════════════════════╝
```

## Это уже система?

Да — по критериям, которые мы для себя считаем честными:

- **загружается сама** на двух архитектурах (OpenSBI→S-mode на riscv64, PVH→ring0
  на x86_64) и доводит себя до интерактивного shell'а;
- **изолирует и переживает падения программ**: процессы в U-mode/ring3 со своими
  адресными пространствами; программа, разыменовавшая мусорный указатель, гибнет
  одна — ядро и соседи живут;
- **помнит своё состояние**: содержимое хранилища (файлы, программы, capability
  домены) переживает перезагрузку; крах посреди записи поднимается консистентно
  (append-only + атомарный суперблок — проверено в том числе умышленным
  убийством QEMU посреди сессии);
- **интерактивна**: цветной shell `vsh` с каталогами (ls · cd · pwd · mkdir · rm · cat ·
  echo · run · clear · exit) и вводом по прерываниям на обеих архитектурах — и с
  serial-терминала в QEMU, и с VGA + PS/2-клавиатуры на реальном x86;
- **обновляема**: система = набор именованных корней на хэши; обновление
  программы — атомарный перенос корня, откат — перенос обратно;
- и главный интеграционный тест: **один и тот же диск грузится и на RISC-V, и на
  x86_64** — каждая архитектура видит общие данные и свои бинари (`bin/riscv64/*`
  и `bin/x86_64/*` бок о бок).

Чем она пока НЕ является: production-ОС. Один CPU (без SMP),
безопасность не аудирована; на реальном x86 (ASUS X54C) уже загружается через
GRUB до интерактивного vsh с редактором строки и клавиатурой (Вехи 41–60), пишет store на
**реальный SATA-диск** (драйвер AHCI, Веха 47) и **устанавливается на диск** (vsh `install`,
Веха 48 — дальше грузится с диска без USB). Есть свои драйверы **Intel e1000** (сеть, Веха 49,
`ping` отвечает) и **USB xHCI + HID-клавиатуры** (Веха 50) — но оба про «типовое» железо: у
конкретного X54C проводной порт Atheros/Realtek (не e1000), а USB — EHCI (не xHCI, Sandy Bridge),
так что именно этот ноут ждёт своих драйверов. Путь к ним начат: с Вехи 51 драйвер может жить в
**userspace** (регистры MMIO + DMA-память по capability), а с Вехи 52 — **спать до прерывания
своего устройства** (IRQ по capability, `SYS_IRQ_WAIT`); фундамент userspace-драйверов закрыт
целиком (e1000 уже работает обычным процессом), а с Вехи 53 над ним поднялся **каркас
Linux-API шима `lx_emul`** — драйвер пишется «как в Linux» (ioremap/kmalloc/dma_alloc_coherent/
request_irq/probe): сперва на Rust (Веха 53), затем на **C** (Веха 54 — настоящий C-драйвер,
кросс-gcc против void-libc), а с Вехи 55 на VOID работают **неизменённые `.c` из ядра
Linux** (lib/sort.c 6.18.7 против шим-заголовков), и с Вехи 56 заведён **Lx_kit** — C-рантайм
ядрового API: аллокатор `kmalloc` (на нём `lib/argv_split.c` честно аллоцирует память ядра) +
с Вехи 57 **двусвязный список** `linux/list.h` (`lib/list_sort.c`) и с Вехи 58 **битовые операции**
`linux/bitops.h` (`lib/hweight.c`), с Вехи 59 — инфраструктура **err.h** (ERR_PTR/IS_ERR) и **io.h** (readl/writel MMIO) — растущий
конвейер к хостингу реальных Linux-драйверов (полигон e1000; закроет Atheros/EHCI/wifi/GPU). Сеть сама пока
базовая — стек ARP/IPv4/ICMP echo в userspace (Веха 34: `ping` работает,
TCP/UDP/DNS ещё нет). Политика коммитов store с Вехи 33 уже НЕ наивна —
SSD-дружелюбие было последним «до железа» пунктом этого списка.

## Ключевые идеи

1. **Объект вместо файла.** Единица хранения — неизменяемое значение,
   адресуемое BLAKE3-хэшем содержимого (content-id). Одинаковое содержимое
   хранится один раз (дедуп). «Изменение» = новый объект + атомарный перенос
   именованного корня. История версий — бесплатно, как в git.
2. **Capability вместо прав доступа.** Доступ к любому ресурсу (объект, корень,
   эндпоинт IPC, устройство, само хранилище) — только по неподделываемому
   дескриптору с правами (read/write/grant/send/exec). Права можно только
   СУЖАТЬ при передаче (аттенуация); есть отзыв. Capability переживают
   перезагрузку вместе с процесс-доменами (`.cspace`).
3. **Персистентность как свойство ядра.** Не «ОС + ФС», а единое пространство
   объектов, у которого диск — истина, RAM — кэш. Ядро не знает понятия
   «файловая система» вообще.
4. **Программа = объект.** ELF исполняется по content-id из store. Секций с
   кодом userspace в образе ядра нет — только «семена», которые первый запуск
   сеет в хранилище.
5. **Микроядерность.** Драйвер блочного устройства, POSIX-слой, сетевой стек
   (ARP/IPv4/ICMP), shell — обычные userspace-процессы, говорящие с ядром через
   синхронный IPC (CALL/RECV/REPLY с reply-capability) и узкий набор
   syscall'ов (~32). Ядро сети не знает — отдаёт лишь сырые Ethernet-кадры;
   протоколы синхронизации нитей (Mutex/Condvar) — тоже userspace, на одном
   примитиве futex.
6. **Мультиархитектурность через узкий контракт.** Вся арх-специфика — в
   `kernel/src/arch/{riscv64,x86_64}` за компилируемым контрактом (~30 функций);
   общий код один, собирается двумя cargo-таргетами.

## «А какая у вас файловая система?»

Никакой — и это осознанно. На диске нет таблицы разделов, суперблоков ext4 и
т.п.: сектор 0 — суперблок VOID, дальше append-only область объектов, в которой
живёт и индекс — дельта-цепочкой с надгробиями (Веха 33: коммит пишет
O(изменений), уплотнение — по порогу мусора, group commit с синком при простое;
крах-устойчивость — суперблок пишется последним). Роль «файлов» играют именованные
корни store (`f<путь>`), роль каталогов — корни-индексы (`d<путь>`): с Вехи 44 у
персоналии есть **иерархия** — папки, пути, `cd`/`pwd`/`mkdir`/`rm`, вложенность,
персистентно. POSIX-семантика (open/read/write/close/readdir/mkdir) — это
**персоналия**: userspace-сервер `posixfs`, транслирующий POSIX-вызовы в объекты
store по IPC (иерархия добавлена БЕЗ единой правки ядра). Захочется другую
семантику — рядом встанет другая персоналия, ядро менять не нужно.

## Бенчмарки

Микробенчи встроены в загрузку (`bench_demo`, программа `bin/bench` меряет из
userspace счётчиком rdtime/rdtsc). Сравнение с Linux — **гость в том же QEMU**
(q35, TCG без KVM, `-m 128M`, тот же TSC; зеркальный бенч —
`Code/bench/bench-linux.rs`, там же инструкция запуска): относительные цифры
честные, абсолютные — цифры эмуляции, не железа.

| Операция (ns/op, QEMU TCG)        | VOID riscv64 | VOID x86_64 | Linux 7.1 x86_64 |
|-----------------------------------|:---:|:---:|:---:|
| null syscall                      | 20 448 | 42 838 | **12 525** |
| IPC туда-обратно между процессами | **90 059** | 152 407 | 1 073 342 (pipe) |
| page fault (ленивая страница)     | **41 514** | 87 524 | 171 386 (anon mmap) |
| появление 32-байтного объекта     | **88 998** (obj_put, с BLAKE3!) | 188 501 | 1 803 521 (create+write, ramfs) |
| чтение объекта                    | **39 310** | 74 967 | 356 838 (open+read+close) |
| exec: полный цикл запуска         | **1 054 340** | 2 277 253 | 27 528 460 (fork+execve+wait) |

Честные оговорки:

- **null syscall у Linux быстрее** (×3.4): у него вылизанный `syscall/sysret`-путь,
  у нас `int 0x80`/`ecall` с полным сохранением кадра и универсальным
  диспетчером. Знаем, где лежат наносекунды.
- **IPC быстрее на порядок** — это дизайн, а не читерство: синхронный rendezvous
  с прямой доставкой буфера против pipe (2+ syscall'а на сторону + futex +
  планировщик).
- exec: бинари разного веса (наш hello — 8.6 КиБ ELF, у Linux static-musl
  4.7 МиБ), но и на порядок величины скидка этого не объясняет.
- «объект» и «файл» не эквивалентны: наш put дополнительно платит за
  криптографический хэш и дедуп — и всё равно быстрее.
- Ядро Linux — NixOS generic (не tinyconfig), это стоит памяти, но слабо влияет
  на горячие пути syscall'ов.

## Память

| | VOID (обе арх.) | Linux 7.1 x86_64 (тот же QEMU) |
|---|:---:|:---:|
| Образ ядра в памяти | **~420–620 КиБ** (вместе с семенами 18 программ) | ~48 МиБ (резерв до MemTotal) |
| RAM после загрузки + uutils-демо (пик) | **≈ 30–37 МиБ**¹ | ≈ 80 МиБ |
| Программа userspace | 6–13 КиБ на ELF (no_std) · 85–122 КиБ (std) · 1.8–2.3 МиБ (coreutils: 8 утилит одним бинарём) | — |

¹ С Вехи 32 (uutils): куча ядра 16 МиБ (2.2-МиБ ELF при exec живёт в ней
дважды — кэш store + копия загрузчика) плюс страницы процессов coreutils;
стек процесса 256 КиБ. Пик рос честно: ≈ 4.9 МиБ (Веха 30) → ≈ 12 МиБ
(Веха 31, std) → сейчас. Против Linux всё ещё вдвое меньше. С Вехи 46 этот
пик — именно ПОТОЛОК, а не растущая утечка: фреймы завершившихся процессов
возвращаются в список свободных и переиспользуются (повторные запуски пик не двигают).

## Что умеет (демо каждой загрузки)

Персистентный store с GC и поколениями · capability (минт/grant/аттенуация/
отзыв/подделка отвергается) · вытесняющая многозадачность ядерных нитей и
процессов · async-executor с диском на прерываниях (PLIC / MSI-X) · IPC с
передачей прав · userspace-драйвер блочного устройства · сервер объектного
store · POSIX-персоналия · ленивые кучи процессов и честные page fault'ы ·
exec-по-хэшу · интерактивный vsh · микробенчи · отчёт памяти · импорт с хоста
(`void-store-import`: файлы и NAR-архивы nix — прямо в образ диска) · контракт
запуска (`run bin/hello мир`: argv, env и стартовые права наследуются) ·
родная std (`run bin/hello-std`: обычный Rust — println/куча/std::fs/HashMap/
Instant/exit-коды — собранный обычным cargo под таргеты `*-unknown-void`) ·
настоящие coreutils (`run bin/coreutils ls`: uutils 0.9.0 — ls/cat/cp/wc/
mv/rm/head/echo одним multicall-бинарём; `cp` на x86_64 создаёт файл, `wc`
на riscv64 его считает — общий диск) · взрослая политика коммитов
(group commit + синк при простое, дельта-индекс, уплотнение по порогу —
загрузка пишет на диск килобайты, а не мегабайты) · сеть
(`net-srv`: стек ARP/IPv4/ICMP echo в userspace, `ping 10.0.2.2` из vsh —
ядро отдаёт лишь сырые кадры virtio-net, протоколы в userspace-сервере) ·
**потоки** (`run bin/threads-std`: обычный `std::thread` + `Arc<Mutex>` на
futex + `thread_local!` через нативный TLS — 4 нити считают общий счётчик, итог
точен; ядро планирует нити внутри процесса, синхронизация — userspace) ·
**C-мир** (`run bin/hello-gnu --greeting=Привет` и `run bin/bzip2 -z файл`:
настоящие GNU hello и bzip2, собранные ПО РЕЦЕПТАМ nixpkgs кросс-gcc+newlib
с глю `void-libc` ~610 строк — autotools/gnulib и Makefile-пакеты приходят
как есть; заодно ядро x86 доросло до FP/SSE-контекста процессов) ·
**checkpoint процессов** (`run bin/freeze`, затем `thaw пример` — хоть после
перезагрузки: замороженное вычисление продолжает с того же шага с тем же
стеком и кучей; образ — дерево объектов store, страницы дедуплицируются,
семантика setjmp — живому 0, размороженному 1) ·
**linux-abi** (`run bin/lhello`, `run bin/busybox echo …` / `uname -a` / `seq 1 5`:
неизменённые static-PIE musl-бинари из кэша nixpkgs — hello и busybox 1.37 —
работают под персоналией Linux; транслятор Linux-syscall'ов в ядре, без единой
новой инструкции: riscv `ecall` общий с VOID, x86 `syscall` ловится как #UD) ·
**wasi** (`run bin/wasirun hello.wasm`: неизменённый wasm32-wasi-модуль работает
через интерпретатор wasmi — ОДИН .wasm на обеих архитектурах; раннер — обычная
userspace-программа поверх порта std, ядро не тронуто). Так закрыты все три
бэкенда пакетной дорожки (native/nix-cross · linux-abi · wasi) ·
**декларативный init** (`switch gen2` + перезагрузка: система поднимается по
конфигу-объекту из store, а не по зашитому сценарию — поколения gen1/gen2/…, откат
сменой корня `system/current`; конфиг пишется в vsh ИЛИ генерится из `nix/system.nix`
настоящим Nix на хосте — модель NixOS, но фундамент родной) ·
**реальное железо** (Вехи 41–43): x86-ядро грузится настоящей прошивкой (multiboot2/GRUB,
не только QEMU), рисует на VGA-экране (у ноутбука нет COM-порта) с **кириллицей** (шрифт
CP866 в знакогенераторе), берёт размер RAM из карты памяти загрузчика, а ввод принимает с
**PS/2-клавиатуры** — `vsh>` интерактивен на реальной машине; консоль цветная (ANSI
работает и в терминале, и на VGA), с `clear` и курсором. Проверено на ASUS X54C (и в QEMU
через GRUB); загрузочный USB — `Code/boot/mkboot.sh` ·
**папки** (`mkdir notes && cd notes && echo hi > a.txt && ls`): у persona posixfs появилась
иерархия — каталоги, пути, `cwd`, `cd`/`pwd`/`mkdir`/`rm`, вложенность, персистентно — БЕЗ
единой правки ядра (файл — корень `f<путь>`, каталог — индекс-корень `d<путь>`).

## Сборка и запуск

Требуются: nix-shell (QEMU, gdb, Rust из оверлея) и rustup-тулчейн по
`Code/rust-toolchain.toml`.

```sh
nix-shell                      # из корня репозитория
cd Code
truncate -s 16M void-disk.img  # один раз: общий диск обеих архитектур

cargo run                                   # RISC-V (QEMU virt)
cargo run --target x86_64-unknown-none      # x86_64 (QEMU q35, PVH)
```

Выход из QEMU: `Ctrl-A`, затем `X`. Диск один на обе архитектуры — попробуйте
записать файл в vsh на одной и прочитать на другой.

## Дальше

Пакетная дорожка (ADR 0004) дошла до **первой честной точки
самодостаточности**: мост host→store, контракт запуска (ABI v2), порт Rust
`std` (теперь и std::fs через IPC, и настоящий аллокатор) и uutils/coreutils —
обычные Rust-программы и настоящие утилиты собираются обычным cargo (тулчейн
`void`) и работают на обеих архитектурах с одного диска; политика коммитов
store дозрела до железа (Веха 33), появилась сеть — стек ARP/IPv4/ICMP echo в
userspace, `ping` из vsh (Веха 34), настоящие потоки — `std::thread`,
`Arc<Mutex>` на futex, `thread_local!` через нативный TLS (Веха 35, разблокирует
sort/rayon/ripgrep), C-мир: GNU hello и bzip2 собираются по рецептам nixpkgs
(pkgsCross gcc+newlib + глю `void-libc`) и работают с того же диска (Веха 36 —
ступень «nixpkgs как книга рецептов» ADR 0004 взята), checkpoint процессов
(Веха 37, наследие KeyKOS): вычисления переживают перезагрузку, freeze/thaw
с образом-деревом объектов store, **linux-abi** (Веха 38, бэкенд B): неизменённые
static-PIE musl-бинари из кэша nixpkgs (hello, busybox) под персоналией Linux —
и **wasi** (Веха 39, бэкенд C): wasm32-wasi-модули через интерпретатор wasmi,
один .wasm на обеих архитектурах, раннер в userspace (ядро не тронуто) — **все три
бэкенда пакетной дорожки ADR 0004 закрыты** (native/nix-cross · linux-abi · wasi) —
и **декларативный init** (Веха 40): система поднимается по конфигу-объекту из store,
поколения и откат сменой корня `system/current`; конфиг пишется в vsh или генерится
настоящим Nix на хосте (`nix/system.nix` → `nix eval` → мост) — модель NixOS на родном
фундаменте. Вехи 41–43 — **реальное железо**: x86-ядро грузится настоящей прошивкой
(multiboot2/GRUB вместо только-QEMU-PVH), VGA-консоль с кириллицей (шрифт CP866) и цветом
(ANSI и в терминале, и на VGA — `clear`, курсор), размер RAM из карты памяти загрузчика и
ввод с **PS/2-клавиатуры** — `vsh>` интерактивен на металле (проверено на ASUS X54C);
загрузочный USB — `Code/boot/mkboot.sh`. Веха 44 — **папки** в persona posixfs: каталоги,
пути, `cd`/`pwd`/`mkdir`/`rm`, вложенность, персистентно — без правок ядра. Веха 45 —
**редактор строки** в vsh: курсор, вставка/удаление в позиции, `←`/`→`/`Home`/`End`, история
`↑`/`↓` (единый ANSI для PS/2 и serial). Веха 46 — **освобождение фреймов**: страницы,
таблицы и корень адресного пространства завершившейся группы возвращаются в список свободных
и переиспользуются (проверено: пик памяти не растёт при повторных запусках) — долгая сессия
больше не течёт к OOM. Дальше: драйверы реального железа (USB-стек, AHCI/NIC) на плате —
известный техдолг собран в `Obsidian/…/notes/known-gaps.md`.
