# 0004. void-pkg — пакеты и самодостаточность: три бэкенда над одним store

## Контекст
Фаза 3 сделала систему самостоятельной (программы из store по content-id, живой shell,
персистентные права, память), но **система без программ бессмысленна** — цель: поставить
VOID на устройство и пользоваться. «Просто взять» чужие пакеты нельзя: у VOID другой ABI.
Полный порт nix внутрь VOID нереалистичен (nix — большая POSIX-программа, nixpkgs собран
под `x86_64-linux`).

Разложение «пакета» показывает, что барьер один: пакет = рецепт (переносимые данные) +
сборка (может идти на хосте) + **runtime-ABI бинаря (единственное настоящее препятствие)** +
дистрибуция/хранение (у нас уже в ядре).

Мотивация-наблюдение: NixOS строит контент-адресацию и иммутабельность в userspace ПОВЕРХ
неподходящего фундамента (изменяемый FHS-Linux) — и всё равно вышла невероятно стабильной.
У VOID те же принципы даны из ядра ([[0002-persistent-content-addressed-capability-core]]) —
та же модель должна работать лучше, потому что ей не приходится бороться с собственной основой.

## Решение
**void-pkg** — не монолитный менеджер, а резолвер над store с тремя бэкендами и порядком
отката **A → B → C** (берётся лучший доступный «вкус» пакета):

- **A. native / nix-cross** — программы, собранные ПОД VOID:
  шорткат — порт Rust `std` для таргета VOID → кросс-сборка crates.io (**uutils** = coreutils
  на Rust, ripgrep, helix…) без портирования C вовсе;
  магистраль — рецепты **nixpkgs** как книга рецептов (`pkgsCross`): кросс-сборка C-программ
  через VOID-libc (newlib/relibc поверх [[posix-personality]]).
- **B. linux-abi** — неизменённые замыкания из бинарного кэша nixpkgs под Linux-персоналией
  (~50–100 syscall'ов для CLI; страшные — futex/clone; старт со статических однопоточных
  musl). Ключевой факт: замыкания nix **не зависят от FHS** — их /nix/store-пути ложатся на
  наш store 1:1. Nix — единственная база, архитектурно совместимая с не-FHS
  контент-адресуемой ОС. Прецеденты: FreeBSD linuxulator, gVisor, Managarm.
- **C. wasi** — wasm32-wasi через `wasmi` (no_std): универсальный медленный fallback;
  capability-модель WASI ложится на нашу ([[capabilities]]) один-в-один.

Общее для всех бэкендов: результат — контент-адресуемые объекты + корни-профили в store.
**Поколения, атомарные обновления и откат не пишем — это свойства store**, а не менеджера.
Сборка — на хосте (мост `void-store-import`: замыкание/NAR → объекты+корни в образ диска);
на устройстве — резолвер и профили. Корни программ получают архитектурное измерение
(`bin/<arch>/name`): ELF под x86 и RISC-V — разные объекты с разными хэшами.

Порядок работ: Веха 23 (userspace в ELF) — пререквизит всего; затем std-порт → uutils +
host-мост (первая точка самодостаточности) → NAR → nixpkgs-cross. B и C — исследовательские
дорожки без дедлайна.

## Последствия
- Плюсы: доступ к крупнейшей пакетной базе чужими РЕЦЕПТАМИ при родном ABI; Rust-шорткат
  даёт юзабельный userland за месяцы, не годы; профили/откат бесплатно; лестница
  самодостаточности с честными ступенями (см. [[void-pkg]]).
- Минусы / компромиссы: libc/std-порты — длинные вложения; Linux-ABI — большой проект;
  до собственного тулчейна на устройстве сборка остаётся хостовой; лицензии — FOSS
  разрешает порт и распространение, unfree-кэши не трогаем.
- Открывает: декларативный init (system-конфиг как объект store — «configuration.nix»
  родными средствами), окружения-как-объекты (аналог nix-shell), «flake» как дерево
  content-id без языка Nix (вычисляет настоящий nix на хосте через мост).

## Альтернативы
- **Порт nix внутрь VOID:** отвергнут — годы, требует POSIX-мира целиком.
- **Свой репозиторий с нуля:** отвергнут — базу пакетов одному не потянуть.
- **AUR/pacman как база:** отвергнут — пакеты Arch намертво предполагают FHS и глобальное
  изменяемое /usr; худший кандидат для не-FHS ОС.
- **Только WASM:** отвергнут как магистраль — экосистема мала, интерпретация медленна;
  остаётся бэкендом C.
