# 0006. vvsh — Lisp VOID для конфига и шелла: вычисление на VOID, не на хосте

## Контекст
Два разных пробела указывают на одно решение.

- **Конфиг системы.** Веха 40 ([[declarative-init]]) поднимает систему из объекта-конфига в сторе,
  НО вычисляет его **Nix на ХОСТЕ** (`nix/system.nix` → `nix eval` → мост), а VOID грузит готовые
  данные. Это «читерство»: логика конфига не самохостится, нужен хостовый Nix. Сам конфиг сейчас —
  плоский текст (`service`/`shell` + токены прав), без языка и без вычислений.
- **Шелл.** `vsh` ([[tty]], Вехи 43/45) — родной, простой командный раннер: без конвейеров,
  редиректов, переменных, управляющих конструкций. Полноценный `bash` дёшево не впихнуть
  (`fork`/`execve`/`pipe`/сигналы/job-control — большой линуксулятор; `fork` архитектурно неудобен
  на персистентном микроядре — клон всего адресного пространства).
- **Тезис VOID** ([[0002-persistent-content-addressed-capability-core]]): всё — объект в
  контент-адресуемом сторе, неизменяемые значения по хэшу. Язык, где выражение ЕСТЬ объект-значение
  (гомоиконность), ложится сюда естественно.
- **Наблюдение:** конфиг-язык и шелл-язык — по сути одно (REPL, который заодно конфиг). Guix так и
  делает — Scheme и для конфигурации, и для системного управления.

## Решение
**vvsh** (double-v sh) — маленький **Lisp / S-выражения**, **ВЫЧИСЛЯЕМЫЙ НА VOID**, результат —
контент-адресуемый объект в сторе.

- **Гомоиконный:** код = данные = объект стора. **Тьюринг-полный НАМЕРЕННО** — гибкость без потолка
  (при желании «на конфиге можно написать Тетрис»).
- **Разделение (ключевое):** язык ВЫЧИСЛЯЕТ → нормализованный объект-данные → init ГРУЗИТ данные.
  Вся мощь на этапе eval; путь загрузки прост и аудируем; результат адресуется по хэшу (откат/дедуп
  бесплатны — как деривация в Nix: мощный язык → фиксированный результат).
- **Двойная роль:** (а) **конфиг системы** — заменяет Nix-на-хосте (самохостинг: eval уезжает с
  хоста на VOID); (б) **движок `vsh`** — интерактивный шелл-REPL с конвейерами/переменными/функциями
  поверх ТОГО ЖЕ языка. Один язык и для конфига, и для шелла.
- **Реализация инкрементально:** парсер S-выражений + примитивы (чисто-данных подмножество) →
  метациркулярный вычислитель (сотни строк) → стдлиб → интеграция в init (конфиг) и в `vsh` (шелл).

## Последствия
- **Самохостинг конфига:** хостовый Nix больше не обязателен для СИСТЕМНОЙ конфигурации (Nix остаётся
  для сборки пакетов, [[0004-void-pkg]]).
- Один язык — меньше поверхности; конфиг аудируем как данные, но вычисляется как программа.
- **Тьюринг-полнота = конфиг может не завершиться** — осознанный компромисс (config-как-программа, а
  не config-как-данные). Init грузит только НОРМАЛИЗОВАННЫЙ результат: не сошёлся eval — система не
  поднимется, но путь загрузки остаётся простым.
- `vsh` получает конвейеры/скрипты **без порта bash** и без гигантского линуксулятора.
- Ещё один язык учить (принято сознательно).

## Альтернативы
- **config-как-данные** (Dhall / Starlark / JSON — специально НЕ Тьюринг-полные, чтобы всегда
  завершаться и анализироваться) — безопаснее, но нет гибкости («Тетриса»). Отвергнуто в пользу
  гибкости.
- **Ленивый Nix-подобный** — ближе к наследию (уже используем `nix/system.nix`), но ленивость
  сложнее реализовать чисто.
- **Встроить готовый интерпретатор** (Rhai / Starlark-rust / Scheme-крейт) через порт std — минимум
  работы, но язык «не свой»; Starlark вдобавок не Тьюринг-полный.
- **Портировать bash** ради шелла — огромный линуксулятор (`fork`/сигналы/job-control), `fork`
  неудобен на персистентном микроядре. Отброшено (реальные скрипты — через линуксулятор+`dash`
  по требованию, если понадобится; повседневный шелл — на vvsh).
- **Оставить конфиг на Nix-хосте + растить родной `vsh`** — не самохостится, дублирование логики
  конфига и шелла.
