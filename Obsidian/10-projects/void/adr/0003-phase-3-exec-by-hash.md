# 0003. Фаза 3 — самостоятельность: программа как объект store (exec по хэшу)

## Контекст
Фазы 0–2 закрыты: стержень [[0002-persistent-content-addressed-capability-core|ADR 0002]]
собран и работает, POSIX-персоналия доказала прозрачность личности. Но система — это
скриптованная демо-последовательность в `kmain`: программы статически вшиты в образ ядра
(секция `.user`), ввода нет, c-space живёт в RAM, capability нельзя передать по IPC.
Полный разбор — в [[phase-2-state-analysis]]. Нужно решить, куда идти дальше:
x86-порт, SASOS, сеть или «самостоятельность» системы.

## Решение
**Фаза 3 — самостоятельность.** Центральный примитив фазы: **программа = неизменяемый
контент-адресуемый объект в store, исполнение — по ContentId** (`exec(hash)`). Это прямое
следствие ADR 0002 — как derivation в Nix: дедупликация программ, воспроизводимость запуска
и проверяемость «что именно исполняется» бесплатно. Такого примитива нет ни у Linux, ни у seL4.

Порядок вех (по одной радикальной идее за работающей вехой, как всегда):
1. **Веха 19 — программа как объект store.** Отдельный ELF-крейт userspace; ядро сидит его
   в store под корнем-именем; минимальный ELF-загрузчик (PT_LOAD → U-страницы, W^X);
   `spawn` из байтов store по ContentId. На втором запуске ELF грузится С ДИСКА.
2. **Веха 20 — UART-ввод + интерактивный shell.** IRQ UART → async-канал → `mini-sh`
   с настоящим вводом: `ls`/`cat`/`echo`/`run <имя|hash>`.
3. **Веха 21 — cap-transfer по IPC + персистентный c-space.** Grant-в-сообщении;
   c-space переживает перезагрузку — тезис ADR 0002 становится полным.
4. **Веха 22 — куча процесса + фолты.** `SYS_MAP`/ленивые страницы; user page fault
   убивает процесс, а не ядро.

Фоном (без отдельной вехи): выносить архзависимое в `kernel/src/arch/riscv64/` за узкий
интерфейс — подготовка к мультиархитектурности, дешёвая пока архитектура одна.

## Последствия
- Плюсы: каждая веха превращает демо в систему (загрузка программ → интерактивность →
  полные capability → живучесть); exec-по-хэшу усиливает стержневой тезис вместо того,
  чтобы отвлекаться от него; после Фазы 3 x86-порт портирует *систему*, а не демо.
- Минусы / компромиссы: ELF-загрузчик — новая поверхность в ядре (минимизируем: только
  PT_LOAD, статические ELF, без релокаций и динамической линковки); x86 и сеть откладываются;
  лимиты персоналии (4 файла × 256 байт) живут до Вехи 22.
- Открывает: init-процесс, персоналии как загружаемые программы, checkpoint процессов
  (ортогональная персистентность вычислений), SASOS-гибрид для доверенных серверов.

## Альтернативы
- **Сразу x86-порт:** портировали бы демо; переносимость дешевле готовить фоновым
  arch-рефакторингом. Отложен, не отменён — см. таблицу цены в [[phase-2-state-analysis]].
- **Сразу SASOS:** гибрид (доверенные серверы в одном AS, изоляция Rust'ом, модель
  Theseus/Hubris) станет естественным ПОСЛЕ exec-по-хэшу — код сервера как проверяемый
  неизменяемый объект. Полный SASOS — поздний эксперимент ([[0001-rust-riscv-microkernel|ADR 0001]]).
- **Сразу сеть (virtio-net):** ещё один драйвер-сервер не меняет качество системы,
  пока в неё нельзя загрузить программу и нельзя с ней поговорить.
