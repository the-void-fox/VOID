# 0007. Графика: свой композитор/тулкит на capability-объектах, персистентный GUI

## Контекст
Цель проекта на сейчас — **заменить NixOS** на рабочем устройстве пользователя, а значит нужна
графическая оболочка (пользователь работает в **niri** — скроллируемый тайлинг). Сейчас у VOID
только **VGA-текст 80×25** ([[platform]], Веха 41, буфер `0xB8000`) — пиксельного фреймбуфера и
мыши нет.

Слои Linux-графики (снизу вверх): пиксельный FB / DRM-KMS → композитор → протокол (Wayland) →
тулкит (GTK/Qt) → WM/приложения; сбоку — шрифты, ввод (libinput), **Mesa** (GPU).

**Порт Wayland+niri — против шерсти VOID и гора:**
- **libwayland** хочет unix-сокеты + `epoll` + передачу fd (`SCM_RIGHTS`) + POSIX-shm (`wl_shm`). У нас
  — **capability-IPC + разделяемые объекты стора**. Транспорт не ложится.
- **niri/smithay** (Rust, портируемее) хочет **DRM/KMS + libinput + EGL/Mesa (GL-рендер)**. **DRM+Mesa**
  — самая большая гора, и половина слоёв требует GPU/DRM, которого нет.

**Инсайт:** shared-object + capability — **лучшая подложка для композитора**, чем сокеты+`SCM_RIGHTS`.
Окно — это **буфер-объект + capability на него**; композитор склеивает объекты. Ложится на тезис
([[0002-persistent-content-addressed-capability-core]]). Более того: объект в персистентном сторе →
**GUI может пережить ребут** (наследие checkpoint, [[checkpoint]] Веха 37) — то, чего нет ни у Wayland,
ни у X.

## Решение
**Свой VOID-родной графический стек — «делаем сами», не порт чужого.**

- **Композитор-сервер** на capability-IPC: окно = **разделяемый буфер-объект + cap**; свой **крошечный
  протокол** (surface / attach-buffer / commit / damage + события ввода) — на порядки меньше Wayland.
  НЕ портируем Wayland/DRM/Mesa/GTK.
- **Свой тулкит** (immediate-mode, чистый Rust) — **пишем сам** (пользователь предпочёл своё, не egui).
- **Софт-рендер сначала** (CPU-блит + свой растеризатор шрифтов). **GPU-ускорение — потом**: целимся на
  **AMD** (amdgpu — открытые доки/исходники), НЕ Nvidia (закрыто). Сроков нет — делаем, чтобы рано или
  поздно дойти.
- **Пиксельный FB** — предпосылка; сперва **простейший путь «увидеть, что работает»** (UEFI-GOP или
  virtio-gpu — по удобству отладки). Плюс **мышь** (PS/2 или USB-HID — HID-клава уже есть, [[usb]]).
- **Политика окон:** сперва **плавающие**, со временем — **скроллируемый тайлинг «как niri»**.
- **Персистентный GUI — определяющая фишка:** окна и состояние **переживают ребут** (контент-адресуемо,
  наследие [[checkpoint]]). Не «ещё один Wayland», а своё в духе VOID.

## Последствия
- Огромная **поздняя фаза** (после vvsh [[0006-vvsh-lisp-config-shell]] и e1000→ping). VOID полезен и
  headless — графика не блокер, а флагман.
- Не тащим DRM/Mesa/libwayland/GTK → меньше внешней поверхности, но композитор+тулкит+рендер пишем сами.
- GPU-ускорение (AMD) — отдельная гора потом (порт amdgpu/DRM тем же dde_linux-конвейером ЛИБО своя
  минимальная поддержка); до неё — софт-рендер (для UI CPU хватает).
- **Персистентный GUI — новизна** (нет у Wayland/X): исследовательский риск и потенциально главная фишка.
- Предпосылки к старту: пиксельный FB + мышь.

## Альтернативы
- **Порт Wayland+niri+Mesa+DRM** — против шерсти (сокеты/`SCM_RIGHTS`/DRM), гора; отброшено.
- **Переиспользовать чистый-Rust GUI** (egui-стиль) — сняло бы тулкит-гору, но пользователь хочет своё.
- **X11 / иное legacy** — нет.
- **Только текст (headless навсегда)** — не отвечает цели «заменить рабочий NixOS».

## Дополнение (2026-08): предпосылка «пиксельный FB» закрывается раньше, терминалом

[[0014-terminal-ereb|ADR 0014]] вытаскивает **первый шаг вперёд**, не трогая ни одного решения
выше. Причина не в графике: знакогенератор VGA держит **256 глифов** (`font.rs`, `[u8; 4096]`),
поэтому нужных владельцу символов в текстовом режиме не будет никогда — нужен пиксель.

Что меняется для этого ADR:

- **FB перестаёт быть далёкой предпосылкой.** Он делается **тегом multiboot2**: VOID уже
  грузится GRUB'ом и уже разбирает теги, так что GRUB ставит режим через VBE и отдаёт готовый
  линейный буфер. Ни GOP, ни virtio-gpu, ни DRM. Оговорка: путь PVH (`-kernel`) фреймбуфера не
  даёт, графический дев-цикл идёт через GRUB-диск; riscv остаётся без FB.
- **Вопрос «кто владеет экраном» встаёт сразу.** В графическом режиме `0xB8000` больше нет, а
  значит правило владения буфером и судьба `vprintln` (serial или своя пиксельная консоль ядра)
  решаются здесь, до всякого композитора.
- **Мышь по-прежнему не сделана** — вторая предпосылка остаётся открытой, терминалу она не нужна.
- **Граница держится явно: ereb — это терминал, а не композитор.** Его мультиплексор (тайлинг +
  маршрутизация ввода + композиция) — по сути 60% композитора, поэтому в ADR 0014 он поставлен
  ПОСЛЕДНИМ шагом: иначе он молча определил бы форму этой фазы. Окно-как-объект, персистентный
  GUI и свой тулкит остаются решениями этого ADR.
