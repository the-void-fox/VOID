# Lx_kit-рантайм: один поток, отдельные стеки, setjmp/longjmp

Это **главный дизайн-развилок** нашего порта. Ниже — как устроен рантайм у Genode
(из `repos/dde_linux/src/lib/lx_kit/{scheduler,task}.cc`) и как мы это кладём на VOID.
Обзор — в [[00-overview]]; порядок инициализации — в [[20-linker-driven-workflow]].

## Центральная идея: весь Linux-код — в ОДНОМ кооперативном потоке

Genode сворачивает **все** ядровые нити, workqueue, tasklet'ы и таймер-коллбэки в
**один поток управления** (Genode entrypoint, EP). Никакого вытеснения: задачи
переключаются только в явных точках. Следствие, критичное для нас:

- **spinlock / mutex / local_irq_disable внутри Linux-кода становятся почти no-op** —
  сериализация уже обеспечена тем, что поток один. Не нужны настоящие атомики/локи
  ради самого драйвера (атомики всё же нужны на стыке с реальным IRQ — см. ниже).
- Гонок внутри портированного `.c` структурно нет — резко упрощает отладку.
- «Блокирующий» вызов ядра (`msleep`, `wait_event`, `schedule()`) = задача уступает
  управление планировщику, а не крутит буси-цикл.

## Task — как устроена задача (task.cc)

- **Отдельный стек на задачу**: `_alloc_stack()` выделяет ~32 КиБ вторичного стека.
- **Контекст-свитч через `setjmp/longjmp`** (не ucontext, не нити ОС):
  - `run()`: `if (_setjmp(_saved_env)) return;` — ставит точку возврата в планировщик.
    Первый запуск (state `INIT`): `arch_execute(_stack, _func, _arg)` — прыжок на стек
    задачи и старт её функции.
  - `schedule()` (задача уступает): `if (_setjmp(_env)) return;` — сохранить своё
    окружение, затем `_longjmp(_saved_env, 1)` — вернуться в планировщик.
  - Возобновление: `run()` видит, что state ≠ INIT, и делает `_longjmp(_env, 1)` —
    задача продолжается ровно с точки, где уступила.
  - `block_and_schedule()`: пометить state = BLOCKED, затем `schedule()` — уйти в
    планировщик и не возвращаться, пока кто-то не разблокирует.
- Свойства задачи: приоритет, **тип** (`IRQ_HANDLER`, `TIME_HANDLER`, …), состояние
  (runnable / blocked / to-destroy).

## Scheduler — цикл (scheduler.cc)

- Задачи — в приоритетно-упорядоченном списке `_present_list`; `_current` — текущая,
  плюс `_idle`-задача.
- `_execute()`: «пройти по задачам, запустить первую runnable; после её выполнения
  начать сначала с головы списка» — так держится приоритетный порядок.
- Пробуждение по категориям: `unblock_irq_handler()` / `unblock_time_handler()`
  идут по списку и делают `unblock()` задачам нужного типа.
- Внешние события (IRQ, таймер) вызывают `schedule()`, который **шлёт сигнал** EP →
  повторный `_execute()`. Иллюзия вытеснения = повторный вход по сообщению.
- Инвариант: коллбэк-обработчик вызывается **только из EP-контекста** (проверка
  идентичности потока) — весь Linux-код сериализован в одном треде.

## jiffies, таймеры, workqueue, tasklet, NAPI, IRQ — на чём стоят

- **jiffies / таймеры**: драйвится Genode-таймером; `TIME_HANDLER`-задача просыпается,
  двигает jiffies и запускает выстрелившие `timer_list`-коллбэки. `mod_timer`/`del_timer`
  — операции над очередью таймеров рантайма.
- **workqueue / tasklet**: не реализуются «по-настоящему» — остаются кодом Linux, а
  рантайм даёт им кооперативную задачу-исполнитель. `schedule_work`/`queue_work` кладут
  work в очередь, задача-воркер её крутит в общем потоке.
- **NAPI / softirq**: та же модель — poll вызывается из задачи, не из отдельного softirq-контекста.
- **IRQ**: реальное прерывание приходит извне (у Genode — IRQ-сессия), обработчик —
  `IRQ_HANDLER`-задача, которую будят `unblock_irq_handler()`. Тело Linux-`request_irq`
  регистрирует handler, а рантайм вызывает его кооперативно после сигнала IRQ.

## Как это лечь на VOID (наше решение)

Первоначальный план был «threads + futex». **Пересматриваем в пользу Genode-модели** —
один поток + setjmp/longjmp + отдельные стеки. Почему для VOID это лучше:

- У нас `lx_kit.c` компилируется void-libc/newlib — `setjmp/longjmp` есть из коробки,
  отдельный стек и «прыжок на него» — маленький арх-специфичный `arch_execute`
  (сменить SP, вызвать функцию) на riscv64 и x86_64 (2 короткие асм-вставки).
- Убирает необходимость настоящих атомиков/локов ради драйвера (наша оговорка Вехи 58
  «set_bit не атомарен» перестаёт быть проблемой для однопоточного Linux-кода).
- Детерминизм и отладка: нет преемпшна внутри портированного кода.
- Futex/нити VOND (Веха 35) остаются, но **не** внутри Lx_kit — они для честной
  многозадачности userspace, а Linux-мир живёт в одном потоке процесса-драйвера.

**Что реально написать в `lx_kit.c` для этого (следующие вехи):**
1. `struct lx_task { jmp_buf env, saved_env; int state; int type; void *stack; ... }`.
2. `lx_task_create(fn, arg)`, `lx_sched_schedule()` (уступить), `lx_sched_run()` (цикл),
   `lx_task_block()/unblock()`.
3. `arch_execute(stack, fn, arg)` — арх-вставка (riscv64: сменить `sp`, `jalr`; x86_64:
   сменить `rsp`, `call`).
4. Поверх: `jiffies` + очередь `timer_list`, `schedule_work`, тело `request_irq`
   (регистрация; вызов — из нашей `SYS_IRQ_WAIT`-петли, Веха 52), `wait_event`/`wake_up`
   как block/unblock, `msleep` → block до таймера (вместо буси-паузы Вехи 61 —
   `udelay/mdelay` остаются буси, они «короткие аппаратные», а `msleep` должен уступать).

**Стык с реальным IRQ VOID.** Реальное прерывание у нас приходит через `SYS_IRQ_WAIT`
(cap, Веха 52) — это единственная точка, где нужен настоящий атомарный флаг между
IRQ-ожидателем и кооперативным циклом (top-half ставит флаг/будит `IRQ_HANDLER`-задачу).
Всё остальное — один поток.
