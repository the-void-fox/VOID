# Линкер-ориентированная разработка порта

Как перестать угадывать API «на упреждение» и дать **линкеру диктовать список дел**.
Ровно так Genode доводит крупный драйвер до линкуемого бинаря. Обзор — [[00-overview]];
рантайм, который наполняет тела, — [[10-lx-kit-runtime]].

## Петля: compile → link → stub → повторить

1. **Compile.** Взять реальный `.c` драйвера, компилировать против заголовков (у нас —
   наши шимы + то, что добавляем по ходу). Чинить только ошибки *типов/парсинга*, не
   реализовывать функции.
2. **Link.** Слинковать всё вместе. Линкер выдаст список **неопределённых символов** —
   это и есть очередь задач.
3. **Stub.** Каждый неопределённый символ закрыть заглушкой:
   - **Массово, автоматом** — сгенерировать пустые тела (`generated_dummies.c`).
   - **Точечно, руками** — для символов, которым «нужно больше, чем просто заглушка»
     (реальное поведение), — написать тело (у нас — в `lx_kit.c` или отдельном
     `lx_emul/*.c`).
4. **Повторить**, пока не слинкуется. Затем — инициализация и probe.

Плюс: не пишем ни строчки API, которого драйвер не трогает. Поверхность из
[[30-e1000-porting-map]] «сжимается» до реально используемого подмножества.

## Инструменты Genode (что копируем идеей, не кодом)

- **`create_dummies`** (`tool/dde_linux/create_dummies`): автоматизирует бывшую ручную
  работу — генерит пустые тела для неопределённых символов, чтобы быстро получить
  линкуемый бинарь. Выход — **`generated_dummies.c`**.
- **`dummies.c`** (ручной): здесь живут функции, которые нельзя оставить пустыми —
  им нужно осмысленное поведение. Разделение auto/manual — важное: не редактируешь
  сгенерированный файл, перегенерация его затирает.
- **`extract_initcall_order`** → **`initcall_order.h`**: снимает из настоящей сборки
  ядра порядок initcall'ов, чтобы выполнить инициализацию **в точности как Linux**.
  Без него lx_emul не знает порядок (`Lx_emul won't know the order`).

### Наши маленькие аналоги (что реально сделать)

- **Генератор заглушек** — тонкий скрипт: прогнать линковку, из `undefined reference`
  вытащить имена, сгенерить `lx_stubs.c` с `void NAME(void) { lx_emul_trace_and_stop(__func__); }`
  (или warn-once + return 0). Держать отдельно от ручного `lx_emul_impl.c`.
- **Порядок initcall** — на первом драйвере можно **вручную** перечислить нужные
  initcall'и (их немного для одного драйвера), позже — снять из ядровой сборки.

## Редирект `module_init` / initcall

Ядро регистрирует инициализацию через секции initcall и `module_init`. В хостинге их
надо вызвать явно. Классический приём Genode/dde_linux:

```c
#define module_init(fn)  void module_##fn(void) { fn(); }
#define module_exit(fn)  void module_exit_##fn(void) { fn(); }
```

Тогда `module_init(e1000_init_module)` порождает вызываемый `module_e1000_init_module()`,
который дёргаем из нашей точки старта. `MODULE_*`-макросы (`MODULE_AUTHOR`,
`MODULE_LICENSE`, `MODULE_DEVICE_TABLE`, …) раскрываем в пусто.

Дефайны сборки, которые ждёт ядровый код: `__KERNEL__`, `KBUILD_MODNAME="e1000"`,
`CONFIG_*` под нужную конфигурацию (у нас уже есть `-DCONFIG_64BIT` в nix/default.nix —
растёт список `CONFIG_PCI`, `CONFIG_NET`, …).

## Probe и driver-model

- После initcall'ов драйвер зарегистрирован в driver-model. Устройство матчится с
  драйвером в `drivers/base/dd.c` → вызывается `.probe`.
- Поддержать **отложенный пробинг**: драйвер может вернуть `-EPROBE_DEFER`, если
  предусловие не готово (`drivers/base/dd.c` бэкоффит и повторяет). Для e1000 на первом
  заходе, скорее всего, не понадобится, но заложить в модель.
- PCI-матч по таблице `pci_device_id` (`MODULE_DEVICE_TABLE(pci, ...)`).

## Порядок доводки (сжатый чеклист)

1. Компилируется (типы) → 2. Линкуется (заглушки) → 3. initcall'и в порядке Linux →
4. probe нашёл устройство (PCI-матч) → 5. netdev поднялся, `open` → 6. TX/RX по кольцам
через DMA-cap → 7. стык с наружу (`net-srv`). Детали шага 5–7 — в [[30-e1000-porting-map]].
