# Веха 7.2 — «ОС не забывает» в коде

Кульминация стержня: [[object-model|объектная модель]] стала долговечной. Принцип — в
[[persistence-and-volatility]] (RAM это кэш, диск это истина), инструмент — [[virtio-blk]]
(чтение/запись секторов). Здесь — как это собрано на диске.

## Раскладка диска (секторы по 512 Б)
```text
  0            суперблок  — 1 сектор = АТОМАРНАЯ запись = точка коммита
  1 .. 17      индекс A  ┐  чередуются; суперблок говорит, какой активен
  17 .. 33     индекс B  ┘
  33 ..        область объектов — только ДОписывается, никогда не перезаписывается
```
- **Суперблок**: магия, поколение (номер коммита), активный индекс (A/B), next_free_sector,
  число объектов, контент-адрес корня «system».
- **Индекс**: массив записей `{ ContentId(32) | сектор(4) | длина(4) }`, по 64 Б (делит 512 →
  8 записей в секторе, без нахлёста).
- **Объекты**: байты значений, каждое с выравниванием по сектору.

## Как это крах-устойчиво
Три свойства складываются в «всё или ничего»:
1. **Объекты неизменяемы** (адрес = хэш) → только дописываются, существующие не портятся.
2. **Индекс пишется в НЕактивный регион** (A↔B), активный остаётся валидным.
3. **Суперблок — одна запись сектора** (атомарна) и пишется ПОСЛЕДНИМ.

Сбой в любой момент до записи суперблока → на загрузке читается старый суперблок, а он указывает
на старый (нетронутый) индекс и старые объекты. Сбой после — читается новый. Промежуточного
состояния не существует. Это ровно то «безопасное сохранение», ради которого нужна
контент-адресация (см. ADR 0002 и [[persistence-and-volatility]]).

## Поток load / commit
- **`load()`** (ЛЕНИВО, доводка): прочитать суперблок (нет магии → чистый диск); прочитать
  активный индекс — только МЕТАданные `(ContentId → сектор, длина)`, байты объектов **не читаем**;
  подтянуть roots-blob и разобрать корни; восстановить поколение, next_free. Байты значения
  подтянет `with()` при первом обращении (промах кэша).
- **`commit()`**: сериализовать корни в roots-blob (сам — контент-адресуемый объект); дописать
  объекты без места на диске (append); записать полный индекс в неактивный регион; записать
  суперблок (поколение+1, новый активный индекс, адрес roots-blob) — коммит.

RAM-хранилище ([[object-model]]) — рабочая копия/кэш; диск — источник истины. С ленивой загрузкой
это уже не фигура речи: вся база не обязана влезать в RAM, в RAM живёт рабочее множество.

## Множественные корни (доводка после Вехи 9)
Раньше на диск писался ровно один корень «system» (32 Б в суперблоке). Теперь карта корней
`{имя → ContentId}` сериализуется в **отдельный объект** (roots-blob), а суперблок хранит лишь его
контент-адрес. Персистентен любой именованный корень. Формат blob: `count | [len|имя|id]*`.
Приём на тему проекта: механизм корней выражен через сам объектный store, а не сбоку от него.

## Проверка (три запуска подряд, один диск)
```
запуск 1: диск пуст — ПЕРВЫЙ запуск           → commit: 7 объектов, поколение 1
запуск 2: загружено 7 объектов, поколение 1
          system root С ПРОШЛОГО запуска: "boot #1 …"   → commit: 8 объектов, поколение 2
запуск 3: system root С ПРОШЛОГО запуска: "boot #2 …"   → commit: поколение 3
```
Корень и объекты переживают выключение QEMU; поколение растёт; прошлые версии корня остаются в
store (неизменяемая история). Задачи каждый запуск кладут одинаковые значения → дедуп, рост
только на 1 маркер за запуск.

## Осознанные упрощения (чиним позже)
- ~~Ленивая загрузка~~ — **сделана** (см. выше).
- ~~Один корень~~ — **сделано**: множественные персистентные корни (см. выше).
- ~~Нет сборки мусора~~ — **сделано**: `gc()` от корней + уплотняющий commit (см. [[object-model]]).
- **Без flush-барьера**: полагаемся на то, что QEMU долетает до файла. На реальном железе нужен
  барьер записи для настоящей durability (см. [[persistence-and-volatility#Цена долговечности]]).
- **Коммит по требованию** (в конце kmain), не автоматический.

## Что это закрывает
**Фаза 1 (стержень VOID) состоялась**: контент-адресуемые неизменяемые объекты + изменяемый
корень + долговечность на диске. То, ради чего затевался проект, работает от загрузки до
перезагрузки.
