# Веха 19 — программа как объект store

Фаза 3 ([[0003-phase-3-exec-by-hash|ADR 0003]]): код программы становится таким же
контент-адресуемым объектом [[object-model|store]], как любое значение — с content-id, версией
и персистентностью, — а не функцией, вшитой в секцию `.user` образа ядра ([[processes]]). Запуск
программы теперь может означать «прочитать байты ELF по content-id и загрузить их», а не
«прыгнуть на адрес в образе ядра».

## 19.1 — программа как отдельный ELF-крейт
`Code/programs/hello` — самостоятельный `#![no_std] #![no_main]` крейт: своя точка входа
(`extern "C" fn _start(arg: usize) -> !`, обычная функция — НЕ ассемблерный трамплин, адрес входа
загрузчик берёт из `e_entry` заголовка ELF, а не из позиции символа в файле) и свой линкер-скрипт
(`programs/hello/linker.ld`), линкующий на базу `0x4000_0000` — начало региона VPN[2]=1, того же,
где раньше жил только стек процесса (см. `proc::USER_REGION_START`). Стек программе, как и всегда,
даёт ядро — линкер-скрипт его не резервирует.

**НЕ член workspace ядра** (`exclude` в `Code/Cargo.toml`) — у своего профиля release (`opt-level
= "z"`, LTO, `panic = "abort"`, `strip = true`, `codegen-units = 1`) нет смысла жить в общем
workspace-профиле ядра: весь ELF целиком ложится в объектный store, кэш которого — это та же
2-МиБ куча ядра, что делят между собой ВСЕ демо. Результат — **8840 байт** готового ELF (заголовок
+ два `PT_LOAD` + напечатать строку и выйти): единицы КиБ, как и требовалось.

### Линковка: три PT_LOAD с разными правами, не один
`linker.ld` явно объявляет `PHDRS` с тремя сегментами — `text` (R+X), `rodata` (R), `data`
(R+W, для `.data`+`.bss`) — вместо того, чтобы положиться на автоматическую группировку линкера.
Между каждым — `ALIGN(4K)`: если бы два сегмента с РАЗНЫМИ правами делили одну 4-КиБ страницу,
загрузчик (см. ниже) замаппил бы эту страницу дважды разными флагами, и последняя запись тихо
победила бы (порча прав без единого сообщения об ошибке). Явные `PHDRS` + выравнивание убирают
эту ловушку на уровне сборки, а не рантайма.

## 19.2 — минимальный ELF-загрузчик (`kernel/src/elf.rs`)
Разбирает заголовок ELF64 (магия, класс, машина `EM_RISCV`, тип `ET_EXEC` — только статические,
без релокаций/`PT_DYNAMIC`) и program header'ы. Для каждого `PT_LOAD`:
- фреймы выделяются постранично (`frame::alloc` — уже обнулённые);
- копируется файловая часть сегмента (пересечение страницы с `[p_vaddr, p_vaddr+p_filesz)`);
- bss **не зачищается отдельно** — фрейм уже нулевой, а копируется ровно `p_filesz` байт, так что
  хвост (в т.ч. страницы целиком за пределами файловой части) остаётся нулём сам по себе;
- маппится `paging::map(root, va, pa, flags)` с правами из `p_flags`, **плюс `U`**; если у сегмента
  сошлись `W` и `X` — жёсткий отказ (`ElfError::WriteExec`), а не попытка «угадать» намерение.

Границы: сегменты обязаны лежать в `[proc::USER_REGION_START, va_limit)`, где `va_limit` —
низ приватного стека ЭТОГО ЖЕ адресного пространства (передаётся из `proc::spawn_elf`, а не
захардкожен в `elf.rs` — единственный источник правды про раскладку у `proc.rs`). Иначе кривой
(или недоверенный) ELF мог бы попросить сегмент поверх маппинга стека, и `paging::map` его тихо
перезаписал бы той же логикой листового PTE, что и любой другой маппинг.

### `proc::spawn_elf` — общий путь с `proc::spawn`
`proc::spawn` (Веха 10.2a) уже умел: клонировать корень ядра + замаппить приватный стек + завести
запись в таблице процессов с заданной точкой входа. Это ровно то, что нужно и для ELF-процесса —
различается только ИСТОЧНИК точки входа (адрес функции в `.user` vs `e_entry` из ELF). Рефакторинг
вынес общее в `new_address_space()` (клон корня + стек) и `create_process()` (домен + кадр +
запись в таблице), так что:
```rust
pub fn spawn(name, entry, arg) -> usize {
    let root = new_address_space();
    create_process(name, root, entry, arg)
}
pub fn spawn_elf(name, elf_bytes, arg) -> Result<usize, elf::ElfError> {
    let root = new_address_space();
    let entry = elf::load(root, elf_bytes, va_limit)?;   // единственное отличие
    Ok(create_process(name, root, entry, arg))
}
```
Отказ `elf::load` (плохой ELF) не заводит процесс и не трогает таблицу — вызывающий получает
`Err` до того, как что-либо необратимо случилось.

## 19.3 — интеграция: семя vs store
`kernel/build.rs` собирает `programs/hello` ОТДЕЛЬНЫМ `cargo build` (см. «грабли» ниже) и передаёт
путь к готовому ELF через `cargo:rustc-env=HELLO_ELF=...`; `main.rs` включает его байты как
`static HELLO_ELF: &[u8] = include_bytes!(env!("HELLO_ELF"))`. Это **семя**, не тело исполнения:

```rust
fn exec_demo() {
    let id = match object::root("bin/hello") {
        Some(id) => id,                              // корень уже на диске — seed не нужен
        None => {                                     // первый запуск: посеять
            let id = object::put(HELLO_ELF);
            object::set_root("bin/hello", id);
            id
        }
    };
    let elf_bytes = object::with(&id, |b| b.map(|x| x.to_vec())); // читаем ИЗ STORE по id
    let bytes = elf_bytes.unwrap();
    let pid = proc::spawn_elf("hello", &bytes, 0).unwrap();
    proc::run();
}
```
Ключевое: путь чтения **одинаков для обоих запусков** — программа исполняется байтами, прочитанными
`object::with` по `content-id`, а не напрямую `HELLO_ELF`. На втором запуске (после перезагрузки)
`object::root("bin/hello")` находит корень, посеянный в прошлый раз, встроенные в ядро байты вообще
не читаются. Корень `bin/hello` переживает `object::gc()` в конце `kmain`, потому что GC помечает
достижимое **от корней** — а `bin/hello` теперь один из них, как `system`/`greeting`/`.dir`.

## Грабли: deadlock на локе target ядра
Первая мысль — собрать `programs/hello` внутри `kernel/build.rs` **тем же** `cargo build`, что
собирает и ядро. Не работает: build-скрипт запускается КАК ЧАСТЬ уже идущего `cargo build` ядра,
который держит файловый лок на `Code/target/`. Если дочерний `cargo build` (даже для другого
крейта) попробует взять тот же лок — гарантированный deadlock, оба процесса зависнут. Решение —
свой `--target-dir` СТРОГО внутри `OUT_DIR` ядра (`OUT_DIR/hello-target/...`): это отдельный от
`Code/target/` каталог, свой лок, никакой коллизии. Плюс `CARGO` (путь к бинарнику cargo,
которым нас собирают, передаётся build-скрипту как переменная окружения) вместо `cargo` из PATH —
гарантия, что дочерняя сборка возьмёт ТОТ ЖЕ toolchain, а не что попало из `$PATH`.

## Осознанные упрощения (что осталось на потом)
- **Только `ET_EXEC`, без релокаций/`PT_DYNAMIC`/`PT_INTERP`.** Одна программа — одно фиксированное
  адресное пространство. Динамическая линковка/PIE — отдельный, существенно больший шаг (нужен
  релокатор в ядре).
- **Одна программа-демо (`hello`).** Инфраструктура (`spawn_elf`, загрузчик) не завязана на
  конкретную программу — второй ELF-крейт добавляется тем же путём (свой `Cargo.toml` в
  `programs/`, добавить в `exclude` и в `build.rs`).
- **Нет проверки на дублирующиеся/пересекающиеся `PT_LOAD`** сверх базовой проверки границ региона
  и `ALIGN(4K)` на уровне линкер-скрипта — для доверенного (собственной сборки) ELF этого
  достаточно; для недоверенных бинарников понадобится более строгая валидация.
- **`bin/<имя>` делит пространство корней** с системными (`system`, `greeting`) и файлами
  персоналии (`.dir`, `motd.txt` и т.п.) — то же упрощение, что уже отмечено в
  [[posix-personality]] для файлов.

## Что дальше
- Вторая программа поверх того же пути (например, ELF-версия `mini-sh` вместо варианта на
  `.user`) — доказать, что загрузчик не завязан на одну программу.
- Capability на «право исполнить объект X» — сейчас `bin/hello` виден всем, у кого есть store-cap
  (как любой другой корень); отдельное право exec — следующий шаг гранулярности.
- Обновление программы без пересборки ядра: сменить корень `bin/hello` на новый content-id
  (например, положенный через store-сервер по IPC, Вехи 13/14) — уже работает механически,
  осталось явно продемонстрировать.
