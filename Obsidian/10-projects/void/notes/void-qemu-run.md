# Как гонять VOID в QEMU по-настоящему

`-cdrom void.iso` даёт устройство **только для чтения**. Store честно отказывается коммитить и
пишет «на диске прежнее консистентное поколение» — это не поломка, а правильный отказ: система
работает, но ничего не сохраняет (ни `rebuild`, ни правки конфига, ни пакеты). ISO — образ
УСТАНОВКИ, его дело загрузиться и записать себя на диск.

Для работы нужен образ ДИСКА:

```
nix-shell -p grub2 mtools util-linux --run \
  "Code/boot/mkdisk.sh Code/target/x86_64-unknown-none/release/void-kernel /var/tmp/void.img 700"

qemu-system-x86_64 -machine q35 -m 1280M -accel kvm \
  -device ich9-ahci,id=a \
  -drive if=none,id=d,file=/var/tmp/void.img,format=raw \
  -device ide-hd,drive=d,bus=a.0 -boot c \
  -device virtio-rng-pci,disable-legacy=on \
  -netdev user,id=n0 -device virtio-net-pci,netdev=n0,disable-legacy=on
```

**`-accel kvm` обязателен, если смотрят на скорость.** Без него QEMU эмулирует каждую инструкцию
(TCG), и кадр композитора стоит там сотни миллисекунд — именно поэтому замеры анимации в
`screenrun.py` бесполезны как оценка плавности: там мерится эмулятор, а не VOID.

**Не класть образ в `/tmp`**: на NixOS это tmpfs, то есть оперативная память (см. `flash.sh`,
Веха 126.2). `/var/tmp` или каталог сборки.

## Сетевой стенд (Веха 135)

До этой вехи сеть проверялась ровно одним способом: `-netdev user`, то есть SLIRP. Это **не
провод, а НАТ внутри QEMU** — он отвечает мгновенно и всегда, сам сочиняет ответы на ARP и DHCP,
широковещание за свои пределы не пускает и не показывает, что мы реально положили на провод.
Проверка «работает в SLIRP» стоит немного: так уже пряталась вялость старта из-за глухого цикла
DHCP (Веха 134).

Три ручки у `screenrun.py`, все без привилегий:

```
VOID_QEMU_NIC   virtio | e1000 | none      какую карту показать гостю
VOID_QEMU_NET   user | seg:<путь> | join:<путь> | tap:<имя> | none
VOID_QEMU_PCAP  <файл.pcap>                записать ВСЁ, что прошло через карту
VOID_QEMU_MAC   52:54:00:00:00:0a          иначе у всех машин MAC одинаковый
VOID_QEMU_SNAPSHOT 1                       писать во временный слой, а не в образ
```

**pcap — главное приобретение.** Раньше о трафике судили по журналу, то есть по тому, что VOID
про себя говорит. Теперь видно, что он делает:

```
VOID_QEMU_PCAP=/var/tmp/wire.pcap python3 Code/tools/screenrun.py образ.img сценарий.txt вых/
nix-shell -p tcpdump --run "tcpdump -r /var/tmp/wire.pcap -nn -ttt"
```

Пустой pcap — это 24 байта (только заголовок). Ровно 24 значит «на проводе не было НИ ОДНОГО
кадра» — отдельный диагноз, не путать с «мало трафика».

### Два VOID'а на одном проводе

```
nix-shell -p qemu --run "python3 Code/tools/netlab.py образ.img сцен-A.txt сцен-B.txt вых/"
```

`-netdev stream` через unix-сокет соединяет две QEMU кадр в кадр, без чужого стека посередине.
Ни root, ни tap, ни моста не нужно. Обе стороны пишут свой pcap в `вых/{a,b}/wire.pcap`, MAC'и
разные, образ открывается снимком (иначе вторая машина падает на «Failed to get write lock»).

Ограничение: **адрес у обеих сторон одинаковый**. Он лежит в конфиге поколения внутри store, а
store — в образе, который у сторон общий; на голом сегменте DHCP не отвечает, и обе берут одну и
ту же статику. Для проверки L2 и широковещания годится, для разговора между машинами — нет. Обход:
`VOID_LAB_IMG_B=другой.img` — сторона B пойдёт со своего образа со своим `net.vv`.

### Управляемый сосед: ARP, ICMP и DNS (Веха 136)

На голом сегменте никто не отвечает на DNS, а SLIRP отвечает сам — мгновенно и не теряя.
`netpeer.py` — «остальной мир» одним скриптом, с ручками на всё, ради чего у DNS есть повторы:

```
python3 Code/tools/netpeer.py --listen /tmp/void-seg.sock --zone a.void=10.0.2.99 &
VOID_QEMU_NET=join:/tmp/void-seg.sock python3 Code/tools/screenrun.py образ.img сцен.txt вых/
```

Сосед слушает, VOID присоединяется (`join:`). По умолчанию берёт адреса 10.0.2.2 и 10.0.2.3 —
те же, что `net-srv` берёт статикой, так что VOID попадает в привычный мир, только честный.
Ручки: `--loss 0.6` (детерминированно по `--seed`), `--delay МС`, `--rcode servfail|nxdomain`,
`--silent`, `--truncate`, `--zone имя=адрес`, `--ip` (можно несколько).

### Выход в настоящую сеть

`VOID_QEMU_NET=tap:<имя>` — требует, чтобы tap был заведён заранее и принадлежал пользователю
(разово, от root): `ip tuntap add dev void0 mode tap user $USER`, дальше в мост или с адресом на
хосте. QEMU сам tap не создаёт: `script=no`.

### Чего эмулятор не даст

Никакой эмулятор не изображает AR8151 (наша atl1c на X54C) — ни QEMU, ни Bochs, ни 86Box, ни
VirtualBox. QEMU из них как раз самый богатый по устройствам; «более продвинутые» точнее
воспроизводят процессор, а не расширяют список карт. Драйвер конкретного чипа проверяется только
на этом чипе.

### Задержка канала

`VOID_QEMU_DELAY_US=15000` — `-object filter-buffer`, придерживает кадры и выпускает их
периодически. Локальный провод отвечает за 0.3 мс, и на нём НЕ ВИДНО ничего, что зависит от
произведения «полоса × задержка»: окна TCP, ретрансмиссий, размера порции. Настоящая сеть — это
десятки миллисекунд, и там ошибка в окне стоит порядков скорости. Именно так нашёлся зажатый
`max_burst_size` (Веха 135): на локальном проводе он давал 4 МиБ/с и выглядел здоровым.
