# Веха 18 — POSIX-персоналия как сервер

Первый шаг слоя совместимости ([[0002-persistent-content-addressed-capability-core|ADR 0002]],
Фаза 2): **POSIX-подобная персоналия живёт в userspace-сервере**, а не в ядре. Программа-клиент
пользуется только POSIX-вызовами (`open`/`write`/`close`/`read`) через тонкий IPC-shim и «не знает»,
что под ней VOID. Классика микроядер (L4Linux, BSD-сервер в Mach): личность ОС — это сервис, а не
ядро.

> **Что это НЕ:** запуск настоящих Linux-ELF-бинарников (загрузчик + эмуляция сотен syscall'ов +
> libc) — отдельная вселенная. Здесь — POSIX-подобный **файловый API через персоналию**, что и есть
> суть «личность как сервер».

## Протокол (поверх готовых IPC/[[ipc-endpoints|эндпоинтов]])
Никаких изменений ядра — только новый сервер и клиент. `op` кодирует операцию (младший байт) и
дескриптор (`op | (fd<<8)`):
- **`OPEN`** `(name)` → `fd` (1 байт в ответе): найти файл по имени или создать, выделить дескриптор.
- **`WRITE`** `(fd, data)`: дописать данные со смещения дескриптора.
- **`READ`** `(fd)` → `bytes`: прочитать с смещения до конца (клиент ограничивает `recv_cap`).
- **`CLOSE`** `(fd)`: освободить дескриптор (файл остаётся в namespace).

## Почему namespace на стеке сервера
У процessов **нет кучи** (userspace без аллокатора — только стек, статики, syscall'ы). Поэтому
namespace фикс. размера (`PX_NFILES` файлов × `PX_DATA_MAX` байт) и таблица дескрипторов живут в
кадре главного цикла сервера. Данные — в `MaybeUninit` (без обнуления → без `memset` в `.user`);
валидность отслеживаем сами (`used`/`size`). Все копии/сравнения — сырыми указателями: ни `memcpy`,
ни паник-путей. Имя/данные клиента приходят в буфере запроса ([[object-store-server|Веха 13]]),
`fd` возвращается в буфере ответа.

## Проверка (вывод в QEMU)
```
[proc] POSIX-персоналия (файлы open/write/close/read) через IPC:
  P7 'posix-app' ← cap на эндпоинт персоналии P6 'posixfs'
[ipc] P7 CALL P6 op=0 (9 байт)   ← open("hello.txt")
[ipc] P7 CALL P6 op=2 (33 байт)  ← write(fd, "...")
[ipc] P7 CALL P6 op=3 (0 байт)   ← close(fd)
[ipc] P7 CALL P6 op=0 (9 байт)   ← open("hello.txt") снова
[ipc] P7 CALL P6 op=1 (0 байт)   ← read(fd)
[posix-app] read('hello.txt') -> Hello, POSIX personality on VOID!
```
Программа создала файл, записала строку, закрыла, открыла по имени и прочитала обратно — файловый
раунд-трип целиком через сервер-персоналию по IPC. Остальные сессии (драйвер, store, вытеснение) и
персистентность не задеты.

## Веха 18.2 — персистентность через store
Персоналия получает **cap на store** (`arg`) и делает файлы долговечными, **не dir-blob'ом, а через
корни-имена**. Ключевой факт: GC ядра оставляет лишь объекты, достижимые **от корней**, поэтому
содержимое файла привязывается к корню-имени (`OBJ_SET_ROOT(name, id)`) — так оно переживает и GC, и
перезагрузку. Приятное следствие: **роты хранилища и есть директория** — не нужен отдельный
сериализованный каталог:
- `open(name)`: сперва искать в RAM namespace; если нет — `OBJ_GET_ROOT(name)` → есть? занять слот и
  поднять содержимое (`OBJ_GET`) : создать пустой.
- `write(fd, …)`: пометить файл «изменён» (`dirty`).
- `close(fd)`: если изменён — `OBJ_PUT(content)` → id, `OBJ_SET_ROOT(name, id)` (как `fsync` на
  закрытии). Всё через **существующие** шлюзы store — изменений ядра снова нет.

Проверка (два запуска подряд):
```
── запуск 1 ──
[obj] P6 OBJ_GET_ROOT 'hello.txt' → нет
[posix-app] hello.txt not found, writing it (first boot)
[obj] P6 OBJ_PUT 33 байт → content-id ; [obj] P6 OBJ_SET_ROOT 'hello.txt'
── запуск 2 (после перезагрузки) ──
[obj] P6 OBJ_GET_ROOT 'hello.txt' → есть ; [obj] P6 OBJ_GET → 33 байт
[posix-app] hello.txt from previous boot: Hello, POSIX personality on VOID!
```
Файл, созданный POSIX-программой, пережил перезагрузку и прочитан обратно **целиком через
персоналию** — POSIX-семантика поверх контент-адресуемого персистентного пространства.

## Веха 18.3 — каталог, stat/unlink/readdir, режимы open
Персоналия дорастает до «настоящей» ФС по мелочи. Почти всё — снова **в userspace**, но одна
честная дыра чинится **в ядре**.

**Ядро (единственное изменение):** появился шлюз `OBJ_DEL_ROOT` (снять корень под правом `WRITE`)
+ `object::del_root`. Это не POSIX-мелочь, а закрытие реального изъяна store: корень можно было
**привязать, но никогда отвязать** — вечная утечка. Снятый корень уходит в GC (если больше ни на
что не сослан), поэтому `unlink` теперь **честный**, а не «пометить пустым».

**Индекс каталога.** Роты хранилища — это множество, которое ядро перечислять не даёт (да и не
должно: там и системные корни `system`/`greeting`). Поэтому персоналия ведёт **свой** список имён —
спец-корень `.dir` (`count | [nlen|name]*`), в RAM ровно в том же виде, что на диске; переживает
перезагрузку. Имя заносится в `.dir` и при персисте на `close`, и при загрузке файла из корня на
`open` — так `readdir` видит и файлы, привязанные к корню **до** появления индекса (напр. `hello.txt`
из 18.2).

**Новые вызовы и режимы:**
- `stat(name)` → `[exists | size]`: ищет в RAM, иначе смотрит корень (подгружает ради длины).
- `unlink(name)`: убрать из RAM-namespace + `OBJ_DEL_ROOT` + удалить из `.dir` (и переписать его).
- `readdir()` → имена через `\n` из индекса каталога.
- `open` **режимы** в `op` (`mode<<16`): `O_APPEND` (курсор в конец), `O_TRUNC` (обнулить).
- **Смещение — своё на каждый дескриптор**: два `open` одного файла = два независимых курсора.

Проверка (два запуска подряд, свежий диск):
```
── запуск 1 ──                       ── запуск 2 (после перезагрузки) ──
hello.txt not found (first boot)     hello.txt from previous boot: Hello, POSIX personality on VOID!
log.txt now: tick                    log.txt now: tick tick        ← O_APPEND растёт с reboot
stat log.txt: size=5                 stat log.txt: size=10
readdir: hello.txt log.txt scratch.txt   readdir: hello.txt log.txt scratch.txt
[obj] OBJ_DEL_ROOT 'scratch.txt' → снят ; unlink scratch.txt -> stat exists=0
```
`log.txt` дописывается на каждой загрузке (`O_APPEND`, персистентно); `readdir` перечисляет каталог;
`unlink` снимает корень (объект уходит в GC) и вычищает `.dir`. Прочие сессии и персистентность целы.

## Веха 18.4 — программа на чистом POSIX-shim (прозрачность)
Финал слоя совместимости: **отделяем shim от программы**. Раньше клиент сам писал `ecall`,
op-коды и `fd<<8` — он «знал», что под ним IPC/VOID. Теперь появляется **libc-заглушка** —
тонкий слой функций (`sh_open/read/write/close/readdir/exit`), прячущий весь ABI ядра, а поверх
неё — программа `mini-sh`, в теле которой **ни одного `ecall`, op-кода или capability**. Это и есть
смысл «личность как сервер»: программа переносима, знает только POSIX.

- **Непрозрачный дескриптор ОС.** У процессов нет U-записываемых статиков (секция `.user` — `R|X`,
  `.data/.bss` — не-`U`), поэтому глобального состояния libc нет: `ep` («связь с ОС») передаётся в
  shim явным аргументом — как контекст libc. Он не раскрывает ни IPC, ни VOID.
- **Стандартные потоки.** Наружу дескрипторы смещены на `+3`: `0/1/2` = stdin/stdout/stderr
  (POSIX). `write(1, …)` идёт в консоль ядра (`SYS_WRITE`) — программа не знает, что это UART; а
  `write(fd≥3, …)` — в персоналию. `cat` буквально `read(fd)` из файла → `write(1)` в stdout.
- **mini-cat / mini-echo.** `mini_echo` = `echo msg > path` (open `O_TRUNC` → write → close);
  `mini_cat` = `cat path` (open → цикл read → write(1) → close). Обе — только вызовы shim.

Проверка — `mini-sh` играет сессию `cat; echo > ; cat; ls` над `motd.txt` (два запуска):
```
── запуск 1 (чистый диск) ──          ── запуск 2 (после перезагрузки) ──
[mini-sh] $ cat motd.txt              [mini-sh] $ cat motd.txt
                    (пусто)           VOID says hi, written by mini-echo, kept by the personality
[mini-sh] $ echo "..." > motd.txt     [mini-sh] $ echo "..." > motd.txt
[mini-sh] $ cat motd.txt              [mini-sh] $ cat motd.txt
VOID says hi, ... the personality     VOID says hi, ... the personality
[mini-sh] $ ls                        [mini-sh] $ ls
motd.txt                              motd.txt
```
`motd.txt` пережил перезагрузку и прочитан обратно **программой, не знающей про VOID** — только
через POSIX-shim. Прочие сессии (драйвер, store, вытеснение) и персистентность целы, 0 PANIC.

## Осознанные упрощения (что осталось на потом)
- ~~**Namespace в RAM сервера** — файлы НЕ переживают перезагрузку.~~ **Закрыто на 18.2.**
- ~~**Нет `stat`/`unlink`/`readdir`, `O_APPEND`, смещений на дескриптор.**~~ **Закрыто на 18.3.**
- ~~**shim встроен в клиента** (программа знает про IPC/VOID).~~ **Закрыто на 18.4**: libc-заглушка +
  `mini-cat`/`echo`, программа знает только POSIX.
- **Файловые корни делят пространство имён с системными** (`system`/`greeting`/…) и с `.dir`.
  Коллизия имени файла с системным корнем = баг; префикс/поддиректория для fs-корней — позже.
- **Один каталог, плоский** (`.dir` — один список), без вложенных директорий/путей.
- **Фикс. размеры** (файлов/имени/данных/каталога), нет ошибок ENOSPC/EMFILE в POSIX-виде.
- **Дескрипторы глобальные** (один клиент в демо), не per-client по [[reply-capability|reply-cap]].
- **shim — набор функций, не настоящая libc**; нет `argv`/`errno`/буферизованного stdio, парсинга
  путей. Настоящие Linux-ELF-бинарники (загрузчик + сотни syscall'ов) — отдельная вселенная.
