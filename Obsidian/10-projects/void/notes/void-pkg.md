# void-pkg — развёрнутый план

Решение зафиксировано в [[0004-void-pkg]]; здесь — рабочая картина: как устроено, что в
каком порядке, где прецеденты и подводные камни.

## Декомпозиция «пакета» (почему это вообще решаемо)

| Часть | Что это | Переносимо? |
|---|---|---|
| Рецепт | derivation, PKGBUILD | да — это данные |
| Сборка | компилятор, окружение | да — на хосте (кросс) |
| **Runtime-ABI** | syscall'ы/libc, которые ждёт бинарь | **нет — единственный барьер** |
| Дистрибуция | хранение, зависимости, откат | у нас в ядре (store) |

Все стратегии — это разные способы пройти барьер ABI.

## Архитектура

```
void-pkg (резолвер; сначала на хосте, позже внутри VOID)
├── A. native / nix-cross:  собрано ПОД VOID (Rust std-порт; nixpkgs pkgsCross + VOID-libc)
├── B. linux-abi:           замыкания из кэша nixpkgs под Linux-персоналией (как есть)
└── C. wasi:                wasm32-wasi через wasmi (no_std), медленный fallback
        порядок разрешения: A → B → C (лучший доступный «вкус» пакета)
        ↓ все дают одно и то же
контент-адресуемые объекты + корни-профили: bin/<arch>/<name>, профиль = дерево content-id
```

Поколения/откат/атомарность — свойства store (A/B-индекс, история корней), менеджер их
не реализует, а ИСПОЛЬЗУЕТ. Ровно то, что NixOS строит поверх симлинков и записей
загрузчика, — у нас слой хранения.

## Бэкенд A: native (главная дорога)

**Rust-шорткат** — самый короткий путь к юзабельному userland без портирования C:
- порт `std` для таргета `*-unknown-void`: реализовать платформенный слой (stdio → SYS_WRITE/
  SYS_READ, fs → персоналия по IPC, process → SYS_EXEC, alloc → SYS_MAP; потоки — заглушки,
  std это допускает, как на wasm-таргетах);
- сразу доступны: **uutils** (coreutils на Rust — настоящие ls/cp/grep одной кросс-сборкой),
  ripgrep, fd, вплоть до редактора helix — статические, без libc;
- прецедент: Redox — std-порт там начинал один человек;
- ✅ Веха 32: uutils работают (8 утилит multicall-бинарём; форк-сабмодуль
  `vendor/coreutils`, ветка void — cfg-заплатки «как WASI», [[uutils]]);
  ripgrep/fd/helix ждут потоков и pipes.

Уже есть со стороны ядра: SYS_MAP (куча, [[process-heap]]), SYS_EXEC ([[interactive-shell]]),
файловые op персоналии ([[posix-personality]]), время в U-mode (Веха 28), argv/env и
стартовые capability + seek/rename (Веха 30, [[process-contract]]). Из std-минимума
не хватает только pipes/dup — отложены до реальной потребности (uutils стартует без них).

**nixpkgs-cross** — расширение на C-мир: кросс-тулчейн на newlib поверх персоналии.
Nix здесь — книга рецептов и сборочный цех НА ХОСТЕ, не программа внутри VOID.
- ✅ Веха 36 ([[nixpkgs-cross]]): свой триплет не понадобился — pkgsCross
  bare-metal тулчейны из кэша + глю `void-libc` (~610 строк) + specs; GNU hello
  (autotools/gnulib) и bzip2 по рецептам nixpkgs работают на обеих архитектурах
  (`nix/default.nix`, функция `voidify` — любой рецепт → пакет VOID).

## Бэкенд B: linux-abi (исследовательская магистраль)

Персоналия с Linux-syscall ABI → неизменённые бинари из **бинарного кэша nixpkgs**.
Почему nix и только nix: замыкания самодостаточны, без FHS — /nix/store-пути отображаются
в наш store напрямую (path ↔ content-id). AUR/deb/rpm предполагают глобальный изменяемый
/usr — мимо. Объём: ~50–100 syscall'ов для CLI (openat/read/write/mmap/brk/execve/stat…);
сложное — futex и clone (потоки). Старт: статические musl, однопоточные. Прецеденты:
linuxulator, gVisor, **Managarm** (хобби-микроядро, добежавшее до Wayland и GCC).

## Бэкенд C: wasi (эксперимент)

`wasmi` компилируется в no_std → интерпретатор внутри VOID достижим малой кровью.
WASI capability-based (preopen-дескрипторы) — идеологически наша модель. Минусы: экосистема
мала, скорость интерпретатора. Держим как «пакет работает везде, где есть VOID, пусть
медленно» и как полигон для cap-интеграции.

## Мост host ↔ store

- ✅ **Веха 29** ([[store-bridge]]): `void-store-import` (хост-утилита) пишет объекты +
  корни в `void-disk.img` тем же кодом, что ядро (store вынесен в `libs/void-store` за
  трейт `BlockIo`). Семена include_bytes остались как fallback чистого диска — вытеснять
  их смысла нет, пока они по КиБ; мост нужен тому, что в семена не влезет (uutils).
- ✅ **NAR-импорт** (та же веха): `nix-store --dump <путь>` → `void-store-import nar` →
  корень на каждый файл (v1 плоский: деревья-объекты ждут иерархического posixfs;
  симлинки пропускаются честно). Поток «nix build → в VOID» — одна команда.
- Арх-измерение корней: `bin/riscv64/hello`, `bin/x86_64/hello` — контент-адресация сама
  разведёт артефакты, но именование корней должно знать архитектуру (следствие
  мультиархитектурности Фазы 4).

## Лестница самодостаточности («поставил на устройство и пользуюсь»)

1. **Веха 23**: userspace в ELF из store — пререквизит всего (снимает `.user` и его мины,
   разблокирует release).
2. **std-порт + uutils + мост — ✅ ДОСТИГНУТА** (Вехи 29–32): девайс грузится в vsh,
   есть настоящие утилиты, всё персистентно — первая честная точка «самодостаточно
   для энтузиаста». Мост — ✅ Веха 29; контракт запуска — ✅ Веха 30
   ([[process-contract]]); std-порт — ✅ Веха 31 ([[std-port]]); uutils —
   ✅ Веха 32 ([[uutils]]: std::fs через IPC + free-list аллокатор + os::fd +
   FP-контекст ядра; 8 утилит с одного диска на обеих архитектурах).
3. **nixpkgs-cross — ✅ ДОСТИГНУТА** (Веха 36, [[nixpkgs-cross]]): C-программы по
   рецептам nixpkgs (hello, bzip2) на обеих архитектурах.
4. **linux-abi**: бинарный кэш nixpkgs напрямую — «пользоваться базой nix» в реалистичной
   форме.
5. **Реальное железо**: VisionFive 2 / x86-минипк (после порта). Цена — драйверы
   (eMMC/NIC; USB — монстр, в последнюю очередь).

## Фишки NixOS поверх (когда база есть)

- Декларативный init: system-конфиг = объект-дерево (какие серверы, какие права, какие
  программы) — kmain-сценарий заменяется чтением конфига из store; generations = история
  корня; откат = set_root.
- Окружения (аналог nix-shell): объект «список программ + список прав для минта».
- «Flake» = дерево content-id (lock-файл вырождается в то, чем store является всегда);
  язык Nix не тащим — вычисляет настоящий nix на хосте через мост.
