# Веха 10.2b — IPC + userspace-сервер

Завершение Вехи 10.2: поверх [[processes|процессов]] добавлен **межпроцессный обмен** (IPC), и
на нём построен первый **userspace-сервер**. Это конституирующий приём микроядра: сервисы живут в
непривилегированных процессах, а не в ядре, и вызываются сообщениями. Прямой шаг к драйверам и
персоналии совместимости в userspace ([[0002-persistent-content-addressed-capability-core|ADR 0002]]).

## Модель IPC (синхронный rendezvous)
Три системных вызова (ABI: номер в `a7`, аргументы в `a0..`, результат в `a0`):
- **`RECV` (4)** → `(a0=сообщение, a1=отправитель)`. Нет запроса → процесс блокируется
  (`RecvWait`), ядро планирует другого.
- **`CALL` (5)** `(dest, msg)` → `a0=ответ`. Отправить запрос и ждать ответа (`ReplyWait`).
- **`REPLY` (6)** `(dest, val)` — ответить клиенту (разбудить его), продолжить работу.

Планирование завязано на блокировки (кооперативно, один hart): когда процесс блокируется, ядро
возобновляет следующего готового ([[processes|`resume`/`next_runnable`]]). Доставка сообщения
напрямую вписывает результат в кадр адресата и делает его `Runnable` (для заблокированного) либо
кладёт запрос в `mailbox` (если адресат ещё не в `RECV`). «Ответ» = запись `a0`+`sepc+=4` в кадр
клиента. Потерянных пробуждений нет: если получатель не ждал, запрос лежит в mailbox до `RECV`.

## Сервер и клиент (в U-mode)
- **Сервер** (P0): `loop { (msg, from) = RECV(); REPLY(from, msg*2) }` — «сервис» (удвоение)
  считается **целиком в userspace**, ядро лишь передаёт сообщения.
- **Клиент** (P1): трижды `CALL(server=0, n)` для n=21,42,63; печатает завершающее сообщение;
  `EXIT`. Ответы сервера логирует ядро (форматировать число в U-mode пока нечем).

Завершение сессии: клиент вышел, сервер навсегда в `RecvWait` → готовых нет → ядро возвращается
в `kmain` (заблокированный сервер просто оставлен — это ожидаемо для демо).

## Проверка (вывод в QEMU)
```
[proc] userspace-сервер + клиент через IPC (SEND/RECV/REPLY):
[ipc] P1 CALL P0 msg=21
[ipc] P0 REPLY P1 val=42      ← сервер удвоил в userspace
[ipc] P1 CALL P0 msg=42
[ipc] P0 REPLY P1 val=84
[ipc] P1 CALL P0 msg=63
[ipc] P0 REPLY P1 val=126
[client] all replies received, exiting
[proc] P1 SYS_EXIT(0)
[proc] сессия процессов завершена — обратно в ядро
```
Клиент и сервер изолированы (свои `satp`), общаются только сообщениями; ядро планирует их по
блокировкам. Стабильно через перезагрузки; персистентность store не задета.

## Осознанные упрощения (следующее)
- **Сообщение — один `usize`** (скаляр). Реальный IPC передаёт буферы/страницы; здесь скаляр
  демонстрирует механизм. Передача буфера появилась на [[block-driver|Вехе 11]] (`CALL`/`REPLY`).
- ~~**Адрес — id процесса**, а не capability.~~ **Закрыто на [[ipc-endpoints|Вехе 12]]**: `CALL`
  берёт cap на эндпоинт (право `SEND`), а не сырой pid — слать сообщение можно только тому, на кого
  есть capability.
- **Кооперативно, без вытеснения** (прерывания в U выключены); один сервер/клиент в демо.
- **Нет доступа процесса к объектному store** — сервер-хранилище (процесс поверх [[object-model]])
  ещё впереди.
