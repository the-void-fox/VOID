# Веха 15 — reply-capability

Закрывает последнюю дыру IPC ([[ipc-endpoints|Веха 12]] защитила `CALL`, но `REPLY` оставался
открытым): сервер отвечал по **сырому id клиента**, запомненному из `RECV`. Любой процесс мог бы
сделать `REPLY(жертва, …)` любому, кто ждёт в `ReplyWait`, и **подсунуть поддельный ответ**.

Теперь `RECV` выдаёт серверу **одноразовый reply-cap** на конкретного вызвавшего, а `REPLY`
требует его предъявить. Нельзя ответить тому, кто не звал; нельзя ответить дважды; нельзя
подделать. Это классический приём KeyKOS/EROS: право ответить — тоже [[capabilities|capability]].

## Механизм
1. **Цель `Target::Reply(caller)`** — reply-cap на клиента `caller` (право `SEND`).
2. **`RECV` выдаёт reply-cap.** При доставке запроса ядро минтит `Reply(caller)` в c-space
   сервера и кладёт его дескриптор в `a1` — туда, где раньше был сырой pid клиента. (И прямая
   доставка в `CALL`, и доставка из mailbox в `RECV`.)
3. **`REPLY(reply_cap, buf, len)`** резолвит cap → id клиента, копирует ответ, будит клиента и
   **отзывает** cap (`revoke` → поколение++ → одноразовость). Подделка/чужой/повторный cap →
   `resolve` отвергает.

Изящно, что **серверы не изменились**: `blk_server`/`store_server` и раньше просто форвардили
значение из `RECV` в `REPLY` — теперь это не pid, а reply-cap, но обращаются с ним как с
непрозрачным числом. Слоты c-space переиспользуются (mint при RECV ↔ revoke при REPLY), поэтому
за N циклов расходуется ~1 слот.

## Проверка (вывод в QEMU)
```
[ipc] P0 REPLY P1 (512 байт)            ← сервер отвечает по reply-cap (легитимно)
...
[ipc] P1 REPLY отклонён: WrongKind  ← нет reply-capability
[blk-cli] forged REPLY DENIED by kernel (not a reply-capability)
```
Все настоящие ответы серверов проходят; попытка клиента подделать `REPLY`, предъявив свой
эндпоинт-cap (не reply-cap), отвергается ядром (`WrongKind`). Store-сессия с 4 op (get_root/get/
put/set_root) целиком работает на reply-cap'ах, персистентность корня не задета.

## Осознанные упрощения (следующее)
- **Reply-cap живёт до REPLY**: если сервер молча не ответит (не наш случай — серверы всегда
  отвечают), cap останется в его c-space до перезапуска. Тайм-аут/отзыв «висящих» — позже.
- **C-space процессов в RAM** — reply-cap'ы, как и прочие, не персистентны (и не должны быть).
- Всё ещё **кооперативно** (следующая веха — вытеснение), один сервер/клиент на демо.
