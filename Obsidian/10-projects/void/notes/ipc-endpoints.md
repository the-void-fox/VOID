# Веха 12 — capability-защищённые IPC-эндпоинты

Соединение двух половин модели KeyKOS/EROS в userspace: [[capabilities|capability]] (Веха 8) +
[[processes|процессы]]/[[ipc|IPC]] (Веха 10). До этой вехи были **две дыры** (записаны как
осознанные упрощения в [[ipc]] и [[block-driver]]):
- `SYS_CALL` брал **сырой id процесса** — любой процесс мог слать сообщение любому;
- `SYS_BLK_READ` был **открыт всем** — любой процесс мог читать любой сектор диска.

Теперь и IPC-вызов, и доступ к устройству идут **только по capability**: держать нужный
дескриптор с нужным правом — единственный способ. Это прямо стержень
[[0002-persistent-content-addressed-capability-core|ADR 0002]]: право = обладание ссылкой.

## Что добавлено
1. **У процесса есть домен защиты.** `proc::spawn(name, entry, arg)` заводит процессу личный
   c-space ([[capabilities]]) и возвращает его `pid` (он же — адрес его эндпоинта). Начальные
   права ядро **минтит** в этот домен и передаёт процессу непрозрачный дескриптор через `a0`
   (`proc::set_arg`) — внутри U-mode c-space недоступен, `Cap` живёт как число в регистре.
2. **Новые цели capability** (`cap::Target`):
   - `Endpoint(pid)` — право **отправить сообщение** процессу-серверу (право `SEND`);
   - `Device(Device::Block)` — право обратиться к **устройству** (право `READ`).
3. **Новое право `SEND`** (`void-abi::Rights`, бит 3) — «можно вызвать эндпоинт». Строка прав
   стала `rwgs` (read · write · grant · send).
4. **Резолверы в ядре** (`cap.rs`): `endpoint(dom, cap) -> pid` (нужен `SEND`) и
   `device(dom, cap, need) -> Device` (нужно `need`). Оба идут через тот же `resolve()`, что и
   доступ к значениям, — подделка/чужая цель/нет права → отказ.
5. **Syscall'ы берут дескриптор, а не сырой аргумент:**
   - `CALL(ep_cap, msg, recv_buf, recv_cap)`: ядро резолвит `ep_cap` → id сервера; нет права →
     `a0=MAX`, процесс **не** блокируется.
   - `BLK_READ(dev_cap, sector, buf)`: без валидного device-cap (право `READ`) — отказ, даже
     если процесс знает номер сектора.

## Демонстрация (вывод в QEMU)
```
[proc] userspace-драйвер + IPC под защитой capability:
  P0 'blk-drv' ← cap на устройство [r---]
  P1 'blk-cli' ← cap на эндпоинт P0 [---s]
[ipc] P1 CALL P0 (по cap) msg=0
[blk] P0 SYS_BLK_READ сектор 0 (по cap)
[ipc] P0 REPLY P1 (512 байт)
[blk-cli] sector 0 via driver-server: VOIDFS
[blk] P1 SYS_BLK_READ отклонён: Denied  ← нет capability на устройство
[blk-cli] direct disk read DENIED by kernel (no device capability)
[proc] P1 SYS_EXIT(0)
```
Клиент читает диск **только** через сервер (предъявив cap на эндпоинт), а его же попытка прочитать
диск **напрямую** (тем же дескриптором — он не device-cap и без права `READ`) ядром **отвергается**.
Дыра закрыта: доступ к железу и к серверу — исключительно по правильному capability.

## Осознанные упрощения (следующее)
- **`REPLY` целится в pid клиента**, запомненный из `RECV`, а не в *reply-capability*. Настоящая
  модель выдаёт одноразовый cap на ответ (нельзя ответить тому, кто не звал) — отдельный шаг.
- **Минтит и раздаёт caps ядро** при spawn (bootstrap). Передача прав **между процессами через
  IPC** (`grant` по сообщению) — следующий рубеж; тогда домены заживут по-настоящему.
- **C-space процесса в RAM**, как и на [[capabilities|Вехе 8]] — не персистентен.
- **Кооперативно, один сервер/клиент**; сообщение — скаляр + буфер 512 Б.
