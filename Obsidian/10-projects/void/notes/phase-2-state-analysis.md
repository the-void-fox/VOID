# Анализ состояния ядра после Фазы 2

Снимок на момент закрытия Вехи 18 (~4800 строк ядра, 21 модуль + `void-abi`).
Вывод: **цельное работающее микроядро, у которого все три ингредиента
[[0002-persistent-content-addressed-capability-core|ADR 0002]] собраны и живут в QEMU** —
но между «все вехи закрыты» и «нормальная работоспособность» лежит структурный разрыв:
система пока представляет собой скриптованную демо-последовательность в `kmain`, а не живую ОС.

## Что ядро умеет

- **Фаза 0:** boot (OpenSBI → S-mode), trap'ы, Sv39 + W^X, куча ядра, многозадачность
  с вытеснением, PLIC. См. [[traps-and-timer]], [[sv39-paging]], [[kernel-heap]], [[scheduling]].
- **Фаза 1 (стержень):** контент-адресуемый store (BLAKE3, дедуп, граф ссылок, GC,
  append-only диск + A/B-индекс, уплотнение при commit); capability (домены, c-space,
  slot+generation, аттенуация, отзыв); async-executor с пробуждением из IRQ.
  См. [[object-model]], [[persistent-store]], [[capabilities]], [[async-executor]].
- **Фаза 2:** U-mode процессы со своим `satp`, syscall-граница, rendezvous-IPC
  (CALL/RECV/REPLY) с передачей буферов и reply-cap, вытеснение процессов, userspace-серверы
  (блок-драйвер, store, POSIX-персоналия) и `mini-sh` на чистом POSIX-shim.
  См. [[processes]], [[ipc-endpoints]], [[reply-capability]], [[posix-personality]].

Доказаны сквозные свойства: *персистентность через userspace-сервер под capability*
и *прозрачность личности* (программа не знает про VOID).

## Разрывы до нормальной работоспособности

По убыванию важности:

1. **Загрузка программ.** Все процессы — функции из `user.rs`, статически вшитые в секцию
   `.user` образа ядра. Нет ELF-загрузчика, нет exec — программу нельзя добавить, не пересобрав
   ядро. Главный барьер между «демо» и «системой».
2. **Нет init и интерактивности.** `kmain` прогоняет фиксированный сценарий и уходит в `wfi`.
   UART работает только на вывод; `mini-sh` играет захардкоженный сценарий.
3. **c-space не персистентен** — дыра в собственном тезисе: ADR 0002 говорит «capability
   требуют персистентности», а сейчас они живут в RAM и минтятся ядром заново при spawn.
4. **Нет передачи capability по IPC.** Cap попадает в процесс единственным способом — ядро
   кладёт его в `a0` при spawn. Делегирование прав в рантайме (grant-в-сообщении) — сердце
   любой cap-системы (seL4/L4) — отсутствует.
5. **Память процессов.** Стек 4 страницы, нет кучи у процессов (отсюда лимиты персоналии:
   4 файла, имя 16, данные 256 байт), нет demand paging, user page fault фатален.
6. **Мелкое:** один hart, DTB не парсится (адреса под QEMU `virt` захардкожены), один общий
   trap-стек, нет тестов/CI, IPC только синхронный (нет notification).

## Фаза 3 — «самостоятельность» (решение: [[0003-phase-3-exec-by-hash]])

- **Веха 19 — программа как объект store:** ELF кладётся в store, исполняется по ContentId.
  Программа = неизменяемое контент-адресуемое значение (как derivation в Nix): дедуп и
  воспроизводимость запуска бесплатно. Такого примитива нет ни у Linux, ни у seL4.
- **Веха 20 — UART-ввод + интерактивный shell:** IRQ UART → async-канал → настоящий `mini-sh`
  (`ls`/`cat`/`echo`/`run <hash>`).
- **Веха 21 — cap-transfer по IPC + персистентный c-space.** Закрывает разрывы 3–4,
  завершает тезис ADR 0002.
- **Веха 22 — куча процесса + фолты:** `SYS_MAP`, ленивые страницы, убийство процесса
  при фолте вместо паники ядра.
- Дальше: virtio-net + сетевой стек как сервер; checkpoint процессов (ортогональная
  персистентность *вычислений* — настоящее наследие KeyKOS: «система, которую нельзя выключить»).

## SASOS

VOID уже наполовину SASOS идеологически: single-level persistent store + capability вместо
файлов и UID — это линия **Opal и Mungi** (ближайший исторический родственник: SASOS 90-х
строились ровно на persistence + capabilities). Store даёт единое пространство *данных*;
SASOS добавил бы единое пространство *адресов*.

Практичный путь, не ломающий [[0001-rust-riscv-microkernel|ADR 0001]] (железная изоляция —
фундамент, SASOS — эксперимент): **гибрид** — оставить S/U-границу, но дать доверенным серверам
жить в одном адресном пространстве с изоляцией средствами Rust (модель Theseus/Hubris).
IPC между такими серверами вырождается в вызов функции — исчезает исторический налог микроядра.
Контент-адресация помогает: если код сервера — неизменяемый объект по хэшу, то «что именно
исполняется в моём пространстве» — проверяемый факт. Полный SASOS остаётся поздней
исследовательской веткой (один баг в `unsafe` рушит гарантию).

## Порт на x86-64

Возможен; стержень (object/cap/executor/chan, логика IPC и планирования, персоналия,
`void-abi`) архитектурно-независим. Архитектурно-специфичное и его цена:

| RISC-V сейчас | x86-64 эквивалент | Сложность |
|---|---|---|
| OpenSBI + `entry.s` | Limine/Multiboot2 boot | средняя (Limine сразу даёт long mode) |
| `csr.rs`, `trap_entry.s` | GDT/IDT/TSS | средняя |
| Sv39 `paging.rs` | 4-уровневый пейджинг | низкая — структура почти идентична |
| `ecall`-граница | `syscall`/`sysret` | низкая |
| PLIC + SBI-таймер | LAPIC/IOAPIC + LAPIC-таймер | средняя |
| virtio-mmio | virtio-pci (перебор PCI) | средняя, самое муторное |
| NS16550 MMIO | тот же 16550, port I/O | тривиальная |

Объём ≈ «переиграть Вехи 1–5 и 10». Рекомендация: не портировать сейчас, но **фоном вынести
архзависимое в `kernel/src/arch/riscv64/`** за узкий интерфейс (trap frame, переключение AS,
таймер, IRQ) — дёшево, пока архитектура одна, почти невозможно потом. aarch64 — промежуточный
вариант, если цель «доказать переносимость».

## Приоритет

Фаза 3 даёт максимум «системности» на вложенное усилие; arch-рефакторинг — фоном;
x86 — после самостоятельности, иначе будем портировать демо.
