# Веха 7.1 — драйвер блочного устройства (virtio-blk)

«Руки» для персистентности: умеем читать и писать 512-байтные секторы виртуального диска.
Поверх этого на [[object-model|Вехе 7.2]] ляжет долговечный store (принцип — в
[[persistence-and-volatility]]).

## Что такое virtio
Стандарт **паравиртуализованных** устройств: гость (наше ядро) знает, что он в виртуалке, и
общается с устройством не через эмуляцию реального железа, а через простой согласованный
интерфейс. Быстро и просто в реализации. Транспорты бывают разные; на QEMU `virt` — **virtio-mmio**
(устройство выглядит как набор регистров в памяти).

## Как находим устройство
QEMU `virt` даёт 8 слотов virtio-mmio по адресам `0x1000_1000 .. 0x1000_8000`. Сканируем их:
у настоящего слота по смещению 0 лежит магия `"virt"` (`0x74726976`); нам нужен слот с
`Version == 2` (modern) и `DeviceID == 2` (block).

> **Грабли, на которые наступили:** после включения Sv39 ([[sv39-paging]]) мы отображали только
> одну страницу UART. Регистры virtio лежат по `0x1000_1000+` и были **не отображены** → первое
> же чтение из `probe()` дало page fault. Починка: отобразить в paging весь MMIO-регион
> `0x1000_0000 .. 0x1000_9000` (UART + слоты virtio) как RW.

## Split virtqueue — три кольца в общей памяти
Обмен идёт через **очередь** из трёх структур в RAM, к которым устройство обращается по
физическому адресу (у нас RAM отображена идентично, поэтому адрес = физический):
- **desc** (таблица дескрипторов) — куски буферов: `[адрес, длина, флаги, next]`. Дескрипторы
  можно сцеплять флагом `NEXT`.
- **avail** (кольцо доступных) — сюда **мы** кладём индексы голов готовых цепочек и двигаем `idx`.
- **used** (кольцо использованных) — сюда **устройство** кладёт завершённые запросы и двигает `idx`.

## Один запрос к диску = цепочка из 3 дескрипторов
1. **Заголовок** (16 Б): тип (`IN`=чтение/`OUT`=запись) + номер сектора. Устройство читает.
2. **Данные** (512 Б): при чтении устройство ПИШЕТ сюда (флаг `WRITE`), при записи — читает.
3. **Статус** (1 Б): устройство пишет результат (0 = OK).

Отправка: кладём голову цепочки (дескриптор 0) в `avail.ring`, двигаем `avail.idx`, пишем в
регистр `QueueNotify` (будим устройство), затем **опрашиваем** `used.idx`, пока не изменится.
Опрос (polling), а не прерывания — так проще для первого драйвера; прерывания добавим позже.

Между шагами нужны барьеры памяти (`fence`), чтобы записи descriptors/avail стали видны
устройству до notify, а данные — нам после того, как увидели used.

## Инициализация (modern virtio 1.0)
1. Сброс: `Status = 0`.
2. Рукопожатие статуса: `ACKNOWLEDGE` → `DRIVER`.
3. Согласование фич: принимаем только `VIRTIO_F_VERSION_1` (обязателен для modern), пишем в
   `DriverFeatures`, ставим `FEATURES_OK` и проверяем, что устройство его не сбросило.
4. Очередь 0: выбрать (`QueueSel=0`), задать размер (`QueueNum`), выделить фреймы под desc/avail/used
   и записать их адреса, `QueueReady=1`.
5. `DRIVER_OK` — устройство готово. Читаем ёмкость из конфиг-пространства.

QEMU запускаем с `-global virtio-mmio.force-legacy=false` (иначе по умолчанию legacy version 1,
а наш драйвер — modern version 2) и с диском:
`-drive file=void-disk.img,if=none,format=raw,id=hd0 -device virtio-blk-device,drive=hd0`.

## Проверка (вывод в QEMU)
```
[blk]  диск найден: 32768 секторов (16 МиБ)
[blk]  сектор 200 до записи: "............"          (первый запуск — нули)
[blk]  запись+чтение сектора 200: совпало ✓
```
На **втором** запуске:
```
[blk]  сектор 200 до записи: "VOID-BLK-7.1"  ← это ПРОШЛЫЙ запуск: диск персистентен!
```
Данные пережили выключение QEMU — фундамент персистентности уже работает.

## Осознанные упрощения (чиним позже)
- **Опрос вместо прерываний** — CPU крутится в ожидании диска. Позже: прерывание + пробуждение задачи.
- Один запрос за раз (очередь по сути на одну операцию).
- Нет обработки ошибок диска сверх проверки байта статуса.
- Драйвер под замком: параллельные обращения сериализуются.

## Что дальше (Веха 7.2)
Поверх этих read/write секторов — **контент-адресуемый store на диске**: раскладка (суперблок +
область объектов), запись объекта по его хэшу, атомарное обновление корня системы, на загрузке —
чтение корня и ленивая подгрузка объектов. Тогда [[object-model|объектная модель]] станет
долговечной по-настоящему.
