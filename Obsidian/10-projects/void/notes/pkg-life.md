# Веха 109 — пакетная жизнь

Последняя веха Фазы 8. Всё, что было собрано по частям — загрузка ([[pkg-fetch]]), замыкание и
профиль ([[pkg-closure]]), дерево в сторе ([[pkg-tree]]), файловый вид ([[store-mount]]), запуск
([[lx-dynamic]]), — сходится в обиход: **установил, запустил по имени, перезагрузился, удалил,
освободил место**.

```
vvsh/> pkg install bsh7n2nx8ndmm1mmww6v2h4851nalj13
  ↓ bsh7n2nx8ndmm1mmww6v2h4851nalj13-glibc-2.42-61-bin  2890576 Б  (сеть 49 с, распаковка 36 с)
замыкание: 7 путей, 74546584 Б (скачано сейчас: 1)
профиль default: поколение gen3

vvsh/> getconf LONG_BIT
64
vvsh/> getconf GNU_LIBC_VERSION
glibc 2.42
```

`getconf` — настоящая программа из nixpkgs. Её не запускали по пути: **голое имя нашлось в
профиле**. Замыкание при этом почти всё уже лежало в сторе — скачался один путь из семи.

## PATH — это профиль

Голое слово в шелле ищется сперва среди программ САМОЙ системы (корень store `bin/<имя>`), потом
в профиле: `<пакет>/bin/<имя>` у каждого пакета **верхнего уровня**. Порядок намеренный — пакет
из nixpkgs не должен молча заслонять `vvsh` или `pkg`. Зависимости в PATH не попадают: человек их
не устанавливал, и у nix ровно та же граница.

Кандидаты перебираются **все по очереди**, а не берётся первый. Причина обнаружилась сама: в
одном сторе спокойно живут пакеты разных архитектур (у нас там x86- и riscv-glibc), `bin/getconf`
есть у обоих, и запуститься должен свой. Так и вышло — чужой не загрузился, следующий заработал.

Запуск по абсолютному пути добавлен в `SYS_EXEC`: имя, начинающееся с `/`, читается из дерева
пакета ([[lx-files]]), всё прочее — по-прежнему корень store.

## Сборка мусора: поколения неприкосновенны

`pkg gc` снимает корни путей, которых нет **ни в одном** поколении профиля, и просит store
собрать мусор (для этого понадобился `SYS_OBJ_GC`: снятый корень сам по себе места не возвращает,
пока никто не прошёл по графу достижимости — раньше это случалось только на загрузке).

Удалённый пакет при этом **не исчезает**, и это не оплошность:

```
vvsh/> pkg remove glibc-2.42-61-bin
профиль default: поколение gen5 (7 путей)
vvsh/> pkg gc
снято путей: 0, собрано объектов: 3 (в поколениях осталось 8)
```

Ноль — потому что старые поколения на него ссылаются, а пока они живы, **работает откат**. Это и
есть главное свойство профиля, и молча ломать его ради освобождения места нельзя. Освободить —
отдельная и явная просьба:

```
vvsh/> pkg gc all
  поколение gen1 снято
  …
  снят bsh7n2nx8ndmm1mmww6v2h4851nalj13
снято путей: 1, собрано объектов: 208 (в поколениях осталось 7)
```

После этого `ls /nix/store` показывает семь путей вместо восьми, а `getconf` продолжает работать —
своей архитектуры пакет остался.

## Полный круг проверен

На **обеих архитектурах**, каждая своим пакетом (`glibc-…-bin` под x86 и под riscv):

1. `pkg install` — скачано только недостающее, остальное найдено в сторе;
2. `getconf LONG_BIT` → `64` — голым именем, через PATH профиля, динамически слинкованный;
3. **перезагрузка** — и `getconf` работает снова: ни загрузки, ни распаковки не потребовалось;
4. `pkg remove` → новое поколение; `pkg gc` бережёт (откат жив); `pkg gc all` освобождает.

  вычисления nixpkgs на устройстве (Фаза 9), либо индекса «имя → путь», посеянного мостом.
- **Профиль один** (`default`), профилей на пользователя нет — как и пользователей ([[capabilities]]).
- **`pkg gc all` не спрашивает подтверждения** — команда явная, но необратимая.
- **Уплотнение store после сборки** делается лишь при пороге мусора и требует всё живое в
  памяти ([[known-gaps]]) — на сторе крупнее кучи ядра это упрётся.
