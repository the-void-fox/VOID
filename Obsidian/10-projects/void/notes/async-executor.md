# Веха 9 — async-executor

Третий ингредиент стержня из [[0002-persistent-content-addressed-capability-core|ADR 0002]]:
«Rust + async чинит конкурентность на современном железе **без ретро-заплаток типа io_uring**».
После [[object-model|объектов]], [[persistent-store|персистентности]] и [[capabilities|прав]] —
это про то, как *исполнять* конкурентную работу (в первую очередь I/O) над этим пространством.

## Нити против future
До этого конкурентность давали **нити** ([[scheduling|`sched`]]): у каждой свой стек, вытеснение
по таймеру. Async — другой механизм, **дополняющий**, не заменяющий:

| | Нить (`sched`, Веха 5) | Async-задача (Веха 9) |
|---|---|---|
| Состояние | свой стек (32 КиБ) | стейт-машина от компилятора, без стека |
| Переключение | вытеснение по таймеру (в любой момент) | кооперативно, в точках `.await` |
| Цена задачи | стек + контекст | размер future (байты) |
| Хорошо для | CPU-bound работы | тысяч конкурентных I/O-ожиданий |

Правило: нить вытесняет процессор у счётной работы; executor даёт дёшево ждать событий. Обе
модели живут в одном ядре.

## Как устроен executor
`async fn` компилятор превращает в **future** — объект с методом `poll(cx) -> Poll`. Executor
(`kernel/src/executor.rs`):
- **очередь готовых** (`ready: VecDeque<TaskId>`) + **карта задач** (`tasks: BTreeMap`);
- `spawn(future)` — кладёт future в карту и id в очередь;
- `run()` — берёт id, **изымает** задачу из карты, `poll`'ит её ВНЕ замка executor'а, и если
  `Pending` — возвращает в карту; если `Ready` — дропает. Опрос вне замка обязателен: `poll`
  может вызвать `wake` (себя или другого) → тому нужен тот же замок → иначе взаимоблокировка.

### Waker — как задача просыпается
`poll` получает `Context` с [`Waker`]. Future, который не может продвинуться, **сохраняет** waker
и возвращает `Pending`. Кто-то потом вызывает `waker.wake()` → id задачи снова в очереди готовых.
Наш `TaskWaker` — это `Arc<{ id }>` (через `alloc::task::Wake`); `wake` просто делает
`ready.push_back(id)`. Два источника пробуждения в демо:
- **self-wake**: `yield_now().await` будит себя тут же (кооперативная уступка) → другие готовые
  задачи получают ход.
- **пробуждение по событию**: `chan::recv().await` на пустом канале паркуется (сохраняет waker);
  `send` из другой задачи забирает waker и будит. Вот ради чего waker и нужен.

## Async-канал (`chan.rs`)
Минимальный MPSC (много отправителей, один потребитель): `Arc<SpinLock<{ queue, recv_waker }>>`.
`send` — `push` + разбудить припаркованного потребителя (waker будим уже ПОСЛЕ отпускания замка
канала, чтобы не держать два замка). `recv().await` — `pop`, иначе сохранить waker и `Pending`.
Инвариант «нет потерянных пробуждений»: значение кладётся до взятия waker, поэтому потребитель
либо увидит его при следующем `poll`, либо будет разбужен.

## Проверка (вывод в QEMU)
```
[async] executor — future-задачи поверх объектного store:
  [A] put "async-A-0"          ← A: put в store, send адрес, yield
  [B] put "async-B-0"          ← B то же (A уступил)
  [C] принял … = "async-A-0"   ← C проснулся по send, забрал оба
  [C] принял … = "async-B-0"
  [A] put "async-A-1"          … цикл повторяется кооперативно …
  [C] всё принято — завершаюсь
```
Узор A,B→C,C→A,B→C,C — это и есть кооперативная многозадачность: производители уступают через
`yield`, потребитель паркуется/просыпается через канал. Всё на **одном** стеке (не нить на задачу).
Значения оседают в объектном store и уходят на диск ближайшим [[persistent-store|commit]] —
async-задачи полноправно пишут в персистентное пространство.

## Пробуждение future из прерывания (доводка после Вехи 9)
Реализован настоящий async I/O: `virtio_blk::read_async` паркует future, а обработчик прерывания
диска (`on_irq` через [[virtio-blk|PLIC]]) будит его. Для этого:
- **Очередь готовых стала irq-safe**: доступ к executor'у обёрнут в `with_exec` (снимает
  прерывания на время удержания замка). Иначе IRQ посреди удержания → `wake` из `on_irq` на том
  же замке → дедлок. (Ср. `with_sched` в [[scheduling]].)
- **Idle = `wfi`**: когда готовых задач нет, но незавершённые есть (ждут события), `run` спит на
  `wfi` до прерывания — а не крутится и не выходит преждевременно.

Проверка: async-задача читает сектор 0 и печатает «разбужен IRQ диска», пока другие задачи шли
своим чередом; счётчик прерываний устройства растёт.

## Осознанные упрощения (чиним позже)
- **Executor кооперативный** — CPU-bound future без `.await` заблокирует остальных. Это природа
  stackless-async; вытеснение — по-прежнему дело нитей.
- ~~Пробуждение только из обычного контекста~~ — **сделано**: future будится из IRQ (см. выше).
- **Один потребитель на канал; нет backpressure** (очередь неограниченна).
- **Executor крутится на нити `main`.** Естественная эволюция — executor как служба, а
  async-задачи — единица работы для userspace-серверов (Фаза 2).

## Что это закрывает
**Фаза 1 (стержень VOID) завершена целиком**: персистентные + контент-адресуемые +
capability-защищённые объекты, и async-модель исполнения над ними. Все три ингредиента ADR 0002
