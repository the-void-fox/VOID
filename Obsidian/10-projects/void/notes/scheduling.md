# Веха 5 — как устроена многозадачность

Как в VOID появилось несколько параллельных нитей исполнения. Связано с [[memory-regions]]
(у каждой задачи свой стек) и [[traps-and-timer]] (регистры, сохранение состояния).

## Задача, контекст, переключение
- **Задача (task)** — независимая нить исполнения в ядре: свой стек + своё сохранённое
  состояние регистров (**контекст**).
- **Контекст** — минимум регистров, чтобы приостановить задачу и позже продолжить её ровно с
  того же места.
- **Переключение (context switch)** — сохранить регистры текущей задачи и загрузить регистры
  другой. После него процессор буквально «продолжает» другую задачу.

## Почему сохраняем только часть регистров
RISC-V ABI делит регистры на:
- **callee-saved** (`ra`, `sp`, `s0..s11`) — функция обязана вернуть их нетронутыми;
- **caller-saved** (`a0..a7`, `t0..t6`) — их сохраняет вызывающий, если они ему нужны.

Мы всегда переключаемся в точке вызова `context_switch` (обычная функция). Значит вокруг этого
вызова компилятор **уже сохранил** нужные caller-saved регистры сам. Поэтому в контексте держим
только 14 callee-saved значений (`switch.s`). Это тот же приём, что `swtch` в xv6.

> Контраст: на trap'е ([[traps-and-timer]]) момент прерывания произвольный, поэтому там
> приходится сохранять **все** регистры (полный TrapFrame). Здесь — только callee-saved.

## Модули
- **switch.s** — `context_switch(old, new)`: сохранить регистры в `*old`, загрузить `*new`,
  `ret`. Плюс `task_trampoline` — точка первого запуска задачи.
- **context.rs** — структура `Context` (раскладка совпадает с switch.s) и объявления.
- **sched.rs** — планировщик: список задач, round-robin, `spawn`/`yield_now`.

## Как запускается новая задача (трюк с трамплином)
У новой задачи ещё нет «места, куда вернуться». Мы подделываем контекст так, чтобы первый же
`context_switch` на неё «вернулся» в `task_trampoline`, а адрес её функции кладём в `s0`:
```
context.ra   = task_trampoline   // куда «вернётся» ret в switch.s
context.sp   = вершина её стека
context.s[0] = адрес функции задачи
```
`task_trampoline` вызывает функцию (`jalr s0`), а если та вернётся — уходит в `task_exit`,
который помечает задачу завершённой.

## Round-robin и главный инвариант
`yield_now`:
1. под замком выбирает следующую незавершённую задачу (по кругу);
2. берёт **сырые указатели** на оба контекста (задачи в `Box`, адреса стабильны);
3. **отпускает замок** и только потом делает `context_switch`.

Шаг 3 — критичный: если уйти в переключение, держа замок планировщика, следующая задача не
сможет его взять в своём `yield_now` → взаимоблокировка. Поэтому замок отпускаем ровно перед
переключением, а сырые указатели остаются валидными, потому что `Box`'ы не двигаются.

## Бутстрап: kmain — это задача №0
Чтобы у первого переключения было куда сохранять текущее состояние, `sched::init()` заводит
задачу «main» с пустым контекстом — это само исполнение `kmain`. Её контекст заполнится
автоматически при первом переключении с неё. `main` работает на загрузочном стеке (из
linker.ld), остальным задачам стек выделяется из кучи.

## Кооперативное vs вытесняющее
Сейчас планирование **кооперативное**: задача сама вызывает `yield_now`. Если задача зациклится
без `yield`, остальные не получат процессор.

**Вытеснение (preemption)** — переключать по таймерному прерыванию, не спрашивая задачу.
Это следующий шаг, и он тоньше: переключение будет происходить из обработчика trap'а, где
прерывания выключены (SIE=0), поэтому нужно аккуратно восстанавливать состояние прерываний
для каждой задачи (иначе разбуженная кооперативная задача продолжит с выключенными прерываниями).
Таймер у нас уже тикает — механизм для вытеснения готов, дело за корректной передачей состояния.

## Проверка (вывод в QEMU)
```
[sched] запущены задачи A/B/C, уступаем управление:
  [A] шаг 0
  [B] шаг 0
  [C] шаг 0
  [A] шаг 1
  ...
  [C] завершилась
[sched] все задачи завершились — управление вернулось в main
```
Порядок A→B→C→A→B→C — это и есть round-robin.
