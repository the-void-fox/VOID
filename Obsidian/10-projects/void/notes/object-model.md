# Веха 6 — объектная модель

Здесь начинается сам тезис проекта из [[0002-persistent-content-addressed-capability-core]].
Всё, что было до этого (Вехи 1–5.5) — фундамент; теперь строим на нём то, ради чего проект.
Пока модель живёт **в RAM** (куча [[kernel-heap]]); долговечной её сделает Веха 7 — принцип
описан в [[persistence-and-volatility]].

## Два кирпича
1. **Неизменяемое значение**, адресуемое по **хэшу содержимого** (`ContentId`). Кладём байты —
   получаем их контент-адрес. Одинаковые байты → один адрес → одна копия (дедупликация).
2. **Изменяемый корень (ячейка)** — именованный указатель на значение. Мутация = переключить
   корень на *новое* неизменяемое значение; старое остаётся в хранилище.

Аналогия с git: значения — это объекты в `.git/objects` (по хэшу, неизменяемы), корни — это
ветки/refs (двигаются). Мы делаем это моделью всей ОС, а не только системы контроля версий.

## Почему именно так (а не «изменяемые объекты»)
Контент-адресация + неизменяемость дают три вещи бесплатно, и все три нужны стержню:
- **Дедупликация** — одинаковые данные хранятся один раз.
- **Дешёвое сравнение и разделение** — равенство = равенство хэшей; общий подграф не копируется.
- **Безопасная персистентность** (Веха 7) — неизменяемый объект пишется на диск один раз и не
  портится; рискует только атомарное переключение корня. Именно это чинит провал старых
  персистентных ОС (см. [[persistence-and-volatility]] и ADR 0002).

История версий получается сама собой: старые значения никто не затирает, они доступны по своим
адресам, пока на них кто-то ссылается (сборку мусора добавим позже).

## Модули
- **void-abi::ContentId** — тип адреса + `ContentId::hash(bytes)`. Хэш пока **заглушка** (четыре
  FNV-1a с разными базисами = 256 бит): детерминизм есть, но криптостойкости нет. Когда адрес
  станет границей доверия (проверка целостности, дедуп недоверенных данных) — заменим на BLAKE3.
- **object.rs** — хранилище в RAM:
  - `put(bytes) -> ContentId` — положить значение (идемпотентно, дедуп);
  - `with(id, f)` — прочитать значение по адресу (через замыкание, т.к. байты живут в хранилище);
  - `set_root(name, id)` / `root(name)` — изменяемые именованные корни;
  - `len()` — сколько уникальных значений.
  Всё под `SpinLock` — хранилище общее для всех задач.

## Проверка (вывод в QEMU)
```
[obj] put "hello"       -> 0bbdaa8046…
[obj] put "hello" снова -> 0bbdaa8046… (тот же адрес: true)   ← контент-адресация
[obj] put "world"       -> f38a0c735e…
[obj] уникальных объектов: 2 (не 3 — "hello" дедуплицирован)   ← дедупликация
[obj] корень 'system' -> 609ae41bf0… (после двух записей)
[obj] старая версия v0 всё ещё в store: "state=0"              ← история версий
```
Плюс две задачи X/Y пишут в **общее** хранилище — показывает, что store это разделяемое
состояние, а не привязан к задаче. (Итог: 10 уникальных объектов.)

## Осознанные упрощения (чиним позже)
- Хэш не криптографический (заглушка) — заменить на BLAKE3.
- Нет сборки мусора — старые версии копятся вечно.
- Значения — плоские байты; структурные ссылки между объектами (объект содержит `ContentId`
  другого) появятся, когда будем строить графы (например, деревья/списки).

## Что дальше (Веха 7)
Сделать хранилище **долговечным**: контент-адресуемый store на диске (virtio-blk в QEMU), RAM
как кэш, атомарное обновление корня системы. После этого «ОС не забывает» станет фактом, а не
планом. Принцип — в [[persistence-and-volatility]].
