# Веха 108.3 — файловый мост персоналии Linux

Третий шаг Вехи 108. Пакет распакован ([[pkg-tree]]) и виден файловым API VOID ([[store-mount]]),
но **чужому бинарю** он всё ещё не был виден: `openat` персоналии Linux отвечал `ENOENT` с самой
Вехи 38. Теперь неизменённая программа из nixpkgs открывает, читает и перечисляет содержимое
настоящего пакета.

Демонстратор — обычная Linux-программа (`lsx`, static-PIE musl, собрана кросс-gcc из nixpkgs; о
VOID она не знает ничего):

```
vvsh/> run bin/lsx ls /nix/store/57iz…-glibc-2.42-61
etc/
lib/
lib64@
libexec/
share/
-- 5 entries in /nix/store/57iz…-glibc-2.42-61

vvsh/> run bin/lsx sum /nix/store/57iz…-glibc-2.42-61/lib/libc.so.6
… size=2413096 read=2413096 fnv=7a3d9201fb4456ee
```

`fnv` — хэш прочитанного; на хосте тот же файл даёт **ровно те же** `size` и `fnv`. То есть
2.4 МБ двоичного файла (148 кусков блоба) доехали до чужой программы байт в байт. Проверено на
**обеих архитектурах**, обе дали одинаковые числа.

## Почему чтение идёт прямо из store, а не через файловый сервер

Файлы в VOID показывает `posixfs` — userspace-сервер, и это правильно. Но персоналия Linux
([[linux-abi]]) живёт **в ядре** (тонкий транслятор syscall'ов, путь FreeBSD linuxulator /
gVisor), и `openat` чужого бинаря обязан ответить **внутри syscall'а**. Сходить оттуда по IPC
нечем: IPC у нас — механизм для процессов, у ядра нет ни своего домена, ни состояния «жду
ответа»; заводить их ради `open` значило бы построить полсистемы асинхронных syscall'ов.

Зато у ядра есть store — он его собственный. А **и дерево пакета, и иерархия posixfs суть просто
корни store** (`pkg/tree/<хэш>` и `f<путь>`). Поэтому `kernel/src/lxfs.rs` — не вторая файловая
система, а тот же граф объектов, прочитанный с другой стороны; формат берётся из общего крейта
`void-tree`, которым пакет пишет `pkg` и показывает `posixfs`. Туда же переехала раскладка
**блоба** (манифест + куски): её читателей стало четверо — загрузчик, `pkg`, `posixfs` и ядро.

**Только чтение.** Запись потребовала бы согласия с кэшем открытых файлов `posixfs`, а пакет и
вовсе неизменяем: `open` на запись отвечает `EROFS` — честно, а не «нет такого файла».

## Что заработало

`openat`/`open`, `read`, `close`, `lseek`, `fstat`, `newfstatat`/`stat`/`lstat`, `faccessat`/
`access`, `readlinkat`/`readlink`, `getdents64`. Дескрипторы с 3 (0/1/2 — консоль), таблица —
своя у процесса. Крупный файл читается кусками: `read` отдаёт не больше остатка текущего куска
блоба — короткое чтение законно, и musl дочитывает сам.

`stat` отдаёт настоящий тип (файл/каталог/ссылка) и **исполняемый бит** — тот, что стоял в NAR.
Времена нулевые намеренно: у пакета их нет, и врать про `mtime` хуже, чем показать эпоху.

## Что вскрыла проверка на x86

На riscv всё заработало сразу, а на x86 **каждый** путь отвечал `ENOSYS`. Причина не в мосте:
musl на x86-64 предпочитает **легаси-номера без `dirfd`** — `open`(2), `stat`(4), `lstat`(6),
`access`(21), `readlink`(89), — а на riscv их не существует вовсе (generic ABI знает только
`*at`). Мы декодировали лишь `*at`-формы.

Заодно нашлась ошибка, которую без x86 никто бы не увидел: номер 89 (`readlink`) был помечен как
`Readlinkat`, а у них **разные аргументы** — у `readlinkat` путь второй, у `readlink` первый.
Работай оно, читало бы путь из буфера ответа.

## Что осталось

- **`mmap` файла не поддержан** — а `ld.so` отображает сегменты библиотек именно им (Веха 108.4).
- **Симлинки не разыменовываются при разборе пути**: `readlink` цель отдаёт, но `open` по пути
  через ссылку не пройдёт. `ld.so` это понадобится (`libc.so.6` в пакетах бывает ссылкой).
- **Относительных путей нет**: cwd Linux-процесса всегда `/`, `dirfd` игнорируется. Пакеты
  адресуются абсолютно, и пока этого хватало.
- **Каталоги иерархии `posixfs` не перечисляются** (их индекс другого формата); файлы её —
  читаются, но в том виде, в каком легли в store последним `close`.
