# Веха 11 — драйвер блоков как процесс-сервер

Первый шаг «драйверного фреймворка»: сервис устройства живёт в **непривилегированном процессе**
([[processes]]), а не в ядре, и вызывается сообщениями ([[ipc]]). Клиент не трогает диск/ядро
напрямую — он просит сервер-драйвер прочитать сектор, тот читает и отдаёт данные по IPC. Это
приближает архитектуру к [[0002-persistent-content-addressed-capability-core|ADR 0002]] (драйверы и
совместимость — вне ядра).

## Что добавлено
1. **IPC с передачей буфера.** `CALL(dest, msg, recv_buf, recv_cap)` запоминает приёмный буфер
   клиента; `REPLY(dest, src_buf, len)` копирует `len` байт из буфера сервера в приёмный буфер
   клиента. Копирование **между адресными пространствами**: ядро читает буфер сервера (текущий
   `satp`, `SUM=1`), а в память клиента пишет через `paging::translate` его таблицы (физический
   адрес отображён в ядре идентично, поэтому переключать `satp` не нужно) — см. `copy_to_space`,
   постранично (буфер может пересекать страницы).
2. **Привилегированный шлюз `SYS_BLK_READ(sector, buf)`.** DMA идёт в **ядерный** буфер (страницы
   процесса не отображены идентично, а устройство адресует физически), затем ядро копирует в буфер
   вызывающего (`SUM=1`). Так драйвер-процесс получает данные, не занимаясь DMA сам.

## Нюанс, который поймали: прерывания в U-mode
`sstatus.SIE` **не** маскирует S-прерывания, пока hart в **U-mode** — там они управляются только
битами `sie`. Таймер (STIE, [[scheduling|Веха 5.5]]) прерывал процесс прямо в U-mode, и обработчик
принимал это за неожиданный trap. Раз процессы пока **кооперативные**, на время сессии процессов
`proc::run` сбрасывает `sie.STIE|SEIE` и восстанавливает по возвращении. (Обработка этих прерываний
как вытеснения процесса — отдельный будущий шаг.)

## Сервер и клиент (U-mode)
- **Сервер-драйвер** (P0): `loop { (sector,from)=RECV(); BLK_READ(sector, buf); REPLY(from, buf, 512) }`.
  Буфер — на стеке через `MaybeUninit` (без обнуления: `[0u8;512]` мог бы вызвать `memset` вне
  секции `.user` → исполнение ушло бы в не-`U` страницу).
- **Клиент** (P1): `CALL(server=0, sector=0, buf, 512)`, затем печатает префикс + первые 6 байт
  сектора + перевод строки.

## Проверка (вывод в QEMU)
```
[proc] userspace-драйвер блоков (сервер) + клиент через IPC:
[ipc] P1 CALL P0 msg=0
[blk] P0 SYS_BLK_READ сектор 0
[ipc] P0 REPLY P1 (512 байт)
[blk-cli] sector 0 via driver-server: VOIDFS      ← клиент получил магию суперблока через сервер
[proc] P1 SYS_EXIT(0)
```
`VOIDFS` — это реальная магия суперблока с диска: данные прошли путь диск → ядро (BLK_READ) →
сервер-процесс → IPC-копия → клиент, ни разу не дав клиенту прямого доступа к железу.

## Осознанные упрощения (следующее)
- **Драйвер всё ещё через ядерный шлюз** (`BLK_READ`), а не владеет MMIO/DMA сам. Полный userspace-
  драйвер (MMIO в адресном пространстве процесса + доставка IRQ процессу + DMA) — крупный
  следующий шаг; главная трудность — DMA к неидентичным страницам процесса.
- ~~**Шлюз никем не защищён**: любой процесс мог бы вызвать `BLK_READ`.~~ **Закрыто на
  [[ipc-endpoints|Вехе 12]]**: `BLK_READ` требует cap на устройство (право `READ`), а `CALL` — cap
  на эндпоинт. Без нужного capability ядро отказывает.
- ~~**`dest` — id процесса**, а не capability на эндпоинт~~ — тоже закрыто на Вехе 12; сообщение —
  фикс. буфер 512 Б.
- **Только чтение** (нет BLK_WRITE); один сервер/клиент; кооперативно.
