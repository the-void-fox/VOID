# Известные пробелы и техдолг

Честная инвентаризация «недоделанного» на конец **Вехи 89** (папки, редактор строки, освобождение фреймов, AHCI-диск, установка на диск, e1000-сеть, USB-клавиатура, userspace-драйверы, хостинг Linux-драйверов до `ping`, фаза vvsh, гигабайты RAM, higher-half ядро, карта памяти регионами и санитария взяты).
Разделяю **по дизайну** (осознанно так) и **техдолг/недоделки** (надо чинить). Обновлять по мере закрытия.

## Файловая система

- **У ядра ФС нет вообще — ЭТО ДИЗАЙН** ([[0002-persistent-content-addressed-capability-core]]):
  есть контент-адресуемый store (объекты по хэшу + корни + capability). «Файлы/папки» —
  это персоналия ([[posix-personality]]), не ядро.
- ~~posixfs ПЛОСКАЯ~~ → **ИЕРАРХИЯ добавлена (Веха 44, [[folders]])**: каталоги/пути/`cwd`,
  `cd`/`pwd`/`mkdir`/`rm`, вложенность, персистентно — файлы под корнями `f<path>`, каталоги
  под `d<path>` (GC-safe), без правок ядра. Осталось: прав (uid/gid/mode) и времён нет,
  `rm -r` нет (только пустой каталог), файл ≤128 КиБ, 16 открытых слотов, std-`create_dir` нет.

## Реальное железо (Вехи 41–47 — грузимся до vsh, диск на SATA есть)

- ~~⚠️ **Загрузка на металле была сломана**~~ → **ПРОВЕРЕНО НА X54C (2026-08-03)**: грузится и
  работает. Заодно закрыт вопрос [[framebuffer]] о скорости — **пиксельная консоль на железе не
  медленнее текстовой**, значит WC-отображение (PAT/MTRR) не нужно. Сеть на X54C честно
  сообщает, что её нет (там Atheros/Realtek, не e1000 — ожидаемо).

- ~~Нет драйверов диска (AHCI/SATA)~~ → **AHCI есть (Веха 47, [[ahci]])**: store читает/пишет
  на реальный SATA-диск (проверено: запись пережила ребут). Опрос, одна команда, LBA48,
  BIOS в режиме AHCI. Осталось: NVMe, NCQ/прерывания.
- ~~Загрузка только с USB~~ → **установка на диск есть (Веха 48, [[install]])**: vsh `install`
  ставит VOID на SATA (GRUB+ядро в p1 FAT, store в p2 `0x9f`), дальше грузится с диска — проверено
  end-to-end в QEMU. Осторожно: **`install` стирает весь диск** (MBR с сектора 0). Осталось: GPT/UEFI,
  выбор диска, мульти-диск, обновление на месте (сейчас только полное стирание), NVMe-цель.
- ~~Нет реального NIC~~ → **e1000 есть (Веха 49, [[e1000]])**: драйвер Intel PRO/1000, ping отвечает
  (проверено в QEMU). НО у X54C проводной порт — Atheros/Realtek, не e1000 → на нём не поднимется
  (нужен драйвер того чипа). rtl8139/Atheros/wifi — отдельные драйверы.
- ~~USB-стека нет~~ → **xHCI + HID-клавиатура есть (Веха 50, [[usb]])**: свой USB-стек (контроллер
  → перечисление → HID boot keyboard), клавиатура на xHCI работает (проверено в QEMU). НО X54C =
  Sandy Bridge → **EHCI**, не xHCI → на нём этот драйвер USB не поднимет (там пока BIOS-legacy в
  `ps2.rs`). Осталось: EHCI, USB-мышь/флешки (MSC), хабы, прерывания вместо опроса.
- ~~Нет **RTC** → часы фиктивные~~ → **часы есть (Веха 86, [[clock]])**: CMOS RTC на x86,
  `google,goldfish-rtc` через DTB на riscv, `SYS_TIME` (№36); `SystemTime` в порте std больше не
  идёт от выдуманной базы, `clock_gettime` различает REALTIME и MONOTONIC. Там же **источник
  энтропии** (`SYS_RANDOM` №37: RDRAND + пул событий через BLAKE3) вместо прежнего xorshift.
  Осталось: **часовых поясов нет** (всё UTC — если прошивка держит RTC в локальном времени, дата
  уедет); **ход часов не корректируется** (`TICK_NS` откалибрована под QEMU, на железе поплывёт —
  нужен NTP или перечитывание RTC; сеть для NTP теперь есть); **времён у файлов** в posixfs всё
  ещё нет.
- ~~На riscv энтропия не криптографическая~~ → **virtio-rng** (перед Вехой 95): драйвер
  арх-нейтральный, подмешивается третьим источником в `random.rs`. Измерение по дороге опровергло
  запись в этой же заметке: **QEMU по умолчанию поднимает модель CPU без `RDRAND`**, то есть
  сильного источника не было ни на одной арх, хотя про x86 документация утверждала обратное
  (проверяется `-cpu max` — с ним `RDRAND` появляется).
- ~~Реальное железо без `RDRAND` и без гипервизора остаётся без источника~~ → **джиттер-источник**
  (`kernel/src/jitter.rs`) + **семя между загрузками** в сторе. Первое — разброс времени
  исполнения на самом процессоре (как jitterentropy в Linux); работает и на Sandy Bridge, и на
  любой плате со счётчиком тактов. Второе — то, что делает любой Unix, и у нас почти даром:
  store персистентен. Проверено в условиях старого железа (QEMU без virtio-rng и без `RDRAND`,
  обе арх): `[rng] джиттер есть`.
  **Что остаётся честной оговоркой:** санитарные тесты ловят ВСТАВШИЙ источник (счётчик не идёт,
  дельты не различаются), а не слабый; сертифицированной по SP 800-90B оценки энтропии нет, и
  давать её — отдельная работа. Джиттер никогда не единственный вход: `random` смешивает все
  источники. На riscv нужен `rdcycle` — доступность проверяется пробой с перехватом illegal
  instruction, а не предполагается (`rdtime` с его 100 нс для джиттера бесполезен).
- Таймерный квант откалиброван под QEMU (~1 ГГц); на железе преемпшн-интервал «не тот».

## Память

- ~~Аллокатор фреймов — bump БЕЗ освобождения~~ → **освобождение есть (Веха 46, [[frame-freeing]])**:
  фреймы завершившихся процессов (страницы + таблицы + корень) возвращаются в список свободных и
  переиспользуются; проверено — пик не растёт при повторных запусках. Осталось: Vec `procs` (слоты
  Finished) не переиспользуется — это КУЧА, не фреймы; арена кучи ядра (16 МиБ) и кольца virtio не
  освобождаются осознанно.
- ~~x86: операционная RAM зажата 256 МиБ~~ → **гигабайты есть (Веха 85, [[platform]])**: объём
  берётся у прошивки (PVH-memmap / DTB `/memory`), direct-map стелется 2-МиБ huge-страницами.
- ~~Потолки RAM несимметричны (riscv 2 ГиБ, x86 1 ГиБ)~~ → **сняты (Веха 87, [[higher-half]])**:
  ядро уехало в верхнюю половину, direct-map смещённый (`VA = PA + KERNEL_OFFSET`) и гигастраничный,
  регион процессов не тронут ([[0010-address-space-layout]]). riscv проверен на 16 ГиБ; x86 держит
  два окна (RAM `0xFFFF_8000_…`, образ `0xFFFF_FFFF_8000_…` — модель кода `kernel`).
- ~~Аллокатор фреймов не уважает карту памяти~~ → **уважает (Веха 88)**: карта памяти — список
  регионов (`frame::Region`, до 16), который прошивка отдаёт через `frame::add_region`; bump идёт
  по регионам, `is_ram` спрашивает карту, direct-map стелется по ней. На x86 наконец читается тег
  multiboot2 «memory map» (E820) — до этого на металле знали только `mem_upper`. RAM выше PCI-дыры
  в деле: `-m 8G` → 8191 МиБ вместо 2047. Осталось: гранулярность раздачи — по-прежнему bump +
  список свободных 4-КиБ фреймов, крупные непрерывные блоки (`reserve`) берутся только внутри
  ОДНОГО региона и теряют его хвост.

## Многозадачность / процессы

- **Один CPU, без SMP** — планировщик/локи/IPI однопроцессорные. Крупная переделка.
- Нет **пайпов между процессами** (`a | b` как поток байтов): в vvsh конвейер есть, но он течёт
  ЗНАЧЕНИЯМИ внутри шелла (Веха 80, [[vvsh-shell]]) — захвата stdout чужого процесса нет.
  `echo … > файл` — редирект внутри шелла в posixfs, не в ядре.
- ~~Нет фонового запуска; мультиплексор невозможен~~ → **ЗАКРЫТО Вехами 98–99**
  ([[process-stdio]], [[multiplexer]]): `SYS_SPAWN` не блокирует родителя, `SYS_WAIT` забирает
  код выхода (в т.ч. неблокирующе), stdio процесса маршрутизируется в IPC-эндпоинт хоста по
  соглашению userspace. Настоящего `fork` по-прежнему нет и не планируется.
- **Ребёнок не знает размер своей панели** (аналога `TIOCSWINSZ`/`SIGWINCH` нет) — программа
  считает, что пишет во весь экран. Первое, что стоит добавить к протоколу stdio.
- ~~**Убивать чужие процессы нельзя**~~ → **`SYS_KILL` есть (Веха 103)**: право из РОДИТЕЛЬСТВА,
  как у `SYS_WAIT` (чужой процесс по-прежнему неприкосновенен). Мультиплексор убивает процесс
  закрытой панели. Осталось: init не умеет снимать СЕРВИС — это часть `switch` без ребута.
- Job control как таковой (группы, сигналы) отсутствует.
- Сигналы linux-abi игнорируются. Checkpoint — только однонитевой.

## Оболочка (vvsh — основная, vsh — спасательная)

- ~~Нет редактирования строки~~ → **есть** и в vsh (Веха 45, [[tty]]), и свой в vvsh (Веха 81):
  курсор, вставка/удаление в позиции, `←`/`→`/`Home`/`End`/`Delete`, история `↑`/`↓`
  (PS/2-стрелки + serial, единый ANSI). Осталось: автодополнения нет, скроллбэка нет, строки шире
  экрана редактируются неидеально.
- Команда ≤128 байт (буфер строки) — длинный конфиг одной строкой в `echo` не влезает.
- vvsh: числа только `i64`, макросов/quasiquote нет, скриптов-файлов с шебангом нет; ошибки
  вычисления печатаются, но стека вызовов не показывают.
- Фоновых задач и job control нет (см. выше) — `run` всегда ждёт ребёнка.

## Store под нагрузкой (замер Вехи 101 — перед пакетной фазой)

- ~~**Всё, положенное за сессию, лежит в RAM**~~ → **ВЫТЕСНЕНИЕ ЕСТЬ (Веха 104)**: коммит
  отпускает `data` у объектов, чьи кадры уже на диске; забирает обратно `ensure_loaded`.
  Замер `store-probe` до и после: **было 8 МиБ пачкой (16 МиБ — паника), стало 64 МиБ без
  отказа**. Проверено, что данные читаются после вытеснения (`cat`, `eval` конфига).
- **Исчерпание кучи ядра — ПАНИКА, а не отказ.** `obj_put` не умеет ответить «не влезло»:
  аллокатор ядра паникует. Любой оверсайз убивает систему целиком.
- ~~Политика group commit не видит put'ов~~ → **починено (Веха 101)**: новый объект считается
  грязной операцией, и порог срабатывает под потоком данных, а не только при смене корней.
- Потолок «файл ≤8 МиБ» в `fetch` снят (список кусков 8192 × 16 КиБ = 128 МиБ).

## Бэкенды пакетов (все три «взяты», но минимальны)

- **linux-abi**: работают applet'ы в stdout (`echo`, `uname`); файловые (`cat FILE`, `ls`, `sh`)
  нет — нет моста linux→posixfs. Нет `clone`/`futex`, fork/exec. Только static-PIE (динамического
  загрузчика `ld.so` нет) — а в nixpkgs почти всё динамическое против glibc.
- **wasi**: только hello (6 импортов). Нет доступа к файлам (preopen'ы); clock/random теперь есть
  чем питать (Веха 86), но в раннер они ещё не проброшены.
- **Менеджера пакетов НА УСТРОЙСТВЕ нет** — «установка» = сборка на хосте (`nix/default.nix`
  `voidify` или cargo под `*-unknown-void`) + мост `void-store-import` в образ диска. Нет
  загрузки по сети, нет резолвера зависимостей, нет профилей; поколения/откат/дедуп даёт store.
  Это предмет ближайшей фазы (см. [[void-pkg]] и [[todo]]).
- **Компилятора на самом VOID нет** — ни C, ни Rust; всё кросс-собирается на хосте.

## Сеть (идёт сейчас — Фаза 7, [[net-stack]])

Взято Вехами 90–93: ~~свои 200 строк ARP/ICMP~~ → **vendored smoltcp**; ~~опрос~~ → **сон до
кадра или срока стека** (прерывание приёма на обеих арх); ~~зашитые адреса SLIRP~~ → **DHCPv4**
(статика осталась запасным путём, настраивается в `.vv` через `arg:`); **DNS** и `resolve` в vvsh;
**TCP** — соединение, обмен, аккуратное закрытие (`200 OK` от example.com получен из шелла).

Осталось:

- Нет **сокет-API уровня std**: `std::net` в порте не реализован, единственный интерфейс — IPC к
  `net-srv` (обёртка `net_cli.rs`).
- ~~HTTPS нет~~ → **Веха 95**: rustls на чистом RustCrypto, отдельной программой `httpsc` (у неё
  ровно два права — сеть и store). Проверка цепочки доказана отказами на badssl.com.
  Осталось: **редиректы для https** не сделаны; провайдер `rustls-rustcrypto` в версии
  `0.0.2-alpha` и тянет `rustls-webpki 0.102` с RUSTSEC-2026-0104 (CRL, мы их не используем).
- Клиенты умеют только `GET`, не держат соединение (`Connection: close`), и файл ограничен
  **512 кусками по 16 КиБ = 8 МиБ** (список детей плоский) — для пакетов нужно дерево поглубже.
- **Владения соединением нет**: хэндл — индекс слота, любой клиент с эндпоинтом сети может назвать
  чужой. Правильнее было бы отдавать cap на само соединение.
- Соединений всего **4**, буферы фиксированы; **`listen` не сделан** — только исходящие.
- Нет фрагментации/реассемблирования IPv4, нет IPv6, нет проверки на реальной LAN (только SLIRP).
- **Один DNS-сервер и одна A-запись** в ответе (`DNS_MAX_*` = 1 в сборке smoltcp): на сети с
  двумя резолверами резерва нет.
- **`ping` и `resolve` всё ещё блокируют цикл** сервера (TCP — уже нет, Веха 93 перевела его на
  отложенные ответы): пока они работают, ответы другим клиентам ждут.

## Устойчивость ядра и ресурсы (аудит перед Фазой 6, 2026-07 → **Веха 89, закрыто**)

Отдельный раздел: это были не «фичи», а **вещи, которые работали только потому, что нагрузки нет**.
С сетью и пакетами каждая превратилась бы в невоспроизводимое падение. Веха 89 закрыла все пять.

- ~~Замки не IRQ-safe~~ → **`SpinLock::lock_irq()`**: глушит прерывания ДО захвата и
  восстанавливает ПРЕЖНЕЕ состояние на drop. Переведены все замки, достижимые из обработчика
  (`ASYNC`, `EXECUTOR`, `SCHED`, кольцо консоли riscv, `XHCI` внутри `console_drain`, куча ядра);
  список — в преамбуле `sync.rs`. В `yield_now` намеренно остался обычный `lock()`: прерывания там
  выключены шире замка, до самого переключения контекста.
- ~~Store не проверяет то, на чём стоит весь тезис~~ → **хэш сверяется** с content-id при каждой
  загрузке с диска, результаты `io.read`/`io.write` больше не игнорируются, коммит атомарен
  (отметки «на диске» — только после успеха всех записей, откат при сбое индекса/суперблока).
  Сверх плана — **самоизлечение**: кадр программы-семени восстанавливается из образа ядра
  (`Store::repair`, по требованию в точке отказа). Пользовательские данные восстановить неоткуда —
  их порча только обнаруживается (`corrupt_reads`).
- ~~Ёмкость носителя неизвестна~~ → **`BlockIo::capacity()`**, коммит считает секторы до первой
  записи. Попутно закрыта смежная дыра: `compact` не запускает фазу 2, если фаза 1 не прошла
  (иначе затирались бы кадры, на которые ещё указывает активный суперблок).
- ~~Нет политики нехватки ресурсов~~ → `map`/`clone_kernel_root` фаллибельны, процессные пути
  отказывают вместо паники ядра (загрузочные остались `assert!` — там памяти всегда хватает).
  Появилась **квота страниц на группу нитей** (четверть рабочей RAM, не меньше 8 МиБ).
- ~~Слоты процессов не переиспользуются~~ → утилизированная группа отдаёт номера в список
  свободных; предварительно `cap::revoke_process` отзывает Endpoint/Reply на этот номер, иначе
  устаревший cap адресовал бы чужой новый процесс.
- ~~У ядерных задач нет guard page~~ → **сторож стека** (магия внизу, проверка на каждом
  переключении). Настоящую guard-страницу не поставить: стек берётся из кучи, а она лежит в
  direct-map, застеленной huge/гигастраницами.
- ~~Аллокатор vvsh — bump с пустым `dealloc`~~ → адресно-упорядоченный **свободный список со
  слиянием** соседей (схема кучи ядра).

Осталось в этом разделе:

- **Нельзя убить процесс.** `SYS_KILL`/сигналов нет: зациклившаяся программа вытесняется таймером
  (система жива), но снять её нельзя, а родитель в `SYS_EXEC` ждёт вечно. `Ctrl-C` в vvsh отменяет
  лишь набор строки. Для интерактивной системы это базовый пробел.
- **Заглушки linux-abi, возвращающие успех.** `nanosleep`/`clock_nanosleep` → 0 **без сна**
  (реальная программа получит busy-loop), `rt_sigaction`/`rt_sigprocmask`/`close`/`fcntl` → 0,
  `munmap` → 0 (bump-куча не освобождает). Для applet'ов сойдёт, для настоящих пакетов — нет.
- **Гранулярность аллокатора фреймов.** Bump + список свободных 4-КиБ фреймов; крупные непрерывные
  блоки (`reserve`) берутся только внутри ОДНОГО региона карты памяти и теряют его хвост.

## Стартовые права ПОЗИЦИОННЫ — ловушка, которая уже сработала

Программа берёт свои права по НОМЕРУ (`start_cap(0)` — файловый сервер, `start_cap(1)` — store).
Порядок задаёт строка конфига, дети наследуют его как есть. Достаточно переставить токены — и
`vvsh` принимает фреймбуфер за файловый сервер: `ls` роняет шелл, `run` ничего не запускает.
Ровно это и случилось на X54C (Веха 99.1): в сторе лежало поколение со старым порядком, а
конфиг переживает обновление ядра.

**ЗАКРЫТО (Веха 99.2).** init кладёт ИМЕНА прав в окружение (`CAP_POSIXFS`, `CAP_STORE`,
`CAP_FB`, `CAP_NET_SRV` — тем же приёмом, что `STDIO=<i>`), а `term` и `vvsh` ищут по имени с
откатом на прежнюю позицию (старые конфиги без имён продолжают работать).
Первая попытка перевести `vvsh` сломала шелл: `cap_named` разбирает окружение и звался из
горячих путей. Лечение — **резолвить один раз на старте** в статики; так и сделано.
Проверено в обоих поколениях: gen3 (панель — `ls`, `run install`, `date`) и gen1 (`resolve
example.com` → адрес, `roots` → корни store).

## Экран и глифы (открыто 2026-08, [[0014-terminal-ereb]])

- ~~**Потолок 256 глифов**~~ / ~~**пиксельного фреймбуфера нет**~~ → **СНЯТО Вехой 96**
  ([[framebuffer]]): тег-запрос в заголовке multiboot2 + разбор инфо-тега 8, консоль рисует
  глифы в пиксельный буфер (в QEMU 1280×800×32). Фреймбуфер отображается как MMIO (он выше
  карты RAM) и **никогда не читается** — скролл идёт через теневой текст. Остаётся в силе:
  путь PVH (`-kernel`) FB не даёт → графика смотрится с GRUB-диска/`void.iso`; режим выбирает
  видео-BIOS; **riscv по-прежнему без FB** (нужен virtio-gpu или ramfb); палитровые 8-битные
  режимы не поддержаны.
- **Скорость пиксельной консоли на металле не измерена — и в QEMU не измеряется**: там
  фреймбуфер это обычная память хоста, а на машине — некэшируемый MMIO через PCIe. Если запись
  окажется медленной, лечится WC-отображением (PAT/MTRR). Замер — на X54C.
- ~~**Не решено, кто владеет экраном**~~ → **РЕШЕНО Вехой 97** ([[terminal]]): владелец ровно
  один, экран выдаётся процессу под `mmio:fb` и возвращается ядру при панике и при смерти
  владельца; вывод ядра в это время идёт в serial.
- **Шрифт терминала вшит в ELF** (2.6 МБ). Срез угла, который уже отомстил: посев такого бинаря
  на riscv падал по куче ядра, из-за чего `term` пришлось сделать x86-only. Переносить в store
  отдельным объектом-деревом (механизм с Вехи 94) — заодно шрифт станет сменяемым без пересборки.
- ~~**Псевдографика не стыкуется**~~ → **на реальном железе рамки СТЫКУЮТСЯ** (проверено на
  X54C); разрывы — артефакт вывода QEMU. Запись оставлена как напоминание: то, что видно в
  эмуляторе, не обязано быть свойством системы.
- **Терминал: после ПЕРЕЗАГРУЗКИ точка вывода уезжает на 2–3 строки вверх** и текст затирает
  сам себя (X54C). В QEMU НЕ воспроизводится — две подряд загрузки дают попиксельно одинаковый
  кадр. Значит причина железозависимая; первый подозреваемый — другой видеорежим от VBE при
  загрузке с диска против загрузки с носителя. Диагностика дешёвая: в баннере терминала печатается
  `экран : Ш×В` — сравнить две загрузки.
- ~~**Нет команды выключения машины**~~ → **ЕСТЬ (Веха 101)**: `poweroff` в обоих шеллах,
  `exit` в `vsh` и выход из `term` — тоже. Под capability (`power` в конфиге, `Target::Power`):
  выключение — одностороннее действие над всей системой, и «может любой процесс» здесь было бы
  дырой ровно того сорта, который модель закрывает. На x86 путь настоящий, ACPI: `RSD PTR ` →
  RSDT/XSDT → FADT → `_S5_` в DSDT → порт PM1; на riscv — SBI (`sbi::shutdown`, был всегда).
  Порядок: сперва финальный синк store, потом питание.
  **Оговорка:** старым поколениям `gen1`/`gen2` (они принадлежат владельцу и не переписываются)
  токена `power` не досталось — там `exit` работает как раньше, пока не сделать `rebuild`.
  Попутно выяснилось, почему «конец сессии» не выключал машину сам: сессия в нынешнем виде НЕ
  КОНЧАЕТСЯ — после ухода шелла остаются сервисы, и планировщик честно крутит их дальше.
- **Direct-map ниже 4 ГиБ тянется на 64 МиБ выше пригодной RAM** (Веха 101) — чтобы ядро могло
  прочитать таблицы ACPI: они лежат в записях карты типа «reclaim», которых нет в списке RAM.
  Это ровно то, что до Вехи 101 давало page fault при попытке выключиться. Аллокатору эти
  страницы по-прежнему не отдаются — только отображению.
- ~~**Терминал ОТРИСОВЫВАЕТ весь кадр**~~ → **починено (Веха 99.2)**: и отрисовка, и перенос
  идут по списку изменившихся строк. Владелец подтвердил на X54C: стало «удовлетворительно», но
  всё ещё медленнее голой консоли ядра. Осталось дорогим **прокручивание панели** (там меняются
  все её строки) — лечится сдвигом уже нарисованных пикселей в RAM, но сперва нужен замер.
- ~~**Схема управления терминалом живёт в коде**~~ → **в конфиге (Веха 100)**: `terminal`/`bind`
  в `/etc/system/terminal.vv` → поколение → `term` читает его из store ([[vvsh-config-layout]]).
  Осталось: перечитать конфиг без перезапуска терминала нельзя; Ctrl-H/I/M привязать невозможно
  (на байтовой консоли это те же байты, что Backspace/Tab/Enter).
- **Разбор ANSI живёт в ЯДРЕ** (`vga.rs::put_char` — автомат Normal/Esc/Csi, SGR, `ESC[2J`,
  движение курсора, [[tty]]). Архитектурно не то место; при переносе грида в userspace уезжает
  туда вместе с ним.
- **Мыши нет** — ни строки в ядре. Терминалу не нужна, композитору ([[0007-graphics-native-compositor]])
  нужна.
- ~~**Нет stdio процессов по IPC**~~ → **есть (Веха 98)**: соглашение поверх обычного IPC
  (`OP_STDOUT`/`OP_STDIN`/`OP_WINSIZE`, [[process-stdio]]); ядро так и не узнало, что такое
  stdio. На нём и стоит мультиплексор ([[multiplexer]]).
- **Запрос к файловому серверу ≤512 байт** (буфер `req` в `bin/posixfs`) — но усечение больше
  НЕ МОЛЧИТ (Веха 101): `SYS_CALL` возвращает доставленную длину запроса и желаемую длину ответа,
  `posix::write` отдаёт реально доехавшее, `echo_to` — успех/неуспех, шеллы сообщают человеку.
  Сама граница осталась: вызов, шлющий больше, по-прежнему доедет обрезанным — просто теперь об
  этом будет известно. Остаётся долгом сделать усечение ОШИБКОЙ, а не сообщённым фактом.

       строит TX-кольцо дескрипторов vendored `e1000_setup_all_tx_resources` на РЕАЛЬНОМ DMA, конфигурирует
       TX-движок (TDBAL/TDLEN/TCTL/TIPG вручную — `e1000_configure_tx` static) и передаёт 60-байтовый кадр:
       дескриптор → TDT → карта выносит его DMA'ом, ставит DD-бит. Проверено (x86): `setup_all_tx_resources
       → ring dma=0x13e3000` (реальный физ-адрес), `TX: desc0.status=0x01 DD=1 TDH=1 — OK`. Первое
       использование DMA-cap портированным Linux-драйвером. Регрессии чисты; ядро не менялось.
     - ✅ **Портированный e1000: TX+RX (ARP round-trip)** (Веха 71, [[lx-e1000-rx]]): добавлено RX-кольцо
       (vendored `e1000_setup_all_rx_resources` на DMA + RX-буферы + `RDBAL/RDLEN/RDT/RCTL` промиск +
       `RAL0`=наш MAC). Драйвер шлёт **ARP-запрос** шлюзу (TX) и **принимает ARP-ответ** (RX, опрос
       DD-дескриптора) — двунаправленный реальный трафик через портированный драйвер. Проверено (x86):
       `TX ARP «who has 10.0.2.2» → DD=1`, `RX: дескриптор 0 DD, 64 Б, ethertype=0806`, `ARP-ОТВЕТ от
       10.0.2.2: MAC шлюза 52:55:0a:00:02:02 — OK` (штатный SLIRP-шлюз — ответ реально пришёл). Регрессии
       чисты; ядро не менялось.
     - ✅ **RX по прерыванию** (Веха 72, [[lx-e1000-irq]]): `request_irq` вшит в idle-путь
       кооперативного планировщика Lx_kit — процесс спит в `vsys_irq_wait` по IRQ-cap, ISR читает
       ICR и будит задачу через `complete`; кадр приходит от реального прерывания, не опроса.
     - ✅ **`ping` через портированный драйвер** (Веха 73, [[lx-e1000-ping]]): ARP → ICMP echo →
       приём reply от живого шлюза. **Способность хостить неизменённые Linux-драйверы доказана**
       ([[void-driver-hosting-proven]]); дальше драйверы конкретных чипов — ПО ТРЕБОВАНИЮ.
   - Своими силами ещё: EHCI, NVMe. GPU-3D = порт Linux DRM+Mesa (гора). **Правка 2026-08:**
     framebuffer больше не значится за UEFI-GOP — он берётся **тегом multiboot2** от GRUB,
     которым мы и так грузимся (см. «Экран и глифы» выше и [[0014-terminal-ereb]]); UEFI-GOP
     потребовал бы UEFI-загрузки, которой у нас нет ([[install]] — MBR+GRUB).
   - Без IOMMU dma-cap = «DMA куда угодно» (драйвер доверенный); настоящая изоляция — потом.
5. ✅ **vvsh** — свой Lisp для конфига и шелла (Вехи 75–84, [[vvsh-shell]]): система грузится в
