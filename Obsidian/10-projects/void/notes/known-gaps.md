# Известные пробелы и техдолг

Честная инвентаризация «недоделанного» на конец **Вехи 89** (папки, редактор строки, освобождение фреймов, AHCI-диск, установка на диск, e1000-сеть, USB-клавиатура, userspace-драйверы, хостинг Linux-драйверов до `ping`, фаза vvsh, гигабайты RAM, higher-half ядро, карта памяти регионами и санитария взяты).
Разделяю **по дизайну** (осознанно так) и **техдолг/недоделки** (надо чинить). Обновлять по мере закрытия.

## Файловая система

- **У ядра ФС нет вообще — ЭТО ДИЗАЙН** ([[0002-persistent-content-addressed-capability-core]]):
  есть контент-адресуемый store (объекты по хэшу + корни + capability). «Файлы/папки» —
  это персоналия ([[posix-personality]]), не ядро.
- ~~posixfs ПЛОСКАЯ~~ → **ИЕРАРХИЯ добавлена (Веха 44, [[folders]])**: каталоги/пути/`cwd`,
  `cd`/`pwd`/`mkdir`/`rm`, вложенность, персистентно — файлы под корнями `f<path>`, каталоги
  под `d<path>` (GC-safe), без правок ядра. Осталось: прав (uid/gid/mode) и времён нет,
  `rm -r` нет (только пустой каталог), файл ≤128 КиБ, 16 открытых слотов, std-`create_dir` нет.

## Реальное железо (Вехи 41–47 — грузимся до vsh, диск на SATA есть)

- ~~⚠️ **Загрузка на металле была сломана**~~ → **ПРОВЕРЕНО НА X54C (2026-08-03)**: грузится и
  работает. Заодно закрыт вопрос [[framebuffer]] о скорости — **пиксельная консоль на железе не
  медленнее текстовой**, значит WC-отображение (PAT/MTRR) не нужно. Сеть на X54C честно
  сообщает, что её нет (там Atheros/Realtek, не e1000 — ожидаемо).

- ~~Нет драйверов диска (AHCI/SATA)~~ → **AHCI есть (Веха 47, [[ahci]])**: store читает/пишет
  на реальный SATA-диск (проверено: запись пережила ребут). Опрос, одна команда, LBA48,
  BIOS в режиме AHCI. Осталось: NVMe, NCQ/прерывания.
- ~~Загрузка только с USB~~ → **установка на диск есть (Веха 48, [[install]])**: vsh `install`
  ставит VOID на SATA (GRUB+ядро в p1 FAT, store в p2 `0x9f`), дальше грузится с диска — проверено
  end-to-end в QEMU. Осторожно: **`install` стирает весь диск** (MBR с сектора 0). Осталось: GPT/UEFI,
  выбор диска, мульти-диск, обновление на месте (сейчас только полное стирание), NVMe-цель.
- ~~Нет реального NIC~~ → **e1000 есть (Веха 49, [[e1000]])**: драйвер Intel PRO/1000, ping отвечает
  (проверено в QEMU). НО у X54C проводной порт — Atheros/Realtek, не e1000 → на нём не поднимется
  (нужен драйвер того чипа). rtl8139/Atheros/wifi — отдельные драйверы.
- ~~USB-стека нет~~ → **xHCI + HID-клавиатура есть (Веха 50, [[usb]])**: свой USB-стек (контроллер
  → перечисление → HID boot keyboard), клавиатура на xHCI работает (проверено в QEMU). НО X54C =
  Sandy Bridge → **EHCI**, не xHCI → на нём этот драйвер USB не поднимет (там пока BIOS-legacy в
  `ps2.rs`). Осталось: EHCI, USB-мышь/флешки (MSC), хабы, прерывания вместо опроса.
- ~~Нет **RTC** → часы фиктивные~~ → **часы есть (Веха 86, [[clock]])**: CMOS RTC на x86,
  `google,goldfish-rtc` через DTB на riscv, `SYS_TIME` (№36); `SystemTime` в порте std больше не
  идёт от выдуманной базы, `clock_gettime` различает REALTIME и MONOTONIC. Там же **источник
  энтропии** (`SYS_RANDOM` №37: RDRAND + пул событий через BLAKE3) вместо прежнего xorshift.
  Осталось: **часовых поясов нет** (всё UTC — если прошивка держит RTC в локальном времени, дата
  уедет); **ход часов не корректируется** (`TICK_NS` откалибрована под QEMU, на железе поплывёт —
  нужен NTP или перечитывание RTC; сеть для NTP теперь есть); **времён у файлов** в posixfs всё
  ещё нет.
  **Веха 116.1 показала, во что это упирается практически:** все наши замеры времени на железе
  завышены во столько раз, во сколько настоящий TSC быстрее предполагаемого гигагерца (на Sandy
  Bridge это 1,6–2,3). Калибровка по независимому источнику (RTC-секунда или PIT) сделала бы
  честными и `date`, и все измерения скорости.
- ~~На riscv энтропия не криптографическая~~ → **virtio-rng** (перед Вехой 95): драйвер
  арх-нейтральный, подмешивается третьим источником в `random.rs`. Измерение по дороге опровергло
  запись в этой же заметке: **QEMU по умолчанию поднимает модель CPU без `RDRAND`**, то есть
  сильного источника не было ни на одной арх, хотя про x86 документация утверждала обратное
  (проверяется `-cpu max` — с ним `RDRAND` появляется).
- ~~Реальное железо без `RDRAND` и без гипервизора остаётся без источника~~ → **джиттер-источник**
  (`kernel/src/jitter.rs`) + **семя между загрузками** в сторе. Первое — разброс времени
  исполнения на самом процессоре (как jitterentropy в Linux); работает и на Sandy Bridge, и на
  любой плате со счётчиком тактов. Второе — то, что делает любой Unix, и у нас почти даром:
  store персистентен. Проверено в условиях старого железа (QEMU без virtio-rng и без `RDRAND`,
  обе арх): `[rng] джиттер есть`.
  **Что остаётся честной оговоркой:** санитарные тесты ловят ВСТАВШИЙ источник (счётчик не идёт,
  дельты не различаются), а не слабый; сертифицированной по SP 800-90B оценки энтропии нет, и
  давать её — отдельная работа. Джиттер никогда не единственный вход: `random` смешивает все
  источники. На riscv нужен `rdcycle` — доступность проверяется пробой с перехватом illegal
  instruction, а не предполагается (`rdtime` с его 100 нс для джиттера бесполезен).
- Таймерный квант откалиброван под QEMU (~1 ГГц); на железе преемпшн-интервал «не тот».

## Память

- ~~Аллокатор фреймов — bump БЕЗ освобождения~~ → **освобождение есть (Веха 46, [[frame-freeing]])**:
  фреймы завершившихся процессов (страницы + таблицы + корень) возвращаются в список свободных и
  переиспользуются; проверено — пик не растёт при повторных запусках. Осталось: Vec `procs` (слоты
  Finished) не переиспользуется — это КУЧА, не фреймы; арена кучи ядра (16 МиБ) и кольца virtio не
  освобождаются осознанно.
- ~~x86: операционная RAM зажата 256 МиБ~~ → **гигабайты есть (Веха 85, [[platform]])**: объём
  берётся у прошивки (PVH-memmap / DTB `/memory`), direct-map стелется 2-МиБ huge-страницами.
- ~~Потолки RAM несимметричны (riscv 2 ГиБ, x86 1 ГиБ)~~ → **сняты (Веха 87, [[higher-half]])**:
  ядро уехало в верхнюю половину, direct-map смещённый (`VA = PA + KERNEL_OFFSET`) и гигастраничный,
  регион процессов не тронут ([[0010-address-space-layout]]). riscv проверен на 16 ГиБ; x86 держит
  два окна (RAM `0xFFFF_8000_…`, образ `0xFFFF_FFFF_8000_…` — модель кода `kernel`).
- ~~Аллокатор фреймов не уважает карту памяти~~ → **уважает (Веха 88)**: карта памяти — список
  регионов (`frame::Region`, до 16), который прошивка отдаёт через `frame::add_region`; bump идёт
  по регионам, `is_ram` спрашивает карту, direct-map стелется по ней. На x86 наконец читается тег
  multiboot2 «memory map» (E820) — до этого на металле знали только `mem_upper`. RAM выше PCI-дыры
  в деле: `-m 8G` → 8191 МиБ вместо 2047. Осталось: гранулярность раздачи — по-прежнему bump +
  список свободных 4-КиБ фреймов, крупные непрерывные блоки (`reserve`) берутся только внутри
  ОДНОГО региона и теряют его хвост.

## Многозадачность / процессы

- **Один CPU, без SMP** — планировщик/локи/IPI однопроцессорные. Крупная переделка. **С 2026-08-04
  этот пробел на критическом пути**: [[0015-hypervisor-linux-guest|ADR 0015]] выбрал гипервизор
  дорогой к Steam/Proton, а игровая VM на одном ядре бессмысленна. Второй предпосылкой там же —
  **IOMMU** (сегодня `dma-cap` = доверенное «DMA куда угодно», см. [[userspace-drivers]]).
- Нет **пайпов между процессами** (`a | b` как поток байтов): в vvsh конвейер есть, но он течёт
  ЗНАЧЕНИЯМИ внутри шелла (Веха 80, [[vvsh-shell]]) — захвата stdout чужого процесса нет.
  `echo … > файл` — редирект внутри шелла в posixfs, не в ядре.
- ~~Нет фонового запуска; мультиплексор невозможен~~ → **ЗАКРЫТО Вехами 98–99**
  ([[process-stdio]], [[multiplexer]]): `SYS_SPAWN` не блокирует родителя, `SYS_WAIT` забирает
  код выхода (в т.ч. неблокирующе), stdio процесса маршрутизируется в IPC-эндпоинт хоста по
  соглашению userspace. Настоящего `fork` по-прежнему нет и не планируется.
- **Ребёнку не СООБЩАЮТ о смене размера панели.** Спросить он может (`OP_WINSIZE` в протоколе
  stdio, Веха 99.3 — `vvsh` печатает размер в баннере), а вот аналога `SIGWINCH` нет: панель
  переразбили — программа узнает об этом, только если спросит сама. *(Запись до Вехи 114
  утверждала, что размер вообще недоступен. Проверено по коду.)*
- ~~**Убивать чужие процессы нельзя**~~ → **`SYS_KILL` есть (Веха 103)**: право из РОДИТЕЛЬСТВА,
  как у `SYS_WAIT` (чужой процесс по-прежнему неприкосновенен). Мультиплексор убивает процесс
  закрытой панели. Осталось: init не умеет снимать СЕРВИС — это часть `switch` без ребута.
- Job control как таковой (группы, сигналы) отсутствует.
- Сигналы linux-abi игнорируются. Checkpoint — только однонитевой.

## Оболочка (vvsh — основная, vsh — спасательная)

- ~~Нет редактирования строки~~ → **есть** и в vsh (Веха 45, [[tty]]), и свой в vvsh (Веха 81):
  курсор, вставка/удаление в позиции, `←`/`→`/`Home`/`End`/`Delete`, история `↑`/`↓`
  (PS/2-стрелки + serial, единый ANSI). Осталось: автодополнения нет, строки шире экрана
  редактируются неидеально. ~~Скроллбэка нет~~ → **ЕСТЬ у панелей терминала (Веха 116,
  [[klog-scroll]])**: `S-PageUp`/`S-PageDown` (в режиме панелей — просто PageUp/PageDown),
  10 000 строк истории, вьюпорт не уезжает под новым выводом. В `vsh` и в консоли ядра
  прокрутки по-прежнему нет — там её негде держать.
- Команда ≤128 байт (буфер строки) — длинный конфиг одной строкой в `echo` не влезает. Правку
  файлов это больше не ограничивает: ~~редактора нет вовсе~~ → **есть `ved`** (Веха 120,
  [[editor]]) — экранный, работает и в консоли ядра (то есть в спасательном шелле), и в панели
  терминала, и в окне. Его собственные долги: нет отмены, поиска и перехода к строке по номеру;
  файл больше 128 КиБ не открыть (потолок `posixfs`, не редактора).
- vvsh: числа только `i64`, макросов/quasiquote нет, скриптов-файлов с шебангом нет; ошибки
  вычисления печатаются, но стека вызовов не показывают.
- Фоновых задач и job control нет (см. выше) — `run` всегда ждёт ребёнка.

## Store под нагрузкой (замер Вехи 101 — перед пакетной фазой)

- ~~**Всё, положенное за сессию, лежит в RAM**~~ → **ВЫТЕСНЕНИЕ ЕСТЬ (Веха 104)**: коммит
  отпускает `data` у объектов, чьи кадры уже на диске; забирает обратно `ensure_loaded`.
  Замер `store-probe` до и после: **было 8 МиБ пачкой (16 МиБ — паника), стало 64 МиБ без
  отказа**. Проверено, что данные читаются после вытеснения (`cat`, `eval` конфига).
- **Исчерпание кучи ядра — паника, но уже НЕ на пути из userspace (Веха 104).** `SYS_OBJ_PUT`
  и `SYS_OBJ_PUT_NODE` резервируют через `try_reserve` и честно отвечают «не влезло»
  (`[obj] … НЕ ХВАТИЛО памяти ядра`) — то есть чужой размер (программа, сеть, архив) больше не
  роняет систему.
  **Осталось:** сам КОММИТ по-прежнему паникует под давлением — там строится индекс-кадр (замер:
  2.78 МБ на диске, забитом 200 МиБ мусора) и прочие служебные векторы обычным аллокатором.
  Воспроизводится, когда носитель кончился: объекты не могут уехать на диск, значит не могут быть
  вытеснены, и растёт всё сразу. На носителе по размеру — не наступает.
- ~~Политика group commit не видит put'ов~~ → **починено (Веха 101)**: новый объект считается
  грязной операцией, и порог срабатывает под потоком данных, а не только при смене корней.
- Потолок «файл ≤8 МиБ» в `fetch` снят (список кусков 8192 × 16 КиБ = 128 МиБ).
- ~~**GC затягивал в память весь достижимый store**~~ → **ЗАКРЫТО (Веха 108.1, [[pkg-tree]])**:
  обход `mark` звал `ensure_loaded` на каждом объекте и ни одного не отпускал. Пока store был
  меньше кучи ядра, это не проявлялось; первый настоящий пакет (glibc — 4291 объект, 37 МБ)
  уронил систему НА ЗАГРУЗКЕ, на обеих архитектурах, и падал при этом не виноватый, а первый
  попросивший память после него. Теперь от объекта берутся только ссылки, а кадр, уже лежащий на
  диске, тут же отпускается: память обхода — O(индекса), а не O(содержимого).
- ~~**`compact` по построению требует всё живое в RAM**~~ → **ЗАКРЫТО (Веха 110, [[store-compact]])**:
  коммит получил режим ПЕРЕСЕЛЕНИЯ — подгружает объект прямо перед записью и отпускает сразу после,
  читая по старому адресу и записывая по новому. Мина была заряжена: store с пакетами дорос до
  93 МиБ при куче ядра 16 МиБ, и уплотнение зовётся ПО ПОРОГУ МУСОРА НА ЗАГРУЗКЕ — то есть
  система переставала бы грузиться после обычного `pkg remove`. Проверено на одном и том же диске:
  старый код — `memory allocation of 16384 bytes failed`, новый — уплотняет 45 МиБ живого и
  поднимается.
- **Уплотнение дорого и не прерывается**: переписывает всё живое ДВАЖДЫ (85 МиБ записи на 45 МиБ
  данных) и в QEMU занимает минуты, всё это время система не загрузилась. Инкрементального
  уплотнения (по кускам области, с продолжением после перезагрузки) нет.
- ~~**Store молча теряет объекты после чередования крупных записей и чтений**~~ → **НАЙДЕНО И
  ЗАКРЫТО (Веха 111, [[pkg-names]])**, и виноват был не store. Демо `blk-cli` (Веха 17) писала
  паттерн в **жёстко зашитый сектор 20000** с комментарием «заведомо свободный: store использует
  низкие». С индексом канала (15 МиБ) область объектов дошла до него, и каждая загрузка стала
  затирать живой кадр на 512 байт — всплывало это как «кадр с диска не сошёлся со своим
  content-id» через сутки и в другом месте. Теперь сектор для опытов ВЫДАЁТ store
  (`void_store::TAIL_RESERVED` — хвост носителя), а ядро передаёт его демке; не сказали — не
  пишем. Мораль на будущее: «вероятно свободный сектор» не бывает.
- ~~**Кэш store растёт без потолка**~~ → **ЗАКРЫТО (Веха 111)**: чтение большого блоба насквозь
  (941 кусок индекса = 15 МиБ) затягивало всё в кучу ядра, и система падала на попытке запустить
  следующую программу (`memory allocation of 647920 bytes failed` — это `httpsc`). Введён
  `CACHE_BUDGET` (четверть кучи ядра); при превышении отпускается всё подгруженное с диска, кроме
  только что прочитанного. Тест `full_scan_of_big_blob_stays_within_cache_budget`.
- **virtio-blk отказывает в записи под пачкой (найдено Вехой 107, x86_64).** Загрузка x86 на диске,
  где уже лежит store, написанный riscv: посев 25 программ своей архитектуры идёт одной пачкой, и
  в лог падает `[store] ЗАПИСЬ ОТКАЗАНА (2 раз) … (4 раз)`. Данные не теряются — коммит по
  построению отменяется целиком, следующий проходит (`поколение 18`, 4130 КиБ за сессию), и
  профиль после этого читается верно, — но загрузка до vsh занимает ~100 с вместо ~15.
  **Подозрение**: очередь 0 у драйвера ОДНА на два пути — синхронный `request` (дескрипторы 0..2
  берутся безусловно, `used_idx` считается сам) и асинхронный `read_async` future демо-загрузки.
  Пересечение даёт чужой `used`-индекс и статус `0xff`, то есть «устройство отказало» на ровном
  месте. Чинится либо разведением дескрипторов, либо запретом синхронного пути, пока есть
  незавершённый асинхронный.

## Бэкенды пакетов (все три «взяты», но минимальны)

- ~~**linux-abi**: только applet'ы в stdout, нет файлов, нет `ld.so`~~ → **ФАЙЛЫ И ДИНАМИКА ЕСТЬ
  (Вехи 108.3–108.4, [[lx-files]], [[lx-dynamic]])**: `openat`/`read`/`fstat`/`getdents64`/
  `readlink` читают пакет прямо из store, а динамический бинарь nixpkgs запускается — ядро грузит
  `ld.so` из `PT_INTERP`, даёт ему `AT_BASE`, `mmap` файла и `mprotect`, дальше он линкует сам.
  Проверено на обеих архитектурах своими glibc. **Осталось**: потоков нет (`clone`), относительных
  путей нет, `munmap` — заглушка, запись в файлы через персоналию невозможна (EROFS).
- **Имя пакета не резолвится** (Веха 109, [[pkg-life]]): `pkg install` принимает хэш пути, а не
  `hello`. Резолвер требует либо вычисления nixpkgs на устройстве (Фаза 9), либо индекса
  «имя → путь», посеянного мостом. Это единственное, что отделяет `pkg install hello` от того,
  что уже работает.
- **wasi**: только hello (6 импортов). Нет доступа к файлам (preopen'ы); clock/random теперь есть
  чем питать (Веха 86), но в раннер они ещё не проброшены.
- ~~**Менеджера пакетов НА УСТРОЙСТВЕ нет**~~ → **ЕСТЬ, но не запускает (Вехи 105–107)**:
  `pkg fetch/install/remove/list/gens/rollback` тянет замыкание из кэша nixpkgs с проверкой
  подписи и NarHash, ведёт профиль поколениями ([[pkg-closure]]). Чего ещё нет: **скачанное не
  запускается** — NAR лежит в store, но в файловой системе не разложен, симлинков персоналия не
  знает, динамического загрузчика нет (Веха 108); имя пакета не резолвится (`pkg install hello`
  требует вычисления nixpkgs — пока только хэш пути); GC не подчищает пути, выпавшие из всех
  поколений (Веха 109). Сборка на хосте (`nix/default.nix` `voidify`, мост `void-store-import`)
  остаётся способом доставки СВОИХ программ.
- **Компилятора на самом VOID нет** — ни C, ни Rust; всё кросс-собирается на хосте.

## Сеть (идёт сейчас — Фаза 7, [[net-stack]])

Взято Вехами 90–93: ~~свои 200 строк ARP/ICMP~~ → **vendored smoltcp**; ~~опрос~~ → **сон до
кадра или срока стека** (прерывание приёма на обеих арх); ~~зашитые адреса SLIRP~~ → **DHCPv4**
(статика осталась запасным путём, настраивается в `.vv` через `arg:`); **DNS** и `resolve` в vvsh;
**TCP** — соединение, обмен, аккуратное закрытие (`200 OK` от example.com получен из шелла).

Осталось:

- Нет **сокет-API уровня std**: `std::net` в порте не реализован, единственный интерфейс — IPC к
  `net-srv` (обёртка `net_cli.rs`).
- ~~HTTPS нет~~ → **Веха 95**: rustls на чистом RustCrypto, отдельной программой `httpsc` (у неё
  ровно два права — сеть и store). Проверка цепочки доказана отказами на badssl.com.
  Осталось: **редиректы для https** не сделаны; провайдер `rustls-rustcrypto` в версии
  `0.0.2-alpha` и тянет `rustls-webpki 0.102` с RUSTSEC-2026-0104 (CRL, мы их не используем).
- Клиенты умеют только `GET`, не держат соединение (`Connection: close`), и файл ограничен
  **512 кусками по 16 КиБ = 8 МиБ** (список детей плоский) — для пакетов нужно дерево поглубже.
- **Владения соединением нет**: хэндл — индекс слота, любой клиент с эндпоинтом сети может назвать
  чужой. Правильнее было бы отдавать cap на само соединение.
- Соединений всего **4**, буферы фиксированы; **`listen` не сделан** — только исходящие.
- **Буфер приёма TCP упирается в СТЕК, а не в сеть** (Веха 135.2, [[net-speed]]): массивы лежат на
  стеке `net-srv`, стек процесса — 256 КиБ, и 4 × 16 КиБ уже заметная его доля. Дальше растить
  окно — только вынеся буферы со стека. Это нынешний потолок скорости.
- Нет фрагментации/реассемблирования IPv4, нет IPv6.
- ~~Проверки нигде, кроме SLIRP~~ → **Веха 135**: честный сегмент между двумя QEMU, pcap и
  задержка канала ([[net-speed]], [[void-qemu-run]]). На настоящей LAN (tap/железо) стек всё ещё
  не гонялся; e1000-путь ожил только в 135.3.
- ~~**Один DNS-сервер**~~ → **Веха 136: четыре** (`dns=A,B` в конфиге, от DHCP берём всех, кого
  дал роутер). **Одна A-запись** в ответе осталась (`DNS_MAX_RESULT_COUNT = 1`).
- **`ping` и `resolve` всё ещё блокируют цикл** сервера (TCP — уже нет, Веха 93 перевела его на
  отложенные ответы): пока они работают, ответы другим клиентам ждут. Веха 136 убрала хотя бы
  ГОРЕНИЕ процессора в этом ожидании (спим по `poll_delay` после первых 20 мс), но 12 секунд
  мёртвого резолвера — это 12 секунд ожидания для остальных клиентов.
- **Кэша DNS нет вовсе** ([[net-dns]]): каждое `resolve` идёт на провод, TTL из ответа читается и
  выбрасывается.
- **Усечённый ответ DNS (бит TC) не обрабатывается** — полагается перезапросить по TCP, чего мы
  не делаем. Стенд это изображать умеет (`netpeer.py --truncate`), проверка не написана.
- **Список блокировки — до ~10 тысяч имён** (арена 192 КиБ в `net-srv`, сравнение точное):
  готовые списки бывают на порядок больше. При переполнении сервер честно печатает, сколько взял
  из скольких.

## Граница «пользователь → ядро» (аудит после Вехи 126.4, 2026-08-10)

Класс, открытый ошибкой флага направления ([[direction-flag]]): **ядро что-то предполагает о
своём окружении, а устанавливать это никто не обязан.** Проверено по коду, не на глаз.

Закрыто:

- **`DF`** — `cld` первой инструкцией `trap_common` (Веха 126.4).
- **`IF`** — шлюзы IDT у нас `0x8e` (interrupt gate): прерывания гасит процессор, обработчики
  не реентерабельны, и целого семейства гонок вместе с этим нет.
- **`TF`/`NT`** — гасит процессор при входе через шлюз.
- **`fs`/`gs`** — ядро их не использует, ошибок вокруг `swapgs` быть не может.
- **Тест враждебного процесса** — `hostile` (Веха 126.5, [[hostile]]): приходит на границу с
  нарочно испорченным состоянием и требует, чтобы ядро выжило. Проверено, что он ЛОВИТ ошибку
  126.4: со снятым `cld` машина гибнет на первой же строке теста.

Открыто, по убыванию цены:

- ~~**SMEP выключен**~~ → **ВКЛЮЧЁН Вехой 128** (`paging::enable_smep`): проверка CPUID (лист 7,
  EBX бит 7) и бит 20 в `CR4`. Ядру теперь ЗАПРЕЩЕНО ЖЕЛЕЗОМ выбирать инструкции из страниц с
  битом U. Включать было безопасно: и трамплин (`entry.s`, записи `0x83`), и окно образа
  отображены без U.
  **ОГОВОРКА: на X54C его нет.** SMEP появился в Ivy Bridge, а там Sandy Bridge — функция честно
  вернёт `false` и промолчит. То есть на целевой машине это задел на будущее, а не защита
  сегодня; из проверенного на ней работает сторож стека.
  Проверять только с `VOID_QEMU_CPU=host`: у `qemu64` по умолчанию SMEP нет, и код просто не
  исполняется (сначала так и вышло — «проверка» соврала бы).
- ~~**У стека trap'ов нет сторожа**~~ → **ЕСТЬ (Веха 128)**: магия `TRAP_CANARY` в самом низу,
  сравнение на каждом возврате в процесс (в `resume`, то есть ПОСЛЕ работы этого trap'а —
  переполнение ловится тем же вызовом, который его допустил). Проверено намеренной порчей:
  `[PANIC] переполнение стека trap'ов ядра` с точным местом.
  Осталось **guard-страница** вместо магии: она ловит запись в тот же миг, а не на выходе. Стек
  лежит в окне образа, которое отображается постранично, — то есть страницу под ним можно
  сделать нечитаемой по-настоящему. Мешает одно: `TRAP_STACK` объявлен в ОБЩЕМ `proc.rs`, а
  правка отображения арх-специфична; аккуратный путь — своя секция в компоновщике (обоих) и
  символы её границ.
- **SMAP** (бит 21) — отдельная работа, не однобитная правка: ядро СОЗНАТЕЛЬНО читает память
  процессов напрямую (`SYS_WRITE`, `SYS_NET_SEND` и прочие), и каждое такое место потребует
  `stac`/`clac`. Взамен ловится «ядро случайно тронуло пользовательский указатель». Проверка
  флага `AC` в `hostile` уже стоит — она заметит, если SMAP включат, а `AC` останется не сброшен.
- **Вход в trap на riscv не разбирали.** Флага направления там нет, но сам вопрос («что вход
  предполагает и не устанавливает») на riscv никто не задавал. `hostile` на riscv пока проверяет
  только сохранность регистров.

## Устойчивость ядра и ресурсы (аудит перед Фазой 6, 2026-07 → **Веха 89, закрыто**)

Отдельный раздел: это были не «фичи», а **вещи, которые работали только потому, что нагрузки нет**.
С сетью и пакетами каждая превратилась бы в невоспроизводимое падение. Веха 89 закрыла все пять.

- ~~Замки не IRQ-safe~~ → **`SpinLock::lock_irq()`**: глушит прерывания ДО захвата и
  восстанавливает ПРЕЖНЕЕ состояние на drop. Переведены все замки, достижимые из обработчика
  (`ASYNC`, `EXECUTOR`, `SCHED`, кольцо консоли riscv, `XHCI` внутри `console_drain`, куча ядра);
  список — в преамбуле `sync.rs`. В `yield_now` намеренно остался обычный `lock()`: прерывания там
  выключены шире замка, до самого переключения контекста.
- ~~Store не проверяет то, на чём стоит весь тезис~~ → **хэш сверяется** с content-id при каждой
  загрузке с диска, результаты `io.read`/`io.write` больше не игнорируются, коммит атомарен
  (отметки «на диске» — только после успеха всех записей, откат при сбое индекса/суперблока).
  Сверх плана — **самоизлечение**: кадр программы-семени восстанавливается из образа ядра
  (`Store::repair`, по требованию в точке отказа). Пользовательские данные восстановить неоткуда —
  их порча только обнаруживается (`corrupt_reads`).
- ~~Ёмкость носителя неизвестна~~ → **`BlockIo::capacity()`**, коммит считает секторы до первой
  записи. Попутно закрыта смежная дыра: `compact` не запускает фазу 2, если фаза 1 не прошла
  (иначе затирались бы кадры, на которые ещё указывает активный суперблок).
- ~~Нет политики нехватки ресурсов~~ → `map`/`clone_kernel_root` фаллибельны, процессные пути
  отказывают вместо паники ядра (загрузочные остались `assert!` — там памяти всегда хватает).
  Появилась **квота страниц на группу нитей** (четверть рабочей RAM, не меньше 8 МиБ).
- ~~Слоты процессов не переиспользуются~~ → утилизированная группа отдаёт номера в список
  свободных; предварительно `cap::revoke_process` отзывает Endpoint/Reply на этот номер, иначе
  устаревший cap адресовал бы чужой новый процесс.
- ~~У ядерных задач нет guard page~~ → **сторож стека** (магия внизу, проверка на каждом
  переключении). Настоящую guard-страницу не поставить: стек берётся из кучи, а она лежит в
  direct-map, застеленной huge/гигастраницами.
- ~~Аллокатор vvsh — bump с пустым `dealloc`~~ → адресно-упорядоченный **свободный список со
  слиянием** соседей (схема кучи ядра).

Осталось в этом разделе:

- **Сигналов нет.** `SYS_KILL` есть с Вехи 103 (право из РОДИТЕЛЬСТВА: снять можно своего
  ребёнка, чужой процесс неприкосновенен) — этим и живёт мультиплексор, закрывая панель. Чего
  по-прежнему нет: сигналов, `Ctrl-C` как прерывания программы (в vvsh он отменяет лишь набор
  строки) и снятия СЕРВИСА силами init. *(Запись до Вехи 114 утверждала, что убить процесс
  нельзя вовсе, — и противоречила соседнему разделу того же файла. Проверено по коду.)*
- **Заглушки linux-abi, возвращающие успех.** `rt_sigaction`/`rt_sigprocmask`/`close`/`fcntl` → 0,
  `munmap` → 0 (bump-куча не освобождает). Для applet'ов сойдёт, для настоящих пакетов — нет.
  ~~`nanosleep`/`clock_nanosleep` → 0 без сна~~ → **ЧЕСТНЫЕ (Веха 114)**: спят по-настоящему,
  через тот же механизм срока, что `futex_wait`; понимают и абсолютный срок (`TIMER_ABSTIME`).
  Появился и свой `SYS_SLEEP(ns)` — до него ЛЮБАЯ программа VOID «ждала» круговым `yield`.
- **Гранулярность аллокатора фреймов.** Bump + список свободных 4-КиБ фреймов; крупные непрерывные
  блоки (`reserve`) берутся только внутри ОДНОГО региона карты памяти и теряют его хвост.

## Стартовые права ПОЗИЦИОННЫ — ловушка, которая уже сработала

Программа берёт свои права по НОМЕРУ (`start_cap(0)` — файловый сервер, `start_cap(1)` — store).
Порядок задаёт строка конфига, дети наследуют его как есть. Достаточно переставить токены — и
`vvsh` принимает фреймбуфер за файловый сервер: `ls` роняет шелл, `run` ничего не запускает.
Ровно это и случилось на X54C (Веха 99.1): в сторе лежало поколение со старым порядком, а
конфиг переживает обновление ядра.

**ЗАКРЫТО (Веха 99.2).** init кладёт ИМЕНА прав в окружение (`CAP_POSIXFS`, `CAP_STORE`,
`CAP_FB`, `CAP_NET_SRV` — тем же приёмом, что `STDIO=<i>`), а `term` и `vvsh` ищут по имени с
откатом на прежнюю позицию (старые конфиги без имён продолжают работать).
Первая попытка перевести `vvsh` сломала шелл: `cap_named` разбирает окружение и звался из
горячих путей. Лечение — **резолвить один раз на старте** в статики; так и сделано.
Проверено в обоих поколениях: gen3 (панель — `ls`, `run install`, `date`) и gen1 (`resolve
example.com` → адрес, `roots` → корни store).

## Оконный режим — долги после первых дней работы (2026-08-10, владелец)

Всё ниже — НЕ критично: система работает, ими можно жить. Записано, чтобы не разбираться заново.

- ~~**В окне не работают стрелки, Home/End, PageUp**~~ → **ЗАКРЫТО Вехой 127**. Диагноз был верен:
  событие клавиши окна возило ОДИН БАЙТ готового ASCII, а у стрелок и PageUp ASCII нет вовсе.
  Теперь `EV_KEY` несёт `sym` + маску модификаторов + кодовую точку (`[3, sym u16, mods u8,
  ch u16, нажата u8]`), и `wm` больше не выбрасывает клавиши без символа. `term` получает
  структуру НАПРЯМУЮ, минуя разбор escape-кодов: у него и так было внутреннее событие
  (`KeyEvent { keysym, mods, text }`), просто ему давали только байты. Проверено на живой
  системе: в окне `helZlo` собирается стрелками, Home/End работают, `Ctrl+S`/`Ctrl+Q` доходят.
  Отпускания клавиш по-прежнему не отдаём, и это осознанно (см. `win.rs`): аккорд перехватывает
  нажатие, и окно получило бы отпускание клавиши, нажатия которой не видело.
  Осталось: `Shift+PageUp` для прокрутки панелей в окне не действует НЕ поэтому — в окне схема
  панелей намеренно не применяется (`mux = false`), иначе префикс мультиплексора съедал бы
  аккорды, адресованные шеллу.
- **Вывод по-прежнему небыстрый** — не только `help`, но и `ls`, `cat`, работа в `ved`. Веха
  120.3 убрала главный расход (пересылку всего окна при прокрутке: 136 → 32 МБ за сеанс), но
  осталось: каждая изменившаяся строка едет объектом store с хэшем BLAKE3, глифы растеризуются
  заново на каждую перерисовку строки. Настоящее лечение — разделяемая память вместо объектов
  (записано отдельным долгом) и кэш глифов.
- **Мерцает ЗАГОЛОВОК окна при перетаскивании.** Строки экрана собираются в памяти и пишутся раз
  (Веха 120.3), но текст заголовка рисуется глифами ПОВЕРХ собранной строки — то есть эти пиксели
  всё ещё пишутся дважды. Лечение — держать готовую полосу заголовка картинкой и вклеивать её в
  строку наравне с содержимым. Владелец: не чинить, декорации всё равно будут переделаны под
  niri+noctalia.
- **Первые 2–4 секунды после старта система вялая** (и в `gen3`, и в `gen4`). Не разобрано.
  Общее у поколений — запуск `term`; кандидаты: поиск шрифта по установленным пакетам (обход
  каталогов через posixfs — десятки round trip) и сброс store на диск после загрузочных записей
  (на флешке запись медленная). Нужен замер, а не догадка.

## Экран и глифы (открыто 2026-08, [[0014-terminal-ereb]])

- ~~**Вывод ядра на машине без COM-порта пропадал совсем**~~ → **ЗАКРЫТО (Веха 116,

- ~~**Потолок 256 глифов**~~ / ~~**пиксельного фреймбуфера нет**~~ → **СНЯТО Вехой 96**
  ([[framebuffer]]): тег-запрос в заголовке multiboot2 + разбор инфо-тега 8, консоль рисует

  режимы не поддержаны.

  остаётся долгом; проверять её надо на живой сети, а не в QEMU.

  128 КиБ**: раньше мегабайтный файл молча приезжал обрезанным, теперь `open` честно отказывает.

- ~~**`SYS_OBJ_LIST_ROOTS` молча обрезал список корней**~~ → **ЗАКРЫТО (Веха 107,
  [[pkg-closure]])**: отдавал `min(длина, буфер)` — и «корней ровно столько» было не отличить от

  отдать», а `roots::text` растит буфер и **отказывается отдавать частичный список**. Спасательный
  vsh кучи не имеет — он говорит об обрезании вслух.

## Предупреждения компилятора в программах никем не читаются (2026-08-10)

Программы `programs/user` собираются **внутри `build.rs` ядра** отдельным вызовом cargo, и его
вывод глушится: при обычной `cargo build` предупреждений userspace не видно вовсе. Обнаружено на
Вехе 127 — в `term.rs` нашлись `subdirs` без единого вызова и лишнее присваивание `redraw`,
висевшие там задолго до правки и просто никем не прочитанные.

Само по себе не критично, но так копится гниль: мёртвый код и подозрительные места накапливаются
незамеченными ровно потому, что о них некому сказать. Проверять руками:

```
nix-shell --run 'cd Code/programs/user && cargo build --release --target x86_64-unknown-none'
```

Лечение — пробросить вывод дочернего cargo наружу (или хотя бы падать на новых предупреждениях в
проверочной сборке). Пока — помнить и заглядывать этой командой.

## atl1c: карта забирает дескрипторы, а на проводе пусто (открыто 2026-08-12)

Состояние на конец Вехи 134: неизменённый драйвер Linux поднимает AR8151 на живом X54C
полностью — probe, кольца на честном DMA, `ndo_open` возвращает 0, линк 1000 Мбит/с полный
дуплекс, `MAC_CTRL` показывает TX и RX включёнными. Кадры отдаются драйверу без отказов, и
**указатель карты в кольце передачи догоняет наш** (`мы 11, карта 11`) — то есть дескрипторы она
разбирает.

Но `tcpdump` на соседней машине (прямой кабель, интерфейс поднят) не видит НИ ОДНОГО кадра —
даже мусорного. Значит карта дескрипторы обрабатывает, а в провод ничего не кладёт.

Что уже исключено:
- передатчик выключен — нет, `MAC_CTRL` с `TX_EN` (это была отдельная ошибка, чинилась ожиданием
  линка перед `ndo_open`);
- кадр не отдан драйверу — нет, `ndo_start_xmit` возвращает `NETDEV_TX_OK`;
- тихий выброс по ошибке отображения памяти — нет, все классы сообщений драйвера включены, и
  «tx-skb dropped due to dma error» не появлялось;
- редкость вместо тишины — считалось: при вещании раз в 200 мс кадры шли бы каждые несколько
  секунд, тридцати секунд `tcpdump` хватило бы.

Куда смотреть дальше: содержимое дескриптора (длина, флаги, физический адрес буфера) и то, что
карта считает о своей передаче — её собственные счётчики в регистрах статистики
(`atl1c_update_hw_stats`, зовётся `ndo_get_stats`, у нас не звался ни разу). Проверять придётся
на железе: AR8151 в QEMU не эмулируется.

**Отдельно: вещание журнала в провод из этой отладки УБРАНО и возвращаться в прежнем виде не
должно.** Журнал уходил широковещательно, то есть любому на сегменте, и включался сам, без права
в конфиге. На прямом кабеле это терпимо, в роутере — утечка журнала ядра всей сети. Понадобится
удалённый журнал — делать адресно, под явным правом поколения и выключенным по умолчанию.

## ~~Консоль отвечает на serial ровно ОДИН раз~~ — ПОЧИНЕНО 2026-08-16 (Веха 139.2)

Дефект был найден на Вехе 138 и записан здесь с диагнозом «наполовину»; вторая половина оказалась
неверной, поэтому запись оставлена целиком — как напоминание, куда смотреть не надо.

**Симптом.** Без сети консоль отвечала на serial ровно один раз и глохла навсегда. С сетью
работала, но с задержкой ~600 мс на нажатие — на глаз «система задумывается», и владелец это
заметил первым, гоняя `vvsh` через `tools/run.sh`.

**Куда я смотрел зря.** На 16550 и на IOAPIC: подозревались IER, маска линии, EOI. Всё это было
настроено правильно — зонд показал RTE `vec=33, edge, active-hi, не замаскирован`, PIC заглушён,
IER=0x01, MCR с OUT2, а журнал прерываний QEMU (`-d int`) подтвердил, что вектор 0x21
доставляется. Настоящий ответ дал `info lapic`: **вектор 33 висит в IRR, ISR пуст** — прерывание
доставлено, но процессор его не берёт. Значит спим с закрытыми прерываниями.

**Настоящая причина.** Очередь событий клавиатуры и мыши (`SYS_KEY_READ`/`SYS_MOUSE_READ`) читает
ТОЛЬКО владелец экрана. В текстовом режиме (`vsh`/`vvsh` в консоли ядра) владельца нет вовсе — а
класть события туда ядро продолжало: с Вехи 119 каждый байт с serial становится ещё и событием
клавиши. Первое же нажатие наполняло очередь, и `key_pending()` оставался истинным НАВСЕГДА. А он
был условием выхода из сна в `wait_stdin`: цикл `sti; hlt; cli` выходил немедленно, `run` тут же
звал `wait_stdin` снова — и простой превращался в холостой цикл с ВЫКЛЮЧЕННЫМИ прерываниями.
Прерывание консоли просто некуда было принять. С сетью ввод подбирался чужими пробуждениями
`net-srv` — отсюда ровно те 600 мс.

**Починка** (`proc.rs`, `wait_stdin`): событие ввода — повод проснуться, только если его ЕСТЬ КОМУ
взять (тот же набор процессов, который оно будит); а события, которые прочитать некому вовсе (нет
владельца экрана), выбрасываются. Замер до и после, одним и тем же стендом: было 600 мс с сетью и
«одно эхо из двенадцати» без сети — стало **1.1 мс в обоих случаях** (это гранулярность самого
замера, то есть задержки нет). Оконный режим проверен отдельно: клавиши и мышь работают, аккорды
тоже.

**Что из этого стоит запомнить.** «Правильно настроенный контроллер» и «прерывание доходит» — не
одно и то же. Вопрос «взял ли его процессор» задаётся ISR/IRR у LAPIC, и именно он экономит часы:
в контроллере всё было верно с самого начала.

## ~~Простой графической сессии жёг ЦЕЛОЕ ЯДРО~~ — ПОЧИНЕНО 2026-08-16 (Веха 139.3)

Найдено сразу за предыдущим и того же семейства — «ждём» на месте, а ожидания нет.

**Симптом, которого никто не видел.** На пустом экране, без сети и без единого нажатия, VOID
занимал **100% процессорного ядра** (замер: 9.98 с ЦП за 10 с простоя у процесса QEMU). Изнутри
это не проявлялось ничем: кадры рисуются по damage, поэтому лишние обороты цикла ничего не
портили — система просто грелась. На ноутбуке ([[target-system]]) это батарея и вентилятор.

**Причина — единицы времени.** Обёртки `recv_timeout`/`recv_console`/`recv_net` брали срок в
ТИКАХ, то есть в таймбазе архитектуры. `wm` писал `recv_console(&mut msg, 200)`, имея в виду
миллисекунды; на x86 `now_ticks` — это `rdtsc`, и 200 тактов означают **60 наносекунд**. Сон
вырождался в опрос. Ровно то же было в `term` (`5`/`200`). Единственным правильным местом
оказался `net-srv`: он один переводил миллисекунды в тики через `ns_to_ticks`, потому что
таймбазу ему пришлось узнать Вехой 136 — тогда чинили ход часов, и остальные вызовы не тронули.

**Починка**: срок в наносекундах у самих обёрток (как у `sleep_ns`), перевод — внутри, рядом с
границей ядра. Программе таймбаза не нужна и знать её незачем; пока знать было надо, двое из трёх
не знали. Замер тем же способом: **100% → 0.3%** простоя, окна, ввод, мышь и обои на месте.

**Урок**: единица измерения в имени параметра — не украшение. `timeout_ticks` читается как
«число», и оба реактора прочли его как миллисекунды; ошибка не даёт ни отказа, ни предупреждения
— только счётчик процессора, на который никто не смотрит.

## ~~Простой жёг ЦЕЛОЕ ЯДРО ПОСЛЕ ПЕРВОЙ КЛАВИШИ~~ — ПОЧИНЕНО 2026-08-17 (Веха 141)

Третий случай того же семейства за два дня — и он пережил починку Вехи 139.3, потому что
причина совсем другая, а симптом тот же.

**Симптом.** Свежая графическая сессия простаивает честно: 0.2% ядра. Стоит НАЖАТЬ ХОТЬ ОДНУ
КЛАВИШУ — и до конца сеанса 100%. Ни одно окно, ни один кадр, ни одно поведение при этом не
меняются; видно только счётчиком процессора снаружи гостя. Обнаружено случайно, при замере
простоя новых обоев ([[logo]]): закрыл последнее окно (`Super+Q`) — и получил 99.7% вместо
ожидаемых 0.3%.

**Причина — кольцо консоли, которое в оконном режиме не читает никто.** Клавиатура кладёт каждое
нажатие в ДВА кольца сразу: в очередь событий (`SYS_KEY_READ` — её читает композитор) и в
байтовое кольцо консоли (`SYS_READ`). В оконном режиме `SYS_READ` не зовёт никто: программы окон
говорят через stdio по IPC. Байты копились навсегда, а `console_has_input()` — условие ВЫХОДА из
сна в `wait_stdin`. После первого нажатия простой не наступал вовсе.

Это ЗЕРКАЛО ошибки [[known-gaps#Консоль отвечает на serial ровно ОДИН раз|Вехи 139.1]]: там
очередь событий копилась в ТЕКСТОВОМ режиме, где её никто не читает, и её уже научились
выбрасывать — но ровно тем же образом байты консоли копятся в ГРАФИЧЕСКОМ, и этого не заметили.

**Починка** (`proc.rs`, `wait_stdin`): бросать байты консоли, если их не читает НИКТО.

Первый признак «никто» был неверный, и владелец нашёл это за полдня: сперва условием стояло
«экраном владеет процесс», то есть «идёт графический сеанс». Но полноэкранный `term` (режим
`mode = "term"`) экраном тоже владеет — и байты консоли читает именно он. Байт мог прийти за миг
до захода в простой, ядро его выбрасывало, а `term` будило СОБЫТИЕ клавиши; тот шёл читать и не
находил ничего. Со стороны — **«система иногда съедает нажатия», и только в текстовом режиме**.

Правильный признак — наблюдаемый: процесс становится ЧИТАТЕЛЕМ консоли по факту первого
`SYS_READ` (поле `reads_console`). Композитор и его клиенты не зовут `SYS_READ` никогда (в окне
клавиши приходят событиями от `wm`), полноэкранный `term` зовёт с первого оборота. Спросить об
этом заранее не у кого — своего «я читаю консоль» в контракте процесса нет, и придумывать его
ради одного места не стоило.

Замер: **100% → 0.0%** в оконном режиме и **0.0%** в текстовом; в текстовом отдельно проверено,
что восемь букв, набранных с паузой в секунду (то есть каждая — после ухода в простой), доходят
все до одной.

**Заодно, по дороге.** Ближайший срок сна ядро искало у ВСЕХ процессов подряд
(`filter_map(|p| p.futex_deadline).min()`), а будило по сроку только три состояния — умерший со
сроком на руках оставил бы в таблице вечно истёкший срок и тот же вечный отказ спать. Оба конца
теперь спрашивают один предикат `sleeps_by_deadline`. В замере эта дыра не стреляла (счётчики
«с фильтром» и «без фильтра» совпали) — это страховка, а не причина.

**И вторая течь, найденная тем же опытом**: `term` при закрытии окна уходил, НЕ убивая свой шелл.
Терминал — единственный вход к этим процессам (их stdio ведёт в его эндпоинт), поэтому после
каждого закрытого окна в системе оставался живой, никому не видимый и ничего не могущий vvsh.
Теперь `term` убивает своих детей перед выходом — тем же `kill`, что и при закрытии панели.

**Урок тот же, что и в 139.3, но с другой стороны**: «кто-то положил событие» ≠ «кто-то его
заберёт». Каждый источник ввода надо проверять на ОБА режима — текстовый и оконный; в одном из
них у него читателя нет.

**И второй урок, из собственной ошибки:** «владеет экраном» — не то же самое, что «не читает
консоль». Признак, выведенный из соседнего свойства, ловит не тот случай; наблюдаемый признак
(«он читал») врать не может.

## ~~Паника программы была МОЛЧАЛИВОЙ~~ — ПОЧИНЕНО 2026-08-17 (Веха 143.1)

`#[panic_handler]` в `void_user` был `exit(101)` без единого слова. Любая паника любой программы
означала «процесс просто исчез»: для композитора это выглядело как «wm умер, паники нет, экран
вернулся ядру», и место падения приходилось искать чтением кода вместо чтения журнала.

Теперь обработчик печатает в КОНСОЛЬ ЯДРА имя программы (из `argv[0]`), файл, строку и сообщение:

```
  [паника] wm: src/bin/wm.rs:1669: index out of bounds: the len is 1280 but the index is 18446744073709551615
```

Именно эта строка и нашла ошибку Вехи 142.1 за один прогон (см. [[compositor-damage]]).

В консоль ядра, а не в stdio: хоста может не быть вовсе (композитор), а если есть — падать может
он сам. Буфер на стеке: куче в этот момент верить нельзя, да и у библиотеки её нет.

## Картинки (Веха 138, [[images]])

- **Аргумент клиенту композитора передать нечем**: конфиг поколения разбирается по пробелам, и

## ~~Шестидесяти кадров в секунду нет~~ — ПОЧИНЕНО 2026-08-18 (Веха 145.4)

Было (замер Вехи 145.3): движение идёт **50 кадрами в секунду**, и упирается это в две
независимые вещи.

- **Ядро пересыпало на 4 мс** — просили 6.6, спали 10.6: сон округлялся вверх до тика таймера.
  **Починено Вехой 145.4**: у арха появился `timer_arm_at(срок)` — TSC-deadline на x86 (или
  измеренный one-shot на машинах постарше), `sbi_set_timer` на riscv. Промах сна 4.06 → **0.07
  мс**, период кадра 20.0 → **16.1 мс (62 кадр/с)**. Разбор — [[traps-and-timer]].
- **Кадр стоит 8.8 мс** — ОСТАЁТСЯ. Это не арифметика, а память: полноэкранный кадр — 12 МБ
  трафика ([[cpu-budget]], «Что попробовали»). Лечится кэшем неподвижного фона, SMP или GPU —
  ничем из того, что делается одной строкой. Пока цел этот потолок, шестьдесят кадров держатся
  только потому, что 9 мс всё ещё меньше 16.

Две ловушки, на которые наступили по дороге, — обе про одно и то же:

1. **Пауза в главном цикле — не период кадра.** Она стоит после отрисовки и к ней прибавляется.
   «Поставим паузу 16 мс, будет 60 кадров» дало 39.
2. **Бюджет обязан ограничивать ОТРИСОВКУ, а не только сон.** Композитор рисовал каждое
   пробуждение, а будит его не только срок: запрос клиента, ответ бара, клавиша. Пока сон
   промахивался на 4 мс, лишние обороты в промахе тонули; с точным пробуждением на кадр стало
   приходиться по два лишних — 95 кадров в секунду ценой полутора расходов. То есть точность
   пробуждения без второго условия просто меняет одну беду на другую.

       доказаны, обе арх. Референс подхода собран в `reference/dde-linux/`.

       `time_after`/`msecs_to_jiffies`) + `linux/timer.h` (`timer_list`/`mod_timer`/`timer_delete`/

       сони чередуются, таймеры `2 3 1`, обе арх. **Оговорки:** (а) jiffies двигается в точках

       `complete`) — чем драйвер ждёт события железа (сброс/линк/DMA), уступая процессор. Поверх
       block/unblock: запись ждущего на стеке задачи, wake_up переводит в готовые (перепроверят
       условие сами — нет потерянных пробуждений в один-поток-модели); таймаут — через таймер Вехи 63.

       обе арх. Оговорка: воркер — демон, при остановке планировщика остаётся заблокированным (стек

       список/биты + err/io/delay + планировщик/таймеры/ожидание/workqueue).

       OK`, обе арх идентично. **Vendored e1000-код исполняется на VOID.**
     - ✅ **Портированный e1000 читает НАСТОЯЩИЙ QEMU-e1000 через MMIO-cap** (Веха 69, [[lx-e1000-hw]]):
       тот же неизменённый `e1000_hw.c` спавнится init'ом как userspace-драйвер (путь Вех 51–54), маппит
       BAR0 по MMIO-cap (`vsys_mmio_map`, start_cap 0) в `hw->hw_addr` — и через `er32`/`ew32` сбрасывает

       Bring-up идёт как задача Lx_kit (vendored `msleep` уступает). `syscall.h` теперь ставится в void-libc;
       `init.rs` предпочитает `lx-e1000-hw`. Проверено (x86, `-device e1000,mac=…99`): `STATUS=0x80080783
       link UP`, `reset_hw`, `MAC=52:54:00:12:34:99` (совпал с заданным!), `speed=1000 duplex=full — OK`.
       Регрессии чисты (x86 без e1000 — `ping` ок; riscv — не спавнится). **Портированный драйвер трогает
       реальное железо.**
     - ✅ **Портированный e1000 ПЕРЕДАЁТ кадр (DMA-TX)** (Веха 70, [[lx-e1000-tx]]): `dma_alloc_coherent`
       в `lx_net.c` сведён с DMA-cap (`vsys_dma_alloc`, start_cap 1; guard `-DLX_HAVE_SYSCALL`). Драйвер
       строит TX-кольцо дескрипторов vendored `e1000_setup_all_tx_resources` на РЕАЛЬНОМ DMA, конфигурирует
       TX-движок (TDBAL/TDLEN/TCTL/TIPG вручную — `e1000_configure_tx` static) и передаёт 60-байтовый кадр:
       дескриптор → TDT → карта выносит его DMA'ом, ставит DD-бит. Проверено (x86): `setup_all_tx_resources
       → ring dma=0x13e3000` (реальный физ-адрес), `TX: desc0.status=0x01 DD=1 TDH=1 — OK`. Первое
       использование DMA-cap портированным Linux-драйвером. Регрессии чисты; ядро не менялось.
     - ✅ **Портированный e1000: TX+RX (ARP round-trip)** (Веха 71, [[lx-e1000-rx]]): добавлено RX-кольцо

       `RAL0`=наш MAC). Драйвер шлёт **ARP-запрос** шлюзу (TX) и **принимает ARP-ответ** (RX, опрос
       DD-дескриптора) — двунаправленный реальный трафик через портированный драйвер. Проверено (x86):
       `TX ARP «who has 10.0.2.2» → DD=1`, `RX: дескриптор 0 DD, 64 Б, ethertype=0806`, `ARP-ОТВЕТ от
       10.0.2.2: MAC шлюза 52:55:0a:00:02:02 — OK` (штатный SLIRP-шлюз — ответ реально пришёл). Регрессии
       чисты; ядро не менялось.
     - ✅ **RX по прерыванию** (Веха 72, [[lx-e1000-irq]]): `request_irq` вшит в idle-путь
