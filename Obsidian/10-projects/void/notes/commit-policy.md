# Политика коммитов store

Вопрос (после Вехи 25): персистентный store коммитит часто — не сожжём ли SSD?
Разбор показал: **опасен не объём данных, а две привычки** сегодняшней реализации.
На QEMU-образе это безразлично; до реального железа — обязательный рефакторинг.

## Что пишет один `commit()` сегодня (object.rs)

1. Только **новые** объекты (append-only) — неизменённые не перезаписываются никогда;
2. roots-blob (новый объект при каждой смене корней);
3. **весь индекс целиком** в неактивный A/B-регион;
4. суперблок (1 сектор, LBA 0) — атомарная точка коммита.

И вызывается он **на каждую операцию**: `OBJ_SET_ROOT`/`OBJ_DEL_ROOT` (proc),
каждая передача capability (`cap::persist`). `echo hi > file` в vsh = два коммита
(корень файла + `.dir`). Плюс GC на каждом boot сбрасывает дисковые адреса выживших →
первый commit после него переписывает всю живую область (уплотнение).

## Две настоящие проблемы масштабирования

- **Частота**: чекпойнт-на-каждый-чих = fsync-на-каждую-запись наивной БД. Даже
  1-байтовое изменение = 3–5 секторов, а NAND-страница (4–16 КиБ) сгорает целиком.
- **Полная перезапись индекса растёт со store**: 24 объекта = 3 сектора (смешно),
  миллион объектов = **64 МиБ на каждый echo** (вот и «убийца SSD»).

НЕ проблема: горячие LBA (суперблок, A/B) — FTL внутри SSD/eMMC сам размазывает
записи по ячейкам (wear-leveling). Стало бы проблемой только на сыром NAND / дешёвых SD.

## Почему архитектура при этом SSD-дружелюбная

- **Контент-адресация = write-once**: объект с данным хэшем пишется один раз за жизнь,
  дедуп бесплатен (Nix-store на SSD живёт годами именно так).
- **Append-only** = последовательная запись — идеальный паттерн для FTL.
- Структурное разделение деревьев (как git): изменил лист — пишутся лист и путь до
  корня, не всё дерево.

## Лекарства (все — штатные, из нашей же родословной)

1. **Group commit**: `set_root`/`persist` помечают store грязным, коммитит таймер/порог.
   KeyKOS чекпойнтил раз в минуты, ext4-журнал — раз в 5 с. A/B-индекс уже гарантирует
   консистентность при крахе — теряется только окно в секунды.
2. **Индекс как объект store**: суперблок указывает на *хэш корня индекса*, дельты
   дописываются как объекты; полная перезапись — только при уплотнении. Идиоматично
   для VOID: индекс становится частью объектного графа.
3. **Уплотнение по порогу мусора** (LSM-подход), а не при каждом GC/boot.

Ориентир: бытовой SSD — 300–600 TBW, Linux-десктоп пишет 10–50 ГБ/день (30+ лет).
VOID с group commit будет писать *меньше* классической ФС (нет записей на месте,
нет журнала поверх данных); без него — обогнал бы на порядки.
