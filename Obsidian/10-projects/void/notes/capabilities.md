# Веха 8 — capability

Вторая половина модели KeyKOS/EROS из [[0002-persistent-content-addressed-capability-core|ADR 0002]].
Первая половина — [[object-model|объектная модель]] + [[persistent-store|персистентность]] («ОС не
забывает»). Теперь — **кто что может трогать** в этом едином пространстве, без UID и файловых прав.

## Идея: право = ссылка
В обычной ОС «может ли процесс тронуть X» решается таблицей прав вне объекта (UID, режим файла,
ACL). В capability-модели **обладание ссылкой на объект И ЕСТЬ право на него**. Нет ссылки — нет
доступа; нельзя «спросить у ядра доступ к чужому объекту по имени» — имя ничего не даёт без
capability. Это устраняет проблему «спутанного заместителя» (confused deputy) и делает права
композируемыми.

## Что на что указывает
Capability целится в один из двух видов объектов (см. [[object-model]]):
- **`Value(ContentId)`** — неизменяемое значение. По природе только чтение.
- **`Root(name)`** — изменяемая ячейка. `WRITE` переустанавливает её на новое значение;
  сами байты неизменяемы, поэтому «запись» двигает *ячейку*, а история версий остаётся.

Права (`void-abi::Rights`, битовая маска): `READ`, `WRITE`, `GRANT`.

> На [[ipc-endpoints|Вехе 12]] цели расширены на **`Endpoint(pid)`** (IPC-сервер) и
> **`Device(Block)`** (устройство), добавлено право **`SEND`** (вызвать эндпоинт). Так capability
> связались с [[processes|процессами]]: доступ к серверу и к железу — только по дескриптору.

## Три свойства = три механизма
| Свойство | Механизм в коде |
|---|---|
| **Неподделываемость** | `Cap` — это дескриптор `(слот, поколение)` в c-space домена, а не сам объект. Любой доступ идёт через `resolve()`, который сверяет дескриптор с таблицей. Выдуманное число → нет слота/не то поколение → отказ. |
| **Наименьшая привилегия (аттенуация)** | `grant(from, cap, to, mask)` даёт права `исходные ∩ mask`. Пересечение может только **сузить** — расширить право передачей нельзя. |
| **Отзыв (revocation)** | `revoke()` освобождает слот и увеличивает его **поколение**. Все ранее выданные дескрипторы на этот слот перестают совпадать → `Stale` (generational handle). |

Почему дескриптор, а не указатель: в едином адресном пространстве ядро доверенно, но модель
готовит границу с userspace (Веха 10) — там userspace будет видеть только непрозрачное число, а
ядро валидировать его по c-space. Тот же механизм работает уже сейчас.

## Модули
- **`void-abi`**: `Rights` (маска + `contains`/`intersect`/`union`/`is_subset_of`) и `Cap`
  (`new(slot, gen)` / `slot()` / `generation()` — непрозрачный дескриптор).
- **`kernel/src/cap.rs`** — c-space и операции:
  - `create_domain(name) -> DomainId` — домен защиты (протопроцесс) со своей таблицей прав.
  - `mint(dom, target, rights) -> Cap` — привилегированное создание capability (при владении).
  - `read(dom, cap, f)` — прочитать значение/ячейку (нужен `READ`); замок c-space отпускается
    перед обращением к [[object-model|store]], чтобы не вкладывать блокировки.
  - `write_root(dom, cap, new_value)` — переустановить ячейку (нужен `WRITE`, цель `Root`).
  - `grant(from, cap, to, mask) -> Cap` — передать в другой домен с аттенуацией (нужен `GRANT`).
  - `revoke(dom, cap)` — отозвать (поколение++).
  - `rights` / `domain_name` — интроспекция.

## Проверка (вывод в QEMU)
```
[cap] capability — неподделываемость · аттенуация · отзыв:
  kernel минтит cap->'demo-cell' [rwg]
  grant -> app с маской [r--] → фактически [r--]  (расширить нельзя)
  app читает ячейку: "demo: version 0"
  app write отклонён: Denied  ← нет права WRITE
  app grant отклонён: Denied  ← нет права GRANT
  kernel пишет v1, читает: "demo: version 1 (owner-written)"
  cap на значение v0: "demo: version 0"  (значения неизменяемы → только чтение)
  подделанный cap отвергнут: Invalid  ← неподделываемость
  cap после отзыва: Stale  ← revocation
```
Каждая строка — одно свойство. Домен `app` может ровно то, что ему передали (чтение), и ничего
сверх; выдуманный и отозванный дескрипторы отвергаются таблицей.

## Осознанные упрощения (чиним позже)
- **C-space в RAM, не персистентен.** По ADR 0002 capability должны переживать перезагрузку
  (иначе теряются права) — как объектная модель была в RAM на Вехе 6 до [[persistent-store]].
  Следующий шаг: сложить c-space в store и коммитить вместе с объектами.
- **Отзыв только своего дескриптора.** Настоящий транзитивный отзыв (все копии, кому передавали)
  требует дерева выдач или косвенности; здесь поколение инвалидирует лишь дескрипторы *этого*
  слота.
- **Минт привилегирован и делается ядром.** В полной модели право минта само выражается
  capability (кто владеет объектом — тот минтит).
- **Домены заведены вручную в демо.** Реальные домены появятся с userspace/процессами (Веха 10),
  где c-space станет частью процесса, а `grant` пойдёт **через IPC**.

## Что это закрывает
Стержень из ADR 0002 собран целиком: **персистентные + контент-адресуемые + capability-защищённые**
объекты. Ингредиенты держат друг друга — персистентность даёт долговечность, контент-адресация даёт
безопасность, capability дают права. Дальше — не новые кирпичи стержня, а как на нём *исполнять*:
[[scheduling|планировщик]] как async-задачи над этим пространством (Веха 9), затем выход в userspace.
