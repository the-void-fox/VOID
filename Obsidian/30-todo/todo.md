**Шрифт из бинаря в store** упирается в тот же потолок, что нашёл замер (объект в 2.6 МБ пройдёт,

  теряла байты ИЗ СЕРЕДИНЫ (на riscv из 700 символов пропало 36 — выглядело как опечатка
  человека). Кольцо тоже 1 КиБ, переполнение печатается при чтении (`[tty] потеряно N байт`).

- [→] **Шрифт из бинаря в store — ОТЛОЖЕН в пакетную фазу.** 2.6 МБ в ELF: уронили посев на riscv

- [x] **Фокусная рамка у панели, прижатой к краю — СДЕЛАНО (Веха 101).** Помечаются все четыре
  стороны, где зазор есть (кроме строки статус-бара), а не только левая и верхняя.
- [x] **Замер кучи ядра — СДЕЛАН (Веха 101), и ответ жёсткий.** Инструмент — команда
  `store-probe [МиБ]` в vvsh (кладёт объекты по 64 КиБ с разным содержимым и считает, сколько
  прошло). Результат на 512 МиБ RAM:
  **8 МиБ одной пачкой проходят, 16 МиБ — ПАНИКА ЯДРА** (`memory allocation of 65536 bytes
  failed`), не отказ. С паузами (шелл успевает уснуть) 8+8 МиБ проходят.
  Диагноз: **store держит в RAM ВСЁ, что положено за сессию**. Коммит пишет кадры на диск, но
  `data` в кэше не освобождает, поэтому потолок — вся куча ядра (16 МиБ), а не «несинхронизи-
  рованное». Плюс политика group commit **не считала put'ы вовсе** — счётчик рос только на смене
  корней, и программа, льющая объекты подряд, не давала ей ни одного повода сработать (починено:
  новый объект — тоже грязная операция; в замере видно, что коммиты пошли).
  **Для Фазы 8 это предпосылка, а не мелочь:** распаковка NAR в десятки мегабайт сегодня роняет
  машину. Нужны две вещи — (а) ВЫТЕСНЕНИЕ из кэша после коммита (объект уже на диске, `data`
  можно отпустить: ленивая подгрузка `ensure_loaded` есть), (б) исчерпание кучи ядра как ОШИБКА,
  а не паника. Обе — первым шагом пакетной фазы.
- [ ] **Двойное копирование ELF при `exec`** — вторая половина того же риска, не замерена.
- [x] **Потолок 8 МиБ на файл — СНЯТ (Веха 101).** Список кусков в `fetch` был фиксированным
  массивом на 512 записей; теперь 8192 (× 16 КиБ = 128 МиБ файла, 256 КиБ списка). Дерева
  поглубже не понадобилось: узел спокойно держит тысячи ссылок.
  **Но связывающим стал другой потолок** — сколько store принимает за сессию (см. замер выше):
  сегодня это ~8–16 МиБ, и упирается он в кучу ЯДРА, а не в формат.
- [x] **Выключение машины — СДЕЛАНО (Веха 101).** `poweroff` в обоих шеллах, `exit` в `vsh` и
  выход из `term` — тоже; под правом `power` из конфига (`Target::Power`). x86 — настоящий ACPI

  остаются сервисы; (б) чтение таблиц ACPI падало в page fault — direct-map не покрывал память
  типа «ACPI reclaim», теперь тянется на 64 МиБ выше RAM.
  **Оговорка:** `gen1`/`gen2` на уже установленных машинах без `power` — там `exit` как раньше,
  до `rebuild`.

# VOID — staged роадмап

Принцип: радикальные идеи включаются по одной, **каждая за работающей вехой** — чтобы всегда
было что-то живое в QEMU, а не вечная стройка. Первые ~5 слоёв одинаковы для любого ядра и не
зависят от стержневого тезиса ([[0002-persistent-content-addressed-capability-core]]) — это
чистое «понять, как всё работает». Радикальное начинается со слоя памяти/хранилища.

## Фаза 0 — фундамент (от железа вверх)
- [x] **Веха 1.** Boot: OpenSBI → entry asm → стек → `kmain`; вывод в UART (NS16550).
- [x] **Веха 2.** Trap/прерывания: обработчик исключений (ebreak), таймерные прерывания (S-mode), дамп регистров при фатале. См. [[traps-and-timer]].
- [x] **Веха 3.** Виртуальная память: Sv39-пагинг, direct map RAM + W^X ядра, переход на трансляцию. См. [[sv39-paging]].
- [x] **Веха 4.** Kernel heap: free-list аллокатор + `#[global_allocator]`, арена из `frame::reserve`, `alloc` работает. См. [[kernel-heap]], [[memory-regions]].
- [x] **Веха 5.** Многозадачность: контексты + кооперативный round-robin планировщик. См. [[scheduling]].
- [x] **Веха 5.5.** Вытеснение (preemption) по таймеру: переключение из trap'а, состояние прерываний на задачу, атомарный вывод. См. [[scheduling]].

- [x] **Веха 7.1.** Драйвер virtio-blk: чтение/запись секторов (virtio-mmio, split virtqueue, опрос). См. [[virtio-blk]].
- [x] **Веха 7.2.** Персистентный store: суперблок + A/B индекс + append-only объекты; корень переживает перезагрузку. См. [[persistent-store]].

- [x] **Веха 17.** `BLK_WRITE`: шлюз записи сектора под правом `WRITE` на устройство; блок-протокол кодирует сектор+флаг записи в `op`. Клиент пишет и читает сектор обратно через сервер. См. [[block-driver]].

## Фаза 3 — самостоятельность (см. [[0003-phase-3-exec-by-hash]])
Центральный примитив фазы: **программа = контент-адресуемый объект, exec по ContentId** — как derivation в Nix, прямое следствие ADR 0002.
- [x] **Веха 19.** Программа как объект store: ELF-крейт `programs/hello` → байты в store под корнем `bin/hello` → минимальный ELF-загрузчик (PT_LOAD, W^X) → `spawn_elf` по ContentId; на втором запуске ELF грузится с диска. См. [[exec-from-store]].
- [x] **Веха 20.** UART-ввод по прерыванию (кольцевой буфер, вычерпывание на тиках) + `SYS_READ`/`SYS_EXEC` (право `EXEC`, foreground-ожидание) + интерактивный `vsh`: `ls`/`cat`/`echo > f`/`run bin/hello`/`exit`; смена корня из userspace = атомарный чекпойнт. См. [[interactive-shell]].
- [x] **Веха 21.** Cap-transfer по IPC (grant-в-сообщении, право GRANT; `CAP_DERIVE` — аттенуация) + персистентный c-space (`.cspace` в store, чекпойнт на каждую передачу, restore с точными поколениями) — capability переживают перезагрузку, тезис ADR 0002 полный. См. [[ipc-cap-transfer]].
- [x] **Веха 22.** Куча процесса (`SYS_MAP`, ленивые страницы, доотображение под шлюзы); user page fault убивает процесс, а не ядро; лимиты POSIX-персоналии сняты (16 файлов × 4 КиБ, метаданные в куче). См. [[process-heap]].

> **Фаза 3 закрыта:** система самостоятельна — программы загружаются из store по content-id,
> есть живой shell с вводом, capability передаются по IPC и переживают перезагрузку вместе с
> c-space, у процессов настоящая ленивая память и честные фолты.

- [x] **Веха 37 — checkpoint процессов — закрыта** ([[checkpoint]], наследие KeyKOS): вычисления переживают перезагрузку. `SYS_CHECKPOINT` (28, право WRITE) — процесс морозит СЕБЯ: страницы пространства → объекты store (дедуп: нулевые страницы стека схлопываются в один), манифест (кадр+heap_brk+args/env+таблица RWX-страниц) → node-объект, страницы — его дети (GC держит образ деревом от корня `proc/<arch>/<имя>`), коммит синхронный. Семантика setjmp: живому 0, размороженному 1. `SYS_RESTORE` (29, право EXEC, vsh `thaw`) — как exec: ждём код выхода; args/env из образа, старт-права — свежее наследство (капабилити сознательно НЕ консервируются). Контракт arch: `page_info` (VA→PA+MAP-флаги); thaw отвергает W+X и адреса вне региона (образу извне не доверяем). Демо `bin/freeze`: цикл с чекпойнтом на шаге 5 — «Я РАЗМОРОЖЕН: продолжаю с шага 5, куча цела ✓» ПОСЛЕ перезагрузки QEMU, итог 385, обе архитектуры, образы двух арх на одном диске. Отложено: многонитевые образы, заморозка чужого/заблокированного, глобальный периодический чекпойнт.

- [x] **Веха 38 — linux-abi (бэкенд B) — закрыта** ([[linux-abi]], исследовательская магистраль [[void-pkg]]): неизменённые static-PIE musl-бинари из кэша nixpkgs работают на VOID под персоналией Linux — трансля́тор Linux-syscall'ов **в ядре** (путь linuxulator). Ключевое: static-PIE (`ET_DYN`, `-static-pie`), а не ET_EXEC@0x400000 (тот на riscv течёт в общие подтаблицы, на x86 — внутрь образа ядра); musl `rcrt1` само-релоцируется, ядро лишь строит стартовый стек с **auxv**. Ни одной новой инструкции: riscv `ecall` общий с VOID (разводит `Proc.linux`), x86 `syscall` при EFER.SCE=0 даёт **#UD** → ловим вектор 6, `rip+=2` (без MSR/стаба). `brk`/`mmap(anon)` поверх ленивой кучи (Веха 22). Демо на ОБЕИХ архитектурах: `hello` (UTF-8 argv, exit-код) и **busybox 1.37** (`echo`/`uname -a`/`true`/`seq`/`printf`/`basename` — один бинарь, мультиплекс по argv). Отложено: файловые applet'ы (`cat FILE`/`ls`/`sh` — нужен мост к posixfs), clone/futex/сигналы. Грабли: cc-wrapper `-pie` ломает `ld -r` busybox'а (`NIX_HARDENING_ENABLE=""` + патч `ld_flags`), riscv-defconfig тянет x86-only SHA-NI.

- [x] **Веха 39 — WASI (бэкенд C) — закрыта** ([[wasi]], последний из трёх бэкендов [[void-pkg]]): неизменённые wasm32-wasi-модули работают через интерпретатор **wasmi** — тот же .wasm на ОБЕИХ архитектурах без пересборки. Микроядерно чисто: `bin/wasirun` — ОБЫЧНАЯ std-программа (тулчейн void, крейт wasmi 0.36 no_std), ядро не тронуто. Читает .wasm как файл (`std::fs` → posixfs), даёт импорты `wasi_snapshot_preview1` (fd_write→SYS_WRITE, proc_exit→SYS_EXIT, args из `std::env::args`). Демо: `run bin/wasirun hello.wasm` печатает из wasm-гостя, argv, exit-код — обе арх. Подпорки: posixfs 4 КиБ→128 КиБ (wasm 63 КБ не влезал), std-арена 16→64 МиБ (wasmi тесно). **Все три бэкенда ADR 0004 закрыты**: A (nixpkgs-cross), B (linux-abi), C (wasi) — `run` в vsh запускает четыре мира с одного диска (родной VOID-ELF, static-PIE musl, busybox, wasm).

- [x] **Веха 40 — декларативный init — закрыта** ([[declarative-init]], первая «фишка NixOS поверх родного фундамента» [[0004-void-pkg]]): система поднимается по КОНФИГУ-объекту из store, а не по зашитому `shell_session`. Конфиг — текст (`service NAME store:rw` / `shell vsh endpoint:posixfs store:xw env`); `init::apply` минтит права по токенам прямо в домены и разводит эндпоинты по именам сервисов — то, что раньше делал kmain руками, теперь из данных. Поколения = история корня, откат = смена `system/current`: vsh `switch GEN` + ребут грузит другую конфигурацию (gen1 полное / gen2 без сети — `ping` наглядно «сети нет»), и назад. Модель NixOS честно: язык Nix НЕ в рантайме — `nix/system.nix` вычисляет конфиг на ХОСТЕ (`nix eval` → мост → `system/gen3`), VOID грузит результат. Конфиг арх-нейтрален (init резолвит `bin/<arch>/*`) — один `system/*` на обе архитектуры. vsh `sysdef GEN FILE` регистрирует файл как поколение.

- [x] **Веха 41 — платформа: загрузка на реальном x86-железе — ПЕРВЫЙ ШАГ закрыт** ([[platform]], слой «платформа» из [[0005-multiarch-arch-boundary]]): x86-ядро грузится настоящей прошивкой (multiboot1/GRUB, не только QEMU-PVH), рисует на VGA (0xB8000 — у ноутбука нет COM-порта) и берёт размер RAM из карты памяти загрузчика (`platform_init` → `arch::ram_limit()` вместо зашитых 128 МиБ; direct-map/фреймы зажаты CAP'ом 256 МиБ). Проверено в QEMU через GRUB (тот же путь, что на металле): `-m 512M`→обнаружено 511, VGA-скриншот показывает загрузку до `vsh>`, без virtio-диска/сети (как на ноутбуке) НЕ падает — сеется в RAM-store, поднимается vsh. Сборка загрузочного USB: `Code/boot/mkboot.sh` → ISO → dd. **Металл проверяет владелец платы** (у ассистента её нет). НЕ поедет с первого раза: клавиатура (нужен PS/2/USB-HID → на `vsh>` замирает), диск/сеть (AHCI/реальный NIC вместо virtio), кириллица на VGA (`?`), аллокатор по memmap.

- [x] **Веха 42 — драйвер клавиатуры (PS/2) — закрыта** ([[platform]], добита на реальном железе ASUS X54C): `vsh>` стал ИНТЕРАКТИВНЫМ на металле. `ps2.rs` — контроллер 8042 (внутренняя клавиатура ноутбука висит на нём как PS/2): скан-коды набора 1 из порта 0x60 → ASCII (Shift/CapsLock, US) → то же кольцо консоли, что и COM1 (`rx_push`). Наполнение: опрос на тиках + IRQ1 через IOAPIC на общий вектор консоли (IRQ будит из сна `wait_stdin`). Проверено в QEMU через `sendkey`: набрано `run bin/hello` — vsh отэхоил, запустил, код 0; кириллица-VGA (Веха 41) + клавиатура = живой русский терминал на реальном экране. Отложено: расширенные клавиши (стрелки), USB-HID, русская раскладка.

- [x] **Веха 43 — полировка TTY/vsh («косметика») — закрыта** ([[tty]], запрос пользователя после запуска на X54C): консоль перестала «выглядеть так себе». Единый механизм — vsh печатает **ANSI-коды**, а VGA-ядро (`vga.rs`) их разбирает (SGR-цвета, `ESC[2J` clear, `ESC[H/K`) и переводит в атрибуты VGA, не рисуя байты; на serial те же коды толкует терминал → цвет/`clear` работают ОДИНАКОВО в QEMU и на реальном экране. Аппаратный курсор VGA теперь двигается за письмом (`sync_cursor`, CRTC 0x0E/0x0F) — не «висит вверху». vsh: `clear`, цветной табличный `help` (жёлтые команды + русские описания), зелёное приглашение. `cd` осознанно отложен — posixfs ПЛОСКАЯ (нет каталогов/cwd).

- [x] **Веха 44 — папки в posixfs (иерархия) — закрыта** ([[folders]], первый пункт [[known-gaps]]): у персоналии появились каталоги/пути/`cwd` БЕЗ правок ядра. Файл — корень `f<путь>`, каталог — индекс-корень `d<путь>` (оба GC-safe); голое имя → `/<имя>` (std-программы работают без пересборки). vsh: резолвер путей (`.`/`..`/абс/отн), приглашение с каталогом (синим), команды `cd`/`pwd`/`mkdir`/`rm` + путь-осознанные `ls [DIR]`/`cat`/`tail`/`echo`/`mv`. Проверено на обеих архитектурах, персистентно (вложенные каталоги переживают перезагрузку). Осталось: прав/времён нет, `rm -r` нет, std-`create_dir` нет.

- [x] **Веха 45 — редактирование строки в vsh — закрыта** ([[tty]], пункт [[known-gaps]]): приглашение стало настоящим редактором — курсор в строке, вставка/удаление в позиции, `←`/`→`/`Home`/`End`/`Delete`, история команд `↑`/`↓` (кольцо на 8). Единый ANSI-механизм: PS/2 (`ps2.rs`) шлёт расширенные клавиши (`0xE0`) как `ESC[…`, terminal QEMU — те же коды, VGA-ядро разбирает (+ добавлено перемещение курсора `ESC[nA/B/C/D`), vsh парсит и перерисовывает строку (позиция по границам символов UTF-8). Проверено: serial (вставка в середине/backspace/история) и VGA через PS/2 (`sendkey up` поднял команду из истории). Ограничение: строки шире экрана редактируются неидеально.

- [x] **Веха 46 — освобождение фреймов — закрыта** ([[frame-freeing]], техдолг #3 из [[known-gaps]]): `frame.rs` дорос до списка свободных (интрузивный Treiber-стек, переиспользование вместо чистого bump); `arch::free_address_space` сносит приватные фреймы пространства (страницы+таблицы+корень), узнавая общие с ядром узлы сравнением с `KERNEL_ROOT` (x86 — с учётом клона PDPT под PML4[0]); `proc::reclaim_dead_spaces` в `resume()` освобождает группу, когда ВСЕ её нити `Finished` (единая точка для exit/exit_group/фолт-килла), предварительно переключив satp/CR3 на живого преемника (нельзя рушить активные таблицы). Проверено: обе арх — демо без OOM, ~327 фреймов вернулись; `run hello` ×12 → пик `[mem]` не сдвинулся (течь остановлена).

- [x] **Веха 47 — драйвер AHCI (SATA) — закрыта** ([[ahci]], первый «настоящий» драйвер железа из [[known-gaps]]): store читает/пишет на реальный SATA-диск в режиме AHCI — тот же интерфейс `BlockIo`, что и virtio-blk. `arch::probe_ahci` (x86) сканирует PCI-шину со ВСЕМИ функциями (на Intel-PCH контроллер на 00:1f.2), берёт ABAR/порт с диском; `ahci.rs` — опросный драйвер (список команд + FIS + PRDT, READ/WRITE DMA EXT, IDENTIFY для ёмкости); `object.rs` диспетчеризует носитель (AHCI → иначе virtio-blk). Проверено в QEMU (ich9-ahci без virtio): store прочитан по AHCI (32768 секторов, все программы), `echo > f` пережил ребут (`cat` вернул текст), регрессия virtio чиста на обеих арх. ⚠️ на реальном ноуте пишет в СЫРОЙ диск (сектор 0) — сотрёт существующую ОС; только пустой/запасной диск.

- [x] **Веха 48 — установка на диск — закрыта** ([[install]], live-USB → install → загрузка с диска): store переехал с сектора 0 в раздел (AHCI читает MBR, `base` LBA; тип раздела `0x9f`), `Code/boot/mkdisk.sh` собирает загрузочный образ (GRUB i386-pc вручную — `grub-bios-setup` на NixOS падает; p1 FAT с ядром, p2 store). Образ едет модулем multiboot2 на install-ISO (`arch::boot_module`, уберегаем от аллокатора фреймов) — установленное ядро == работающему. vsh `install` → `SYS_INSTALL` (№30, гейт store WRITE): пишет префикс на диск, растягивает p2 на весь диск, чистит store-область, замораживает кэш. Проверено end-to-end в QEMU: чистый диск → install → ребут только с SATA → VOID грузится, пишет, переживает ещё ребут. ⚠️ install СТИРАЕТ весь диск.

- [x] **Веха 49 — драйвер Intel e1000 (NIC) — закрыта** ([[e1000]], настоящая сеть на металле): драйвер PRO/1000 (PCI 8086:100e/10d3, BAR0 MMIO, RX/TX-кольца дескрипторов, MAC из RAL/RAH или EEPROM, опрос) даёт net-srv те же сырые кадры, что virtio-net; носитель диспетчеризуется `net.rs` (e1000 ↔ virtio-net, зеркало AHCI/virtio-blk). Проверено в QEMU (`-device e1000`): `ping 10.0.2.2` отвечает через e1000; регрессия virtio-net (обе арх) чиста. ⚠️ у X54C проводной порт Atheros/Realtek — не e1000; e1000 — первый общий NIC, не финал для этого ноута.

- [x] **Веха 50 — USB xHCI + HID-клавиатура — закрыта** ([[usb]], самый большой драйвер, 3 части): (A) контроллер — сброс/DCBAA/кольцо команд/кольцо событий/запуск/порты, Enable Slot проверяет машинерию; (B) перечисление — Address Device (input-контекст, EP0 TR-кольцо), control-трансферы по EP0, GET_DESCRIPTOR; (C) HID — config-дескриптор→interrupt-эндпоинт, SET_CONFIGURATION/SET_PROTOCOL(boot)/Configure Endpoint, poll_hid (из console_drain) парсит boot-репорты→ASCII→консоль; таймер не маскируется при простое, когда USB-клава поднята (у USB нет прерывания). Проверено в QEMU (qemu-xhci+usb-kbd, QMP send-key): набор «pwd»→Enter выполнился. ⚠️ X54C=Sandy Bridge→EHCI, не xHCI — этому ноуту не поднимет.

- [x] **Веха 51 — фундамент userspace-драйверов — закрыта** ([[userspace-drivers]], слой 1 к Linux-драйверам): capability-цели `Mmio{base,len}`/`Dma`; `SYS_MMIO_MAP` (маппит регистры устройства в процесс) + `SYS_DMA_ALLOC` (DMA-страница + физ-адрес); `frame::is_ram`-guard при сносе простора (не освобождать MMIO-листья); токены init `mmio:`/`dma`; демо `bin/e1000d` — Intel e1000 В USERSPACE (замапил BAR, прочитал MAC по MMIO, отправил кадр — карта выставила DD). Проверено в QEMU (virtio-net ядру + e1000 драйверу). Осталось из фундамента: доставка IRQ в userspace.

- [x] **Веха 52 — прерывания в userspace — закрыта** ([[irq]], второй и последний механизм фундамента [[userspace-drivers]]): драйвер спит до прерывания своего устройства вместо опроса. Capability-цель `Irq{vector}`; отдельный IDT-вектор `VEC_USERDRV=35` (обработчик НЕ берёт замок таблицы процессов — только атомарный флаг `USERDRV_IRQ_PENDING` + EOI); `SYS_IRQ_WAIT` (№33) → `State::IrqWait`, `drain_userdrv_irq` будит ждущих в `resume`/`wait_stdin`. Тонкость IOAPIC: QEMU-e1000 без MSI → PCI INTx **level-triggered active-low** (`route_level_low`: polarity/trigger-биты) + **oneshot-маска** (пины стартуют замаскированными; `SYS_IRQ_WAIT` взводит через `userdrv_irq_arm`, обработчик снова маскирует — как threaded-oneshot IRQ в Linux, без шторма). Демо `bin/e1000d`: размаскировал причину в IMS, дёрнул её через ICS, уснул в `SYS_IRQ_WAIT`, проснулся от реального прерывания карты (`ICR=0x04`=LSC). Проверено в QEMU; riscv — заглушки (`userdrv_irq_arm`/`e1000_irq_setup`), загрузка без регрессий.

- [x] **Веха 53 — lx_emul: первый каркас Linux-API шима — закрыта** ([[lx-emul]], верхний слой к хостингу Linux-драйверов): драйвер пишется «как в Linux», шим переводит вызовы в syscall'ы VOID (Genode `dde_linux`-стиль, каркас на Rust). `programs/user/src/lx_emul.rs`: `ioremap`+`readl`/`writel` (→`SYS_MMIO_MAP`), `dma_alloc_coherent`→`{cpu,dma}` (→`SYS_DMA_ALLOC`), `request_irq(handler)` — нить (`SYS_THREAD_SPAWN`), крутящая `SYS_IRQ_WAIT` (= Linux threaded-oneshot IRQ, ровно наш IOAPIC-oneshot), `kmalloc`/`kzalloc`/`kfree` (свой bump+free-list поверх `SYS_MAP`), `Completion` (futex), `module_init(probe)`+`Device` (собирает mmio/dma/irq cap из стартовых прав). Демо `bin/lx_e1000` — e1000 как Linux-СТИЛЕВОЙ драйвер (init спавнит его вместо `e1000d`): `ioremap`→сброс/линк→`dma_alloc_coherent` кольцо+буфер→TX (DD)→`request_irq`+`wait_for_completion`, проснулся от реального IRQ карты (threaded-нить, `ICR=0x04`). Проверено в QEMU (обе нити чисто вышли по `SYS_EXIT`, vsh поднялся); riscv — компилируется и сеется, не спавнится (нет e1000), без регрессий. Обе арх: 0 предупреждений.

- [x] **Веха 54 — lx_emul C-путь: C-драйвер против C-шима — закрыта** ([[lx-emul-c]], продолжение [[lx-emul]]): драйвер на C, скомпилированный кросс-gcc против void-libc, работает на VOID и гонит e1000 Linux-подобным API — тот же тулчейн, что для реальных `.c` из Linux. `void-libc/lx_emul.{c,h}` (в libvoid.a): `lx_emul.h` — чистый Linux-API без syscall.h (ioremap/readl/writel/dma_alloc_coherent/kmalloc/request_irq/completion/printk/module_init); `printk(fmt,…)` через newlib vsnprintf; `request_irq` — нить (SYS_THREAD_SPAWN) на SYS_IRQ_WAIT; kmalloc → newlib malloc; completion → futex. `syscall.h` дорос драйверными обёртками. `programs/lx-cdriver/lx_e1000.c` — e1000 как Linux-стилевой C-драйвер (кириллица в printk свободно — C-литералы UTF-8). Сборка: `nix-build nix -A <arch>.lx_e1000` (кросс-gcc оффлайн из локального стора) → мост `void-store-import put … bin/<arch>/lx_e1000_c` → init спавнит C-драйвер, если импортирован, иначе Rust `lx_e1000`. Проверено в QEMU x86: ioremap→SYS_MMIO_MAP, printk %02x→MAC, dma_alloc_coherent+writel→DD, request_irq(threaded C-нить)+wait_for_completion→реальный IRQ (ICR=0x04), SYS_EXIT рубит обе нити, vsh поднялся. riscv — компилируется и импортирован, не спавнится (нет e1000), без регрессий. Обе арх: 0 предупреждений. C-ELF на диске (void-disk.img в .gitignore), воспроизводится nix-build+мост.

  (порты 0x70/0x71, ждать сброса UIP, BCD/binary, регистр века); **riscv/QEMU virt** —
  `google,goldfish-rtc`, адрес берём из DTB (FDT-парсер уже есть с Вехи 85), читаем 64-битные
  наносекунды Unix; ядро запоминает `wall_base` на загрузке и отдаёт `wall = база + uptime` новым
  syscall'ом (`SYS_TIME`, №36); туда же — **энтропия** (RDRAND на x86 / пул от тактов и событий на
  riscv). Потребители: `SystemTime::now` в порте std (убрать фиктивную базу), `clock_gettime`
  (REALTIME vs MONOTONIC), `getrandom`, `date` в vvsh, времена файлов в posixfs (пункт
  [[known-gaps]]). Помнить: правка std → пересборка std-программ и uutils ([[std-port]], [[uutils]]).

  Причина потолков
  ([[platform]], Веха 85): direct-map **тождественный** (VA == PA), а регион всех процессов прибит
  линкером к `[0x4000_0000, 0x8000_0000)` (1..2 ГиБ) — `programs/user/linker.ld` + `USER_REGION_START`/
  `USER_STACK_TOP_VA` в `proc.rs`. На x86 RAM отображается с нуля, поэтому обязана кончиться на
  1 ГиБ; на riscv RAM начинается с 0x8000_0000 (выше региона процессов), там конфликта нет и
  потолок 2 ГиБ — просто консервативная константа `RAM_CAP`. Решение (см. [[0010-address-space-layout]]):
  **перенести регион процессов в высокие адреса** — база `0x20_0000_0000` (128 ГиБ): валидно и для
  Sv39 (нижняя половина < 2^38 = 256 ГиБ), и для x86 (остаётся внутри PML4[0], клон PDPT работает
  как прежде). После этого direct-map свободно растёт до 128 ГиБ на обеих архитектурах. Заодно:
  **1-ГиБ гигастраницы** в direct-map (сейчас 2-МиБ) — десятки гигабайт отображаются десятками
  записей. Цена: пересборка ВСЕХ программ (включая std-программы и uutils) под новую базу.

## Фаза 7 — сеть (см. [[0008-network-stack]])
Цель фазы: программа на VOID может **открыть соединение и что-то скачать**. Ядро не меняется по
существу — оно и дальше отдаёт сырые кадры ([[virtio-net]], [[e1000]]); всё новое живёт в
userspace-сервере `net-srv`, стек — **vendored smoltcp** (решение и разбор безопасности — в ADR).

- [x] **Веха 90 — smoltcp в net-srv: UDP поверх настоящего стека — ЗАКРЫТА.** Vendored smoltcp
  (версия прибита, сборка оффлайн — `programs/user/vendor/`); трейт `Device` — тонкая обёртка над
  `SYS_NET_SEND`/`SYS_NET_RECV` (`sys::net_phy`), `Instant` — из `sys::now()`. Свои ~200 строк
  ARP/IPv4/ICMP выброшены. **От плана отступили в одном:** вместо «нить стека + нить IPC» сервер
  стал **РЕАКТОРОМ** — один цикл `poll` + неблокирующий приём IPC. Двух нитей не понадобилось, а
  общей очереди с futex'ом — тем более: гонок нет по построению. Демо: UDP-запрос к DNS SLIRP
  (ответ пришёл) на обеих арх. Урок вехи — про ARP: `NeighborCache` глушит запросы на 1 с ПО
  ВСЕМУ КЭШУ (`silent_until` не по адресу), из-за чего бюджет ровно в 1 с давал ложное «нет
  ответа»; нашлось дампом трафика (`filter-dump`), в котором не было даже ARP.
- [x] **Веха 91 — сон вместо опроса — ЗАКРЫТА.**

    `net-srv` спит в ядре, момент пробуждения называет сам стек (`poll_delay`).

    36 со шлюзом в IDT). Кадр будит сервер сразу, потолок сна снят.

    проверять — это касалось и `futex_wait` с таймаутом (на холостой системе не просыпался вовсе).
  - **Три причины, по которым прерывание не приходило** (все три пришлось найти, ни одна не
    видна из кода — только из измерений):
    1. **x86:** virtio-net не привязывал очередь приёма к вектору MSI-X
       (`PCI_QUEUE_MSIX_VECTOR`) — virtio-blk это делает, потому у диска IRQ был, а у сети нет.
    2. **x86:** у нового вектора не было шлюза в IDT (`TRAP_STUBS` — фиксированная таблица);
       прерывание на вектор без шлюза не игнорируется, а **убивает машину**.
    3. **riscv (главная):** политики масок были взаимоисключающими — `irq_mask_preempt` включает
       таймер и ГЛУШИТ устройства, `irq_mask_stdin` наоборот. Сон со сроком требовал таймера,
       поэтому прерывание карты копилось в PLIC: pending-бит стоял, а `claim` его не видел, ведь
       SEIE был выключен. Добавлена третья политика `irq_mask_idle` — таймер И устройства.
       Попутно: линию virtio-mmio надо один раз снять при включении источника (`ack_pending`) —
       за время работы опросом она осталась поднятой, а PLIC ловит ФРОНТ.
  - **Чем это ловилось:** дамп DTB (проверить номера IRQ), чтение `InterruptStatus` устройства и
    регистра pending PLIC, лог `claim()`. Отдельный урок: первый лог claim'ов имел лимит в 6
    строк и его выбрали прерывания диска на загрузке — диагностика соврала, пришлось фильтровать.

    `SYS_REPLY` его не исполнит. Ждёт КЛИЕНТ (он стоит в `SYS_CALL`), а не цикл сервера — так
    сервер стал многоклиентским без единой нити. Это снимает изъян, записанный Вехой 92
    («один запрос за раз»), для всего TCP.
  - [x] Пул из 4 соединений со своими буферами; хвост отправки (`hold`) — чтобы не отвечать
    «отправлено 0» и не заставлять клиента крутить вызовы вхолостую; сроки на рукопожатие и на
    ожидание данных (клиента нельзя держать в `SYS_CALL` вечно).
  - [x] `recv` берёт из сокета **ровно столько, сколько запросил клиент**: IPC обрезает ответ по
    приёмному буферу, и лишнее пропало бы из потока молча. Отсюда же `\r` в ридере vvsh — без
    него не написать ни одного сетевого протокола.
  - **Проверено (обе арх):** `(tcp-send h "GET / HTTP/1.0…")` к **example.com** отдаёт настоящие
    `HTTP/1.1 200 OK` и страницу; второй `recv` — пусто (EOF после `Connection: close`), закрытие
    аккуратное. Многокусковый путь проверен отдельно контрольным сервером на хосте (через
    SLIRP `10.0.2.2`): файл 4750 байт приехал пятью кусками **1024+1024+1024+1024+843 = 4939 =
    заголовок 189 + тело 4750**, содержимое совпало побайтно. Крайние случаи: отказ в соединении,
    негодный хэндл, переиспользование слота, обращение после закрытия — все дают верный код.
  - **Найдено измерением:** отказ в соединении приходил клиенту как «негодный запрос». Причина в
    обёртке, а не в сервере: ответ-ошибка — 1 байт, ответ-успех — 2, а обёртка требовала двух
    всегда и подменяла честную причину. Видно было только на живом отказе — путь успеха молчал.
- [x] **Веха 94 — HTTP-клиент — ЗАКРЫТА.** GET с `Content-Length`, **chunked** и редиректами;
  тело — **потоком прямо в store**.
  - [x] **«Потоковый put» получился деревом, а не сессией.** Копить объект в ядре смысла нет —
    его куча и есть узкое место. Тело режется на куски по 16 КиБ, каждый кусок — обычный
    `obj_put`, а **узел** связывает их (`SYS_OBJ_PUT_NODE`, №38; читать обратно —
    `SYS_OBJ_CHILDREN`, №39). В памяти живёт ОДИН кусок; дедуп одинаковых кусков достаётся даром;
    **content-id узла — Merkle-корень** над содержимым, посчитанный самим устройством. Дерево не
    новая машинерия: `checkpoint` строит такое же с Вехи 37, и GC уже умеет по нему ходить.
  - [x] Команды vvsh: `(fetch "url" ["корень"])` → печатает байты/куски, ВОЗВРАЩАЕТ content-id;
    `(blob "корень" [смещение длина])` — сводка или кусок содержимого (чтение скачанного обратно).
  - **Проверено (обе арх):** контрольный файл 114000 байт приехал **7 кусками**, срезы совпали с
    хостом побайтно — включая границу куска 16384, самое подозрительное место; **chunked** (сервер
    с кусками 1/700/4095/16384/9/20000 байт) — 57000 байт, 4 куска, срезы точные; относительный
    `Location: /sub/` отработал; `example.com` — 559 байт, как у curl. Повторная загрузка того же
    файла даёт **тот же content-id**, и он **совпадает между riscv и x86**. Блоб, скачанный в
    прошлой загрузке системы, читается после ребута.
  - **Ошибка, которую поймал первый же прогон:** `SYS_OBJ_GET_ROOT` возвращает ЧИСЛО БАЙТ id (32),
    а не код возврата, — а `blob` проверял на 0 и объявлял «нет такого корня» о существующем.
    Загрузка при этом работала: путь записи и путь чтения врозь.
- [x] **Веха 95 — HTTPS: rustls на чистом RustCrypto — ЗАКРЫТА.** ← ворота в Фазу 8 открыты.
  - [x] **Криптография без единой строки C**: провайдер `rustls-rustcrypto` вместо `ring`/`aws-lc`
    (в тех C и ассемблер, а у нас нет ни libc, ни заготовок под VOID). Всё дерево — 105 крейтов —
    вендорено и собирается `no_std`+`alloc` под наши таргеты.
  - [x] **`no_std`-режим rustls даёт «небуферизованный» API** — и это оказалось удобнее
    буферизованного: сокета с `Read`/`Write` у нас нет, есть IPC к `net-srv`, а небуферизованное
    соединение как раз просит байты у транспорта, не зная про него ничего.
  - [x] **Отдельная программа `httpsc`, а не команда шелла.** 105 крейтов чужого кода не должны
    работать с полномочиями `vvsh` (весь store, posixfs, сеть). У `httpsc` ровно два права —
    сеть и store. Первый случай, когда чужого кода стало много, и cap-модель отработала по делу.
  - [x] **Отказ вместо театра**: `sys::random_is_strong()` (`SYS_RANDOM(kind=1)`) — нет
    подтверждённого источника случайности, TLS не начинается вовсе.
  - **Проверено (обе арх):** `https://cache.nixos.org/nix-cache-info` — 51 байт, содержимое
    совпало (`StoreDir: /nix/store`…), content-id **одинаков на riscv и x86**;
    `https://www.gnu.org/licenses/gpl-3.0.txt` — **35149 байт, 3 куска**, ровно как у curl.
  - **Главное — доказано, что проверка НАСТОЯЩАЯ.** Клиент, принимающий любой сертификат, вёл бы
    себя на удачном запросе точно так же, поэтому отдельно прогнаны стенды badssl.com:
    `expired` → «сертификат просрочен», `self-signed` и `untrusted-root` → «цепочка не ведёт к
    доверенному корню», `wrong.host` → «сертификат выдан на другое имя». Причины называются
    поимённо намеренно: по общему «ошибка TLS» не отличить чужую неисправность от своих сбитых
    часов, а это ровно те два случая, которые пользователь обязан различать.
  - **Долг:** редиректы для https не сделаны (для http есть) — сервер с 3xx честно отвергается.

## Фаза 8 — пакеты на устройстве (см. [[0009-ondevice-packages]])
Цель фазы: **`pkg install hello` на самом VOID** — скачать из бинарного кэша nixpkgs, разложить в
контент-адресуемый store, запустить. Сборка из исходников — Фаза 9, отдельно.

- [x] **Веха 105 — NAR, xz и zstd на устройстве. ЗАКРЫТА** ([[pkg-unpack]]) — настоящие архивы с
  `cache.nixos.org` (`niri-26.04-doc`, 103 988 → 522 912 Б, 57 файлов) распакованы самой VOID на
  ОБЕИХ архитектурах; распакованный размер совпал с хостовым `xz -d` побайтно, содержимое файла —
  с исходником, после ребута дерево на месте.
  - **xz**: закреплённая копия `lzma-rs` 0.3.0 в `programs/user/vendor-compress/` — `no_std`+`alloc`,
    только декодер, а `std::io`/`byteorder`/`crc` заменены шимами ВНУТРИ копии: зависимостей у
    неё не осталось ни одной (иначе унификация фич однажды включила бы `std`). Тела декодеров не
    тронуты. 27 host-тестов, включая контрольные значения CRC (RevEng), обе проверки контейнера
    (CRC32 и CRC64), обрезанный и испорченный архив.
  - **Вход тремя видами**: объект, блоб из кусков (так кладёт `fetch`) и любой из них сжатый.
    Сжатый НЕ материализуется в куче: распаковщик тянет куски через `BlobReader`. Сжатие
    определяется по содержимому (магия), а не по имени корня.
  - **Три ошибки, которые нашёл настоящий пакет** (игрушечный архив их не показывал): posixfs
    держал слот файла вечно → потолок «16 РАЗНЫХ файлов за сессию» (теперь вытеснение чистого
    слота, как в store Вехой 104); `ls` молча обрезал список на 512 байтах → каталог из 50 имён
    показывался как 18 (теперь буфер = индекс каталога, а `ls` сообщает, если доехало меньше, чем
    сервер хотел отдать); `poweroff` падал в #PF на PVH-загрузке — поправку Вехи 101 про ACPI в
    direct-map сделали только для multiboot2, теперь продублирована для PVH.
  - **Осталось долгом:** `SYS_OBJ_GET` не сообщает длину объекта (читаем удвоением буфера) и
    настоящей потоковой распаковки нет — распакованный NAR собирается в памяти целиком, потому что
    `void_nar::walk` берёт слайс (полный поток = pull-парсер NAR, отдельный шаг).
  - **zstd — тоже сделан (105.2).** Замер вскрыл, что кэш nixpkgs перешёл на zstd: случайная
    выборка путей (2026-08-04) — **15 из 22 `zstd`, 7 `xz`**. Копия `ruzstd` 0.8.3 (+ `twox-hash`
    для XXH64) легла рядом, каталог переименован в `vendor-compress`. Исходники НЕ ТРОНУТЫ вовсе:
    `ruzstd` `no_std` сам по себе и со своим io-шимом — изменены только манифесты. Распаковка
    тоже потоковая. Проверено на обеих архитектурах, оба формата в одном сеансе
    (`perl-5.42.0-env`, 8611 → 568 296 Б, 31 файл и 182 симлинка), размер совпал с `zstd -d`
    побайтно. Заодно: печатать каждый пропущенный симлинк нельзя (в `perl-env` их 182) — теперь
    первые пять поимённо, остальные числом.
  - **Ещё один долг оттуда же:** симлинков в персоналии нет, а настоящие пакеты состоят из них
    чуть ли не наполовину. Установка пакета потребует их поддержать — в posixfs или раскладкой
    пакета прямо в store.

- [x] **Веха 106 — `pkg fetch`: narinfo → store, с проверкой. ЗАКРЫТА** ([[pkg-fetch]]).
  `pkg fetch <хэш|путь>` скачивает narinfo, проверяет **подпись кэша** (ed25519 по отпечатку
  `1;путь;NarHash;NarSize;ссылки`), скачивает архив, распаковывает и сверяет **NarHash** (sha256
  распакованного NAR). Проверено на ОБЕИХ архитектурах настоящими путями: один сжат xz и без
  зависимостей, другой zstd и с четырьмя.
  - **Доказано, что проверки настоящие** (приём Вехи 95 со стендами badssl): подмена метаданных
    (`NarSize + 1` в отпечатке) → «ПОДПИСЬ НЕ СОШЛАСЬ — путь отвергнут»; подмена содержимого
    (`digest[0] ^= 1`) → «NarHash не сошёлся» с обеими величинами. Успешная загрузка сама по себе
    ничего не доказывает — клиент без проверок вёл бы себя так же.
  - **`pkg` — отдельная программа** (довод `httpsc`): чужого кода много, полномочий нужно мало —
    ровно store и сеть. Скачивает по-прежнему `httpsc`, TLS остаётся в своём процессе.
  - Порядок проверок: подпись ДО загрузки архива, NarHash — после распаковки. Скачанный сжатый

  - **Осталось:** имя пакета не резолвится (`pkg fetch hello` требует вычисления nixpkgs — пока
    только хэш или путь); `References` считаются, но не загружаются (Веха 107); `StoreDir` зашит.
- [x] **Веха 107 — замыкание зависимостей и профили. ЗАКРЫТА** ([[pkg-closure]]).

    с именем пути. Отсюда даром дедуп, достижимость вместо «списка не удалять» и отсутствие

    `libc.so.6` 2413096 Б блобом из 148 кусков. Обе архитектуры, x86 читал написанное riscv;
    после ребута всё на месте.
  - **Вскрыло беду не этой вехи**: GC затягивал в память ВЕСЬ достижимый store и ронял загрузку
    (`memory allocation of 16384 bytes failed`) — теперь обход берёт только ссылки. `compact`
    болен тем же по построению, записан в [[known-gaps]].
- [x] **Веха 108.2 — /nix/store виден файловым API. ЗАКРЫТА** ([[store-mount]]). posixfs
  МОНТИРУЕТ дерево пакета (тот же `src/tree.rs`, что им пишет `pkg`) и отдаёт его read-only под
  `/nix/store/...`. Пакет туда не переписывается: под точкой монтирования сервер уходит в другую
  раскладку.
  - **Файл пакета не ограничен 128 КиБ**: в слоте лежит УЗЕЛ, а не содержимое — чтение идёт прямо
    из дерева кусками (`libc.so.6` 2.4 МБ). **Симлинки** появились (`readlink`) — своих у
    персоналии нет, а у пакетов их половина. **`/nix/store` — список корней `pkg/tree/*`**, а не
    отдельный индекс: рассинхрону взяться неоткуда. **Запись отвергается** — пакет неизменяем.
  - Подняты: путь 128 → 512 байт, буфер ответа со стека в кучу (в `lib/gconv` 255 записей, в
    `share/i18n/locales` — 369).
  - Сверено с хостом на обеих архитектурах: списки каталогов совпали до последней записи,
    `cat` файлов — байт в байт, `tail` файла на **3.4 МБ** прочитал верные байты из куска №206
    (то есть `seek`+чтение по большому смещению внутри блоба работают), запись под `/nix/store`
    отвергнута трижды (`mkdir`/`rm`/`echo >`).
  - **Осталось**: персоналия Linux сюда ещё не ходит (108.3); симлинки не разыменовываются при
    разборе пути; кэша последнего куска у слота нет.
- [x] **Веха 108.3 — мост персоналии Linux к файлам. ЗАКРЫТА** ([[lx-files]]). Неизменённая
  программа из nixpkgs (static-PIE musl) открывает, читает и перечисляет настоящий пакет:
  `openat`/`open`, `read`, `close`, `lseek`, `fstat`/`stat`/`lstat`/`newfstatat`, `access`,
  `readlink(at)`, `getdents64`.
  - **Чтение идёт прямо из store, а не через posixfs**, и это вынужденно: персоналия живёт В
    ЯДРЕ, а `openat` обязан ответить внутри syscall'а — ходить оттуда по IPC нечем (у ядра нет ни
    домена, ни состояния «жду ответа»). Зато и дерево пакета, и иерархия posixfs — просто корни
    store, так что `lxfs.rs` не вторая ФС, а тот же граф с другой стороны. Формат дерева и блоба
    переехал в общий крейт `libs/void-tree` — читателей стало четверо.
  - **Только чтение**: `open` на запись отвечает EROFS — честно, а не «нет файла».
  - Сверка: `sum` (FNV) файла на **2.4 МБ** дал на устройстве те же size и хэш, что на хосте, —
    на ОБЕИХ архитектурах.
  - **x86 вскрыл две вещи**: musl там предпочитает легаси-номера без `dirfd` (`open`/`stat`/
    `lstat`/`access`/`readlink`), которых на riscv нет вовсе, — без них мост отвечал ENOSYS на
    всё; и номер 89 (`readlink`) был помечен как `readlinkat`, у которых РАЗНЫЕ аргументы (путь
    первый против второго).
  - **Осталось**: `mmap` файла (нужен `ld.so`), разыменование симлинков при разборе пути,
    относительные пути, перечисление каталогов иерархии posixfs.
- [ ] **Веха 108.4 — динамический бинарь запускается**: `PT_INTERP`, загрузка `ld.so` (релокации
  делает он сам), стартовый набор syscall'ов glibc (`mmap`/`openat`/`fstat`/`arch_prctl`(TLS)/
  `set_tid_address`/`futex`/`clock_gettime`/`getrandom`/`exit_group`). Демо: неизменённый
  динамический `hello` из nixpkgs.
- [ ] ~~**Веха 108 — запуск скачанного (доводка персоналии Linux).**~~ Разбита на 108.1–108.3
  выше; исходная формулировка: три части: (а) **файловый мост**
  linux→posixfs (сегодня в [[linux-abi]] работают только applet'ы в stdout) и видимый путь
  `/nix/store/...`; (б) **динамический загрузчик** — `PT_INTERP`, запуск `ld.so` (релокации делает
  он сам, нам — загрузить и дать syscall'ы); (в) **стартовый набор glibc**: `mmap`/`openat`/`fstat`/
  `arch_prctl`(TLS)/`set_tid_address`/`futex`/`clock_gettime`/`getrandom`/`exit_group`. Демо:
  неизменённый динамический `hello` из nixpkgs запускается на VOID.
- [ ] **Веха 109 — пакетная жизнь.** `PATH` из профиля (голое имя в vvsh ищет и там), `pkg` в help,

**Риски и предпосылки фазы (проверить рано):** куча ядра 16 МиБ и двойное копирование ELF при
`exec` — большие пакеты в неё не влезут (нужен потоковый put и, возможно, отображение ELF без
второй копии); posixfs с файлом ≤128 КиБ обходим только через store; динамические glibc-бинари
тянут заметный кусок «второго Linux» — если упрёмся, запасной путь `pkgsStatic` (у́же ассортимент,
зато без `ld.so`).

## Опционально / исследовательское
- [ ] SASOS-эксперимент: изоляция средствами Rust вместо железных границ (см. [[0001-rust-riscv-microkernel]]). Практичный первый шаг — гибрид: доверенные серверы в одном AS (модель Theseus/Hubris), код сервера = проверяемый объект по хэшу. См. [[phase-2-state-analysis]].
- [ ] **Меш VoidConnect как источник store и приёмник деривации** ([[0012-mesh-distributed-work]]).
  Соседний проект владельца (`../VoidConnect`) — P2P-сеть без центра, уже на BLAKE3 и чанках, то есть
  на одном языке с нашим store. Распределять нагрузку **деривациями**, а не разделяемой памятью:
  единица работы должна быть на 2–3 порядка дороже round trip, и деривация (чистая функция
  content-id → content-id) ровно такая. Порядок: меш-substituter («не собирать дважды») → offload
  целой сборки на мощный пир → опционально кворум по хэшам. Порт УМЕНЬШАЕТ VoidConnect: `db`/sqlite
  не нужен (store и есть база), `ui` ждёт графики. Блокер — сокеты и tokio (потоки/futex), то есть
  после Фазы 7.
- [ ] **Персоналия для чужого софта, в пределе `.exe`** ([[0011-foreign-software-personalities]]).
  Мир процесса СОБИРАЕТСЯ из ничего, а не вырезается: без ambient authority можно безопасно врать
  программе про её привилегии. Приём доказан этажом ниже — [[lx-emul]] хостит неизменённые .c ядра
  Linux (Веха 73). Фаза 12+: нужны GPU, оконная система, потоки и полный linux-abi. **Обход
  kernel-античита в цели НЕ входит** — против аппаратной аттестации локальная ложь не работает в
  принципе (разбор — в ADR).
- [ ] **Гипервизор: Linux гостем под VOID** ([[0015-hypervisor-linux-guest]], решение 2026-08-04).
  Цель владельца «Steam и Proton» разобрана по путям, и выбран НЕ путь персоналии: у совместимости
  с ABI нет края (Steam тянет namespaces, D-Bus, udev, evdev, 32-битный `ld.so`), у виртуализации
  край есть — гость либо загрузился, либо нет. VOID остаётся хозяином, Linux становится обычным
  cap-доменом; устройства — virtio (мы уже знаем формат с драйверной стороны), диск гостя = объект
  store, значит откат VM достаётся механикой поколений. Лестница: **SMP → IOMMU → минимальный
  гипервизор (SVM/NPT) → Linux в VM без passthrough → passthrough GPU**. Первые две ступени и так
  висят в [[known-gaps]] — теперь у них есть причина и порядок. Оговорка про железо: passthrough
  единственной видеокарты отдаёт экран гостю (нужна вторая карта либо передача владения).
  Побочный выигрыш — старая NixOS владельца может жить ВНУТРИ VOID: не «заменить», а «пустить
  внутрь». Античит-аттестация по-прежнему не проходится ([[0011-foreign-software-personalities]]).
