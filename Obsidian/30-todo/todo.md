# VOID — staged роадмап

Принцип: радикальные идеи включаются по одной, **каждая за работающей вехой** — чтобы всегда
было что-то живое в QEMU, а не вечная стройка. Первые ~5 слоёв одинаковы для любого ядра и не
зависят от стержневого тезиса ([[0002-persistent-content-addressed-capability-core]]) — это
чистое «понять, как всё работает». Радикальное начинается со слоя памяти/хранилища.

## Фаза 0 — фундамент (от железа вверх)
- [x] **Веха 1.** Boot: OpenSBI → entry asm → стек → `kmain`; вывод в UART (NS16550).
- [x] **Веха 2.** Trap/прерывания: обработчик исключений (ebreak), таймерные прерывания (S-mode), дамп регистров при фатале. См. [[traps-and-timer]].
- [x] **Веха 3.** Виртуальная память: Sv39-пагинг, direct map RAM + W^X ядра, переход на трансляцию. См. [[sv39-paging]].
- [x] **Веха 4.** Kernel heap: free-list аллокатор + `#[global_allocator]`, арена из `frame::reserve`, `alloc` работает. См. [[kernel-heap]], [[memory-regions]].
- [x] **Веха 5.** Многозадачность: контексты + кооперативный round-robin планировщик. См. [[scheduling]].
- [x] **Веха 5.5.** Вытеснение (preemption) по таймеру: переключение из trap'а, состояние прерываний на задачу, атомарный вывод. См. [[scheduling]].

## Фаза 1 — стержень (тут начинается VOID)
- [x] **Веха 6.** Объектная модель в RAM: неизменяемые значения по хэшу + дедуп + изменяемые корни/история версий. См. [[object-model]], [[persistence-and-volatility]].
- [x] **Веха 7.1.** Драйвер virtio-blk: чтение/запись секторов (virtio-mmio, split virtqueue, опрос). См. [[virtio-blk]].
- [x] **Веха 7.2.** Персистентный store: суперблок + A/B индекс + append-only объекты; корень переживает перезагрузку. См. [[persistent-store]].
- [x] **Веха 8.** Capability: непод­делываемые дескрипторы (слот+поколение), c-space на домен, аттенуация при grant, отзыв. См. [[capabilities]].
- [x] **Веха 9.** Async-executor: future-задачи + waker + async-канал поверх объектного store. См. [[async-executor]].

> **Фаза 1 закрыта:** все три ингредиента ADR 0002 (персистентность · контент-адресация · capability) + async-модель исполнения над ними собраны и работают в QEMU.

- [x] **Веха 12.** Capability-защищённые IPC-эндпоинты: домен на процесс, `CALL` по cap на эндпоинт (`SEND`), `BLK_READ` по cap на устройство (`READ`) — доступ к серверу/железу только по дескриптору. См. [[ipc-endpoints]].

- [x] **Веха 17.** `BLK_WRITE`: шлюз записи сектора под правом `WRITE` на устройство; блок-протокол кодирует сектор+флаг записи в `op`. Клиент пишет и читает сектор обратно через сервер. См. [[block-driver]].
- [x] **Веха 18.** Слой совместимости — POSIX-персоналия как сервер (под-вехи 18.1–18.4, **закрыта**).

    - [x] **18.3.** `stat`/`unlink`/`readdir`, режимы open (`O_APPEND`/`O_TRUNC`), смещения на дескриптор; персистентный индекс каталога `.dir`; шлюз ядра `OBJ_DEL_ROOT` (честный unlink — корень уходит в GC). См. [[posix-personality]].

## Фаза 3 — самостоятельность (см. [[0003-phase-3-exec-by-hash]])
Центральный примитив фазы: **программа = контент-адресуемый объект, exec по ContentId** — как derivation в Nix, прямое следствие ADR 0002.
- [x] **Веха 19.** Программа как объект store: ELF-крейт `programs/hello` → байты в store под корнем `bin/hello` → минимальный ELF-загрузчик (PT_LOAD, W^X) → `spawn_elf` по ContentId; на втором запуске ELF грузится с диска. См. [[exec-from-store]].
- [x] **Веха 20.** UART-ввод по прерыванию (кольцевой буфер, вычерпывание на тиках) + `SYS_READ`/`SYS_EXEC` (право `EXEC`, foreground-ожидание) + интерактивный `vsh`: `ls`/`cat`/`echo > f`/`run bin/hello`/`exit`; смена корня из userspace = атомарный чекпойнт. См. [[interactive-shell]].
- [x] **Веха 21.** Cap-transfer по IPC (grant-в-сообщении, право GRANT; `CAP_DERIVE` — аттенуация) + персистентный c-space (`.cspace` в store, чекпойнт на каждую передачу, restore с точными поколениями) — capability переживают перезагрузку, тезис ADR 0002 полный. См. [[ipc-cap-transfer]].
- [x] **Веха 22.** Куча процесса (`SYS_MAP`, ленивые страницы, доотображение под шлюзы); user page fault убивает процесс, а не ядро; лимиты POSIX-персоналии сняты (16 файлов × 4 КиБ, метаданные в куче). См. [[process-heap]].

> **Фаза 3 закрыта:** система самостоятельна — программы загружаются из store по content-id,
> есть живой shell с вводом, capability передаются по IPC и переживают перезагрузку вместе с
> c-space, у процессов настоящая ленивая память и честные фолты.

Проверено в QEMU через `sendkey`: набрано `run bin/hello` — vsh отэхоил, запустил, код 0; кириллица-VGA (Веха 41) + клавиатура = живой русский терминал на реальном экране. Отложено: расширенные клавиши (стрелки), USB-HID, русская раскладка.

- [x] **Веха 43 — полировка TTY/vsh («косметика») — закрыта** ([[tty]], запрос пользователя после запуска на X54C): консоль перестала «выглядеть так себе». Единый механизм — vsh печатает **ANSI-коды**, а VGA-ядро (`vga.rs`) их разбирает (SGR-цвета, `ESC[2J` clear, `ESC[H/K`) и переводит в атрибуты VGA, не рисуя байты; на serial те же коды толкует терминал → цвет/`clear` работают ОДИНАКОВО в QEMU и на реальном экране. Аппаратный курсор VGA теперь двигается за письмом (`sync_cursor`, CRTC 0x0E/0x0F) — не «висит вверху». vsh: `clear`, цветной табличный `help` (жёлтые команды + русские описания), зелёное приглашение. `cd` осознанно отложен — posixfs ПЛОСКАЯ (нет каталогов/cwd).

- [x] **Веха 44 — папки в posixfs (иерархия) — закрыта** ([[folders]], первый пункт [[known-gaps]]): у персоналии появились каталоги/пути/`cwd` БЕЗ правок ядра. Проверено на обеих архитектурах, персистентно (вложенные каталоги переживают перезагрузку). Осталось: прав/времён нет, `rm -r` нет, std-`create_dir` нет.

- [x] **Веха 45 — редактирование строки в vsh — закрыта** ([[tty]], пункт [[known-gaps]]): приглашение стало настоящим редактором — курсор в строке, вставка/удаление в позиции, `←`/`→`/`Home`/`End`/`Delete`, история команд `↑`/`↓` (кольцо на 8). Проверено: serial (вставка в середине/backspace/история) и VGA через PS/2 (`sendkey up` поднял команду из истории). Ограничение: строки шире экрана редактируются неидеально.

- [x] **Веха 46 — освобождение фреймов — закрыта** ([[frame-freeing]], техдолг #3 из [[known-gaps]]): `frame.rs` дорос до списка свободных (интрузивный Treiber-стек, переиспользование вместо чистого bump); `arch::free_address_space` сносит приватные фреймы пространства (страницы+таблицы+корень), узнавая общие с ядром узлы сравнением с `KERNEL_ROOT` (x86 — с учётом клона PDPT под PML4[0]); `proc::reclaim_dead_spaces` в `resume()` освобождает группу, когда ВСЕ её нити `Finished` (единая точка для exit/exit_group/фолт-килла), предварительно переключив satp/CR3 на живого преемника (нельзя рушить активные таблицы). Проверено: обе арх — демо без OOM, ~327 фреймов вернулись; `run hello` ×12 → пик `[mem]` не сдвинулся (течь остановлена).

- [x] **Веха 47 — драйвер AHCI (SATA) — закрыта** ([[ahci]], первый «настоящий» драйвер железа из [[known-gaps]]): store читает/пишет на реальный SATA-диск в режиме AHCI — тот же интерфейс `BlockIo`, что и virtio-blk. `arch::probe_ahci` (x86) сканирует PCI-шину со ВСЕМИ функциями (на Intel-PCH контроллер на 00:1f.2), берёт ABAR/порт с диском; `ahci.rs` — опросный драйвер (список команд + FIS + PRDT, READ/WRITE DMA EXT, IDENTIFY для ёмкости); `object.rs` диспетчеризует носитель (AHCI → иначе virtio-blk). Проверено в QEMU (ich9-ahci без virtio): store прочитан по AHCI (32768 секторов, все программы), `echo > f` пережил ребут (`cat` вернул текст), регрессия virtio чиста на обеих арх. ⚠️ на реальном ноуте пишет в СЫРОЙ диск (сектор 0) — сотрёт существующую ОС; только пустой/запасной диск.

- [x] **Веха 48 — установка на диск — закрыта** ([[install]], live-USB → install → загрузка с диска): store переехал с сектора 0 в раздел (AHCI читает MBR, `base` LBA; тип раздела `0x9f`), `Code/boot/mkdisk.sh` собирает загрузочный образ (GRUB i386-pc вручную — `grub-bios-setup` на NixOS падает; p1 FAT с ядром, p2 store). Образ едет модулем multiboot2 на install-ISO (`arch::boot_module`, уберегаем от аллокатора фреймов) — установленное ядро == работающему. vsh `install` → `SYS_INSTALL` (№30, гейт store WRITE): пишет префикс на диск, растягивает p2 на весь диск, чистит store-область, замораживает кэш. Проверено end-to-end в QEMU: чистый диск → install → ребут только с SATA → VOID грузится, пишет, переживает ещё ребут. ⚠️ install СТИРАЕТ весь диск.

- [x] **Веха 49 — драйвер Intel e1000 (NIC) — закрыта** ([[e1000]], настоящая сеть на металле): драйвер PRO/1000 (PCI 8086:100e/10d3, BAR0 MMIO, RX/TX-кольца дескрипторов, MAC из RAL/RAH или EEPROM, опрос) даёт net-srv те же сырые кадры, что virtio-net; носитель диспетчеризуется `net.rs` (e1000 ↔ virtio-net, зеркало AHCI/virtio-blk). Проверено в QEMU (`-device e1000`): `ping 10.0.2.2` отвечает через e1000; регрессия virtio-net (обе арх) чиста. ⚠️ у X54C проводной порт Atheros/Realtek — не e1000; e1000 — первый общий NIC, не финал для этого ноута.

- [x] **Веха 51 — фундамент userspace-драйверов — закрыта** ([[userspace-drivers]], слой 1 к Linux-драйверам): capability-цели `Mmio{base,len}`/`Dma`; `SYS_MMIO_MAP` (маппит регистры устройства в процесс) + `SYS_DMA_ALLOC` (DMA-страница + физ-адрес); `frame::is_ram`-guard при сносе простора (не освобождать MMIO-листья); токены init `mmio:`/`dma`; демо `bin/e1000d` — Intel e1000 В USERSPACE (замапил BAR, прочитал MAC по MMIO, отправил кадр — карта выставила DD). Проверено в QEMU (virtio-net ядру + e1000 драйверу). Осталось из фундамента: доставка IRQ в userspace.

- [x] **Веха 52 — прерывания в userspace — закрыта** ([[irq]], второй и последний механизм фундамента [[userspace-drivers]]): драйвер спит до прерывания своего устройства вместо опроса. Capability-цель `Irq{vector}`; отдельный IDT-вектор `VEC_USERDRV=35` (обработчик НЕ берёт замок таблицы процессов — только атомарный флаг `USERDRV_IRQ_PENDING` + EOI); `SYS_IRQ_WAIT` (№33) → `State::IrqWait`, `drain_userdrv_irq` будит ждущих в `resume`/`wait_stdin`. Тонкость IOAPIC: QEMU-e1000 без MSI → PCI INTx **level-triggered active-low** (`route_level_low`: polarity/trigger-биты) + **oneshot-маска** (пины стартуют замаскированными; `SYS_IRQ_WAIT` взводит через `userdrv_irq_arm`, обработчик снова маскирует — как threaded-oneshot IRQ в Linux, без шторма). Демо `bin/e1000d`: размаскировал причину в IMS, дёрнул её через ICS, уснул в `SYS_IRQ_WAIT`, проснулся от реального прерывания карты (`ICR=0x04`=LSC). Проверено в QEMU; riscv — заглушки (`userdrv_irq_arm`/`e1000_irq_setup`), загрузка без регрессий.

- [x] **Веха 53 — lx_emul: первый каркас Linux-API шима — закрыта** ([[lx-emul]], верхний слой к хостингу Linux-драйверов): драйвер пишется «как в Linux», шим переводит вызовы в syscall'ы VOID (Genode `dde_linux`-стиль, каркас на Rust). `programs/user/src/lx_emul.rs`: `ioremap`+`readl`/`writel` (→`SYS_MMIO_MAP`), `dma_alloc_coherent`→`{cpu,dma}` (→`SYS_DMA_ALLOC`), `request_irq(handler)` — нить (`SYS_THREAD_SPAWN`), крутящая `SYS_IRQ_WAIT` (= Linux threaded-oneshot IRQ, ровно наш IOAPIC-oneshot), `kmalloc`/`kzalloc`/`kfree` (свой bump+free-list поверх `SYS_MAP`), `Completion` (futex), `module_init(probe)`+`Device` (собирает mmio/dma/irq cap из стартовых прав). Демо `bin/lx_e1000` — e1000 как Linux-СТИЛЕВОЙ драйвер (init спавнит его вместо `e1000d`): `ioremap`→сброс/линк→`dma_alloc_coherent` кольцо+буфер→TX (DD)→`request_irq`+`wait_for_completion`, проснулся от реального IRQ карты (threaded-нить, `ICR=0x04`). Проверено в QEMU (обе нити чисто вышли по `SYS_EXIT`, vsh поднялся); riscv — компилируется и сеется, не спавнится (нет e1000), без регрессий. Обе арх: 0 предупреждений.

- [x] **Веха 54 — lx_emul C-путь: C-драйвер против C-шима — закрыта** ([[lx-emul-c]], продолжение [[lx-emul]]): драйвер на C, скомпилированный кросс-gcc против void-libc, работает на VOID и гонит e1000 Linux-подобным API — тот же тулчейн, что для реальных `.c` из Linux. `void-libc/lx_emul.{c,h}` (в libvoid.a): `lx_emul.h` — чистый Linux-API без syscall.h (ioremap/readl/writel/dma_alloc_coherent/kmalloc/request_irq/completion/printk/module_init); `printk(fmt,…)` через newlib vsnprintf; `request_irq` — нить (SYS_THREAD_SPAWN) на SYS_IRQ_WAIT; kmalloc → newlib malloc; completion → futex. `syscall.h` дорос драйверными обёртками. `programs/lx-cdriver/lx_e1000.c` — e1000 как Linux-стилевой C-драйвер (кириллица в printk свободно — C-литералы UTF-8). Сборка: `nix-build nix -A <arch>.lx_e1000` (кросс-gcc оффлайн из локального стора) → мост `void-store-import put … bin/<arch>/lx_e1000_c` → init спавнит C-драйвер, если импортирован, иначе Rust `lx_e1000`. Проверено в QEMU x86: ioremap→SYS_MMIO_MAP, printk %02x→MAC, dma_alloc_coherent+writel→DD, request_irq(threaded C-нить)+wait_for_completion→реальный IRQ (ICR=0x04), SYS_EXIT рубит обе нити, vsh поднялся. riscv — компилируется и импортирован, не спавнится (нет e1000), без регрессий. Обе арх: 0 предупреждений. C-ELF на диске (void-disk.img в .gitignore), воспроизводится nix-build+мост.

## Фаза 6 — фундамент под остальное: часы и память
Две вещи, которые нужны и сами по себе, и всему дальнейшему (TLS без часов бессмысленен, пакеты
без памяти некуда класть). Делаются ДО сети.

- [x] **Веха 86 — настоящие часы (RTC) и источник случайности — ЗАКРЫТА** ([[clock]]). Сейчас времени как такового нет:
  `arch::now_ticks()` даёт монотонные тики с загрузки, а «настенные часы» в порте std — **фиктивная
  база 2026-07-01 + uptime** (`vendor/rust/library/std/src/sys/time/void.rs`), `linux-abi`
  `clock_gettime`/`gettimeofday` считают то же самое, `getrandom` — xorshift от счётчика
  (`sys/random/void.rs`, честно помечен «не криптографический»). Сделать: **x86** — CMOS RTC
  (порты 0x70/0x71, ждать сброса UIP, BCD/binary, регистр века); **riscv/QEMU virt** —
  `google,goldfish-rtc`, адрес берём из DTB (FDT-парсер уже есть с Вехи 85), читаем 64-битные
  наносекунды Unix; ядро запоминает `wall_base` на загрузке и отдаёт `wall = база + uptime` новым

- [x] **Веха 87 — снятие потолка RAM: HIGHER-HALF ЯДРО** (решение уточнено по итогам первого

  Причина потолков
  ([[platform]], Веха 85): direct-map **тождественный** (VA == PA), а регион всех процессов прибит
  линкером к `[0x4000_0000, 0x8000_0000)` (1..2 ГиБ) — `programs/user/linker.ld` + `USER_REGION_START`/

  1 ГиБ; на riscv RAM начинается с 0x8000_0000 (выше региона процессов), там конфликта нет и
  потолок 2 ГиБ — просто консервативная константа `RAM_CAP`. Решение (см. [[0010-address-space-layout]]):
  **перенести регион процессов в высокие адреса** — база `0x20_0000_0000` (128 ГиБ): валидно и для
  Sv39 (нижняя половина < 2^38 = 256 ГиБ), и для x86 (остаётся внутри PML4[0], клон PDPT работает
  как прежде). После этого direct-map свободно растёт до 128 ГиБ на обеих архитектурах. Заодно:
  **1-ГиБ гигастраницы** в direct-map (сейчас 2-МиБ) — десятки гигабайт отображаются десятками
  записей. Цена: пересборка ВСЕХ программ (включая std-программы и uutils) под новую базу.

    `platform_init`, bump идёт по регионам, `is_ram`/`reserve`/`used_bytes` — по карте. Обе арх
    сообщают один регион → этап проверяемо нулевой (нормализованный diff полного лога).
  - [x] **Этап 2** — x86: тег 6 (E820) у multiboot2 и записи PVH-memmap → регионы.
  - [x] **Этап 3** — riscv: все узлы `/memory*` и все пары в `reg` (банки платы), подрезка по
    досягаемости direct-map; `ram_limit()` удалён из контракта `arch` — у дырявой карты «конец
    RAM» одним числом ничего не значит.
  - **Ловушка:** direct-map нельзя стелить буквально по карте. Ниже 4 ГиБ дыры (VGA `0xB8000`,
    BIOS, ACPI) ЗАКРЫВАЕМ отображением — ядро ходит туда через direct-map, и вырез дал бы triple
    fault, как в Вехе 87; выше 4 ГиБ — строго по регионам. Раздачи это не касается: чего нет в
    карте, аллокатор не выдаст. После `mm_enable` пробуем верхнюю страницу каждого региона на
    запись/чтение — карта и таблицы обязаны совпадать.
  - **Проверено:** x86 PVH `-m 8G` → 8191 МиБ в 3 регионах (было 2047), GRUB `-m 6G` → 6143 МиБ
    в 3 регионах с полной загрузкой (сеть, store, vvsh), riscv `-m 16G` → 16384 МиБ.
  Закрывает давний техдолг «аллокатор не уважает карту памяти» из [[known-gaps]].

- [x] **Веха 89 — санитария: устойчивость ядра под нагрузкой — ЗАКРЫТА** (аудит перед фазой;
  места в коде — [[known-gaps]]). Пять вещей, которые работали «потому что нагрузки нет»:
  - [x] **(1) IRQ-safe замки.** `SpinLock` не выключал прерывания → латентный дедлок: поток берёт
    замок, приходит прерывание, обработчик берёт тот же замок, а отпустить некому. Появился
    `lock_irq()` (глушит прерывания ДО захвата, восстанавливает ПРЕЖНЕЕ состояние на drop);
    переведены все замки, достижимые из обработчика: `ASYNC`, `EXECUTOR`, `SCHED`, кольцо консоли
    riscv, `XHCI` (он внутри `console_drain` — неочевидный путь) и куча ядра (пробуждение future
    аллоцирует). Ручные обёртки убраны, список «кто достижим из IRQ» — в преамбуле `sync.rs`,
    чтобы правило жило в коде, а не в головах.
  - [x] **(2) Целостность store.** Кадр с диска принимался как есть, результаты `io.read/write`
    игнорировались. Теперь хэш сверяется с content-id (не сошлось → объект НЕДОСТУПЕН, а не
    мусор), `read_object`→`Option`, `write_object`→`bool`, коммит атомарен по-настоящему: отметки
    «на диске» ставятся после успеха ВСЕХ записей, сбой индекса/суперблока их откатывает.
    Счётчики `corrupt_reads`/`failed_writes`, отчёт — в момент ЧТЕНИЯ (в коммите порча уже не
    ловится).
  - [x] **САМОИЗЛЕЧЕНИЕ (сверх плана).** Байты семян лежат в образе ядра, значит повреждённый кадр
    программы восстановим: `Store::repair` кладёт содержимое заново (старый кадр — в мусор, свежий
    допишет коммит). Чиним ПО ТРЕБОВАНИЮ, в точке отказа `spawn_prog`: store намеренно ленив, и
    сверять все программы на каждой загрузке значило бы читать их все впустую. Пользовательские
    данные восстановить неоткуда — они только обнаруживаются.
  - [x] **(3) Ёмкость носителя.** `BlockIo::capacity()`; коммит считает секторы ДО первой записи —
    влезает целиком или не начинается. Смежная дыра: `compact` пишет в две фазы, и фаза 2 затирает
    область с начала — это безопасно ТОЛЬКО если фаза 1 прошла (иначе активный суперблок ещё
    указывает на эти кадры). Теперь фаза 1 проверяется, при отказе учёт откатывается по снимку.
    Ядро на «полно» пробует уплотнение и повторяет коммит один раз.
  - [x] **(4) Политика нехватки памяти.** `map`/`clone_kernel_root` стали фаллибельными
    (`#[must_use]` сам перечислил все места, где отказ игнорировался). Загрузочные пути — `assert!`
    (там памяти всегда хватает, а если нет — система нежизнеспособна), процессные — честный отказ:
    ELF → `OutOfMemory`, фолт кучи → процесс убит, шлюзы и драйверы → ошибка. Плюс **квота страниц
    на группу нитей** (четверть рабочей RAM, не меньше 8 МиБ) — её не было вовсе.
  - [x] **(5) Слоты процессов + мелочи.** Утилизированная группа отдаёт номера в список свободных.
    Предпосылка: номер процесса — адрес его эндпоинта, поэтому `cap::revoke_process` сперва
    отзывает Endpoint/Reply на этот номер, иначе устаревший cap адресовал бы ЧУЖОЙ новый процесс.
    Сторож стека ядерных задач (guard-страницу не поставить: стек из кучи, а она в huge-страницах
    direct-map). Аллокатор vvsh получил свободный список со слиянием вместо пустого `dealloc`.
  **Проверено прицельно, а не рассуждением:** бит-флип байта в кадре объекта → обнаружение,
  починка, вторая загрузка чистая; 256-КиБ диск → система живёт, коммит отклонён, образ не тронут;
  заниженная квота → процесс убит, ядро цело; загрузка на 24 МиБ RAM; шесть `run` подряд в ОДИН
  слот P6. Нормализованный diff полного лога обеих арх — нулевой помимо перенумерации процессов.

## Фаза 7 — сеть (см. [[0008-network-stack]])
Цель фазы: программа на VOID может **открыть соединение и что-то скачать**. Ядро не меняется по
существу — оно и дальше отдаёт сырые кадры ([[virtio-net]], [[e1000]]); всё новое живёт в
userspace-сервере `net-srv`, стек — **vendored smoltcp** (решение и разбор безопасности — в ADR).

- [ ] **Веха 90 — smoltcp в net-srv: UDP поверх настоящего стека.** Vendored smoltcp (версия
  пинится, сборка оффлайн); трейт `Device` — тонкая обёртка над `SYS_NET_SEND`/`SYS_NET_RECV`;
  `Instant` — из `sys::now()`. **Главная переделка — архитектура сервера:** сегодня `net-srv`
  блокируется в `sys::recv` (IPC) и опрашивает кадры busy-poll'ом только внутри `ping`; стеку же
  нужно тикать всё время (входящие + таймеры ретрансмиссии), продолжая отвечать клиентам. Решение:
  **нить стека + нить IPC** (потоки есть с Вехи 35, [[threads]]) c futex-синхронизацией очередей.
  Демо: UDP-эхо до хоста (SLIRP) на обеих арх.
- [x] **Веха 91 — сон вместо опроса — ЗАКРЫТА.**
  - [x] **`SYS_RECV` со сроком** (режим 2) и **со сроком ИЛИ кадром** (режим 3): реактор
    `net-srv` спит в ядре, момент пробуждения называет сам стек (`poll_delay`).
  - [x] **Прерывание приёма virtio-net** на обеих арх (riscv — PLIC, x86 — MSI-X + новый вектор
    36 со шлюзом в IDT). Кадр будит сервер сразу, потолок сна снят.
  - [x] Починен давний изъян: `wait_stdin` глушил таймер в простое, поэтому сроки некому было
    проверять — это касалось и `futex_wait` с таймаутом (на холостой системе не просыпался вовсе).
  - **Три причины, по которым прерывание не приходило** (все три пришлось найти, ни одна не
    видна из кода — только из измерений):
    1. **x86:** virtio-net не привязывал очередь приёма к вектору MSI-X
       (`PCI_QUEUE_MSIX_VECTOR`) — virtio-blk это делает, потому у диска IRQ был, а у сети нет.
    2. **x86:** у нового вектора не было шлюза в IDT (`TRAP_STUBS` — фиксированная таблица);
       прерывание на вектор без шлюза не игнорируется, а **убивает машину**.
    3. **riscv (главная):** политики масок были взаимоисключающими — `irq_mask_preempt` включает
       таймер и ГЛУШИТ устройства, `irq_mask_stdin` наоборот. Сон со сроком требовал таймера,
       поэтому прерывание карты копилось в PLIC: pending-бит стоял, а `claim` его не видел, ведь
       SEIE был выключен. Добавлена третья политика `irq_mask_idle` — таймер И устройства.
       Попутно: линию virtio-mmio надо один раз снять при включении источника (`ack_pending`) —
       за время работы опросом она осталась поднятой, а PLIC ловит ФРОНТ.
  - **Чем это ловилось:** дамп DTB (проверить номера IRQ), чтение `InterruptStatus` устройства и
    регистра pending PLIC, лог `claim()`. Отдельный урок: первый лог claim'ов имел лимит в 6
    строк и его выбрали прерывания диска на загрузке — диагностика соврала, пришлось фильтровать.
- [ ] **Веха 92 — DHCP + DNS.** DHCPv4-сокет smoltcp (адрес/маска/шлюз/DNS от роутера; статика
  остаётся запасным путём и настраивается в `.vv` — [[vvsh-config-layout]]); DNS-сокет и команда
  `resolve имя` в vvsh. Демо: адрес получен от QEMU-SLIRP, `resolve cache.nixos.org` печатает A-запись.
- [ ] **Веха 93 — TCP + сокет-API по IPC.** Протокол `net-srv` дорастает до `tcp_connect`/`send`/
  `recv`/`close` (право пользоваться сетью = cap на эндпоинт); клиентская обёртка в
  `programs/user/src/lib.rs`, команды в vvsh. Демо: соединение с хостом, обмен байтами, аккуратное
  закрытие. Позже поверх этого — `std::net` в порте std ([[std-port]]).
- [ ] **Веха 94 — HTTP-клиент.** GET с `Content-Length`/chunked и редиректами; загрузка **прямо в
  store** (потоково), а не в posixfs — у персоналии файл ≤128 КиБ, а пакеты мегабайтные; для этого —
  потоковый `obj_put` (сейчас объект кладётся одним слайсом). Демо: скачать файл по HTTP и проверить
  его хэш на устройстве.
- [ ] **Веха 95 — HTTPS: rustls на чистом RustCrypto.** Провайдер без `ring`/`aws-lc` (без C и asm)
  под таргет `*-unknown-void`, корневые сертификаты (`webpki-roots`), проверка цепочки по часам
  Вехи 86. Демо: `https://cache.nixos.org/nix-cache-info` скачан **самим VOID**. ← ворота в Фазу 8

## Фаза 8 — пакеты на устройстве (см. [[0009-ondevice-packages]])
Цель фазы: **`pkg install hello` на самом VOID** — скачать из бинарного кэша nixpkgs, разложить в
контент-адресуемый store, запустить. Сборка из исходников — Фаза 9, отдельно.

- [ ] **Веха 96 — NAR и xz на устройстве.** Парсер NAR выносится из `tools/void-store-import` в
  общий `no_std`-крейт (как в своё время [[store-bridge]] вынес формат store), распаковщик xz —
  чистый Rust (`lzma-rs`). Распаковка идёт **прямо в store**: файл = объект по хэшу, каталог =
  индекс-корень (та же раскладка, что у posixfs-иерархии [[folders]]) — дедуп и GC достаются даром.
  Демо: локальный `.nar.xz` разложен в store и виден в `ls`.
- [ ] **Веха 97 — `pkg fetch`: narinfo → store, с проверкой.** GET `/<hash>.narinfo`, разбор
  (`StorePath`/`URL`/`Compression`/`NarHash`/`References`/`Sig`), скачивание `.nar.xz`, **проверка
  `NarHash` (sha256) и подписи кэша (ed25519, ключ `cache.nixos.org-1`)** — загрузка из чужого кэша
  становится доверяемой по содержимому. Демо: `pkg fetch hello` кладёт замыкание одного пути.
- [ ] **Веха 98 — замыкание зависимостей и профили.** Рекурсивная загрузка `References`; профиль =
  корень-индекс (`profile/<имя>`), установка/удаление = новый корень, откат = смена корня —
  механика поколений [[declarative-init]] переиспользуется целиком. `pkg install/list/remove/rollback`
  в vvsh. Демо: пакет с зависимостями встаёт полностью, откат возвращает прежний профиль.
- [ ] **Веха 99 — запуск скачанного (доводка персоналии Linux).** Три части: (а) **файловый мост**
  linux→posixfs (сегодня в [[linux-abi]] работают только applet'ы в stdout) и видимый путь
  `/nix/store/...`; (б) **динамический загрузчик** — `PT_INTERP`, запуск `ld.so` (релокации делает
  он сам, нам — загрузить и дать syscall'ы); (в) **стартовый набор glibc**: `mmap`/`openat`/`fstat`/
  `arch_prctl`(TLS)/`set_tid_address`/`futex`/`clock_gettime`/`getrandom`/`exit_group`. Демо:
  неизменённый динамический `hello` из nixpkgs запускается на VOID.
- [ ] **Веха 100 — пакетная жизнь.** `PATH` из профиля (голое имя в vvsh ищет и там), `pkg` в help,
  подчистка store по GC, README/`notes/pkg-ondevice.md`, end-to-end демо: чистая система → `pkg
  install` → запуск → ребут → пакет на месте.

**Риски и предпосылки фазы (проверить рано):** куча ядра 16 МиБ и двойное копирование ELF при
`exec` — большие пакеты в неё не влезут (нужен потоковый put и, возможно, отображение ELF без
второй копии); posixfs с файлом ≤128 КиБ обходим только через store; динамические glibc-бинари
тянут заметный кусок «второго Linux» — если упрёмся, запасной путь `pkgsStatic` (у́же ассортимент,
зато без `ld.so`).

  не нужен (store и есть база), `ui` ждёт графики. Блокер — сокеты и tokio (потоки/futex), то есть
  после Фазы 7.

  программе про её привилегии. Приём доказан этажом ниже — [[lx-emul]] хостит неизменённые .c ядра
  Linux (Веха 73). Фаза 12+: нужны GPU, оконная система, потоки и полный linux-abi. **Обход
  kernel-античита в цели НЕ входит** — против аппаратной аттестации локальная ложь не работает в
  принципе (разбор — в ADR).
