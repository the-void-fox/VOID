Аппаратный курсор VGA теперь двигается за письмом (`sync_cursor`, CRTC 0x0E/0x0F) — не «висит вверху». vsh: `clear`, цветной табличный `help` (жёлтые команды + русские описания), зелёное приглашение. `cd` осознанно отложен — posixfs ПЛОСКАЯ (нет каталогов/cwd).

Файл — корень `f<путь>`, каталог — индекс-корень `d<путь>` (оба GC-safe); голое имя → `/<имя>` (std-программы работают без пересборки). vsh: резолвер путей (`.`/`..`/абс/отн), приглашение с каталогом (синим), команды `cd`/`pwd`/`mkdir`/`rm` + путь-осознанные `ls [DIR]`/`cat`/`tail`/`echo`/`mv`. Проверено на обеих архитектурах, персистентно (вложенные каталоги переживают перезагрузку). Осталось: прав/времён нет, `rm -r` нет, std-`create_dir` нет.

- [x] **Веха 45 — редактирование строки в vsh — закрыта** ([[tty]], пункт [[known-gaps]]): приглашение стало настоящим редактором — курсор в строке, вставка/удаление в позиции, `←`/`→`/`Home`/`End`/`Delete`, история команд `↑`/`↓` (кольцо на 8). Единый ANSI-механизм: PS/2 (`ps2.rs`) шлёт расширенные клавиши (`0xE0`) как `ESC[…`, terminal QEMU — те же коды, VGA-ядро разбирает (+ добавлено перемещение курсора `ESC[nA/B/C/D`), vsh парсит и перерисовывает строку (позиция по границам символов UTF-8). Проверено: serial (вставка в середине/backspace/история) и VGA через PS/2 (`sendkey up` поднял команду из истории). Ограничение: строки шире экрана редактируются неидеально.

- [x] **Веха 46 — освобождение фреймов — закрыта** ([[frame-freeing]], техдолг #3 из [[known-gaps]]): `frame.rs` дорос до списка свободных (интрузивный Treiber-стек, переиспользование вместо чистого bump); `arch::free_address_space` сносит приватные фреймы пространства (страницы+таблицы+корень), узнавая общие с ядром узлы сравнением с `KERNEL_ROOT` (x86 — с учётом клона PDPT под PML4[0]); `proc::reclaim_dead_spaces` в `resume()` освобождает группу, когда ВСЕ её нити `Finished` (единая точка для exit/exit_group/фолт-килла), предварительно переключив satp/CR3 на живого преемника (нельзя рушить активные таблицы). Проверено: обе арх — демо без OOM, ~327 фреймов вернулись; `run hello` ×12 → пик `[mem]` не сдвинулся (течь остановлена).

- [x] **Веха 47 — драйвер AHCI (SATA) — закрыта** ([[ahci]], первый «настоящий» драйвер железа из [[known-gaps]]): store читает/пишет на реальный SATA-диск в режиме AHCI — тот же интерфейс `BlockIo`, что и virtio-blk. `arch::probe_ahci` (x86) сканирует PCI-шину со ВСЕМИ функциями (на Intel-PCH контроллер на 00:1f.2), берёт ABAR/порт с диском; `ahci.rs` — опросный драйвер (список команд + FIS + PRDT, READ/WRITE DMA EXT, IDENTIFY для ёмкости); `object.rs` диспетчеризует носитель (AHCI → иначе virtio-blk). Проверено в QEMU (ich9-ahci без virtio): store прочитан по AHCI (32768 секторов, все программы), `echo > f` пережил ребут (`cat` вернул текст), регрессия virtio чиста на обеих арх. ⚠️ на реальном ноуте пишет в СЫРОЙ диск (сектор 0) — сотрёт существующую ОС; только пустой/запасной диск.

- [x] **Веха 48 — установка на диск — закрыта** ([[install]], live-USB → install → загрузка с диска): store переехал с сектора 0 в раздел (AHCI читает MBR, `base` LBA; тип раздела `0x9f`), `Code/boot/mkdisk.sh` собирает загрузочный образ (GRUB i386-pc вручную — `grub-bios-setup` на NixOS падает; p1 FAT с ядром, p2 store). Образ едет модулем multiboot2 на install-ISO (`arch::boot_module`, уберегаем от аллокатора фреймов) — установленное ядро == работающему. vsh `install` → `SYS_INSTALL` (№30, гейт store WRITE): пишет префикс на диск, растягивает p2 на весь диск, чистит store-область, замораживает кэш. Проверено end-to-end в QEMU: чистый диск → install → ребут только с SATA → VOID грузится, пишет, переживает ещё ребут. ⚠️ install СТИРАЕТ весь диск.

- [x] **Веха 49 — драйвер Intel e1000 (NIC) — закрыта** ([[e1000]], настоящая сеть на металле): драйвер PRO/1000 (PCI 8086:100e/10d3, BAR0 MMIO, RX/TX-кольца дескрипторов, MAC из RAL/RAH или EEPROM, опрос) даёт net-srv те же сырые кадры, что virtio-net; носитель диспетчеризуется `net.rs` (e1000 ↔ virtio-net, зеркало AHCI/virtio-blk). Проверено в QEMU (`-device e1000`): `ping 10.0.2.2` отвечает через e1000; регрессия virtio-net (обе арх) чиста. ⚠️ у X54C проводной порт Atheros/Realtek — не e1000; e1000 — первый общий NIC, не финал для этого ноута.

- [x] **Веха 50 — USB xHCI + HID-клавиатура — закрыта** ([[usb]], самый большой драйвер, 3 части): (A) контроллер — сброс/DCBAA/кольцо команд/кольцо событий/запуск/порты, Enable Slot проверяет машинерию; (B) перечисление — Address Device (input-контекст, EP0 TR-кольцо), control-трансферы по EP0, GET_DESCRIPTOR; (C) HID — config-дескриптор→interrupt-эндпоинт, SET_CONFIGURATION/SET_PROTOCOL(boot)/Configure Endpoint, poll_hid (из console_drain) парсит boot-репорты→ASCII→консоль; таймер не маскируется при простое, когда USB-клава поднята (у USB нет прерывания). Проверено в QEMU (qemu-xhci+usb-kbd, QMP send-key): набор «pwd»→Enter выполнился. ⚠️ X54C=Sandy Bridge→EHCI, не xHCI — этому ноуту не поднимет.

# VOID — staged роадмап

Принцип: радикальные идеи включаются по одной, **каждая за работающей вехой** — чтобы всегда
было что-то живое в QEMU, а не вечная стройка. Первые ~5 слоёв одинаковы для любого ядра и не
зависят от стержневого тезиса ([[0002-persistent-content-addressed-capability-core]]) — это
чистое «понять, как всё работает». Радикальное начинается со слоя памяти/хранилища.

## Фаза 0 — фундамент (от железа вверх)
- [x] **Веха 1.** Boot: OpenSBI → entry asm → стек → `kmain`; вывод в UART (NS16550).
- [x] **Веха 2.** Trap/прерывания: обработчик исключений (ebreak), таймерные прерывания (S-mode), дамп регистров при фатале. См. [[traps-and-timer]].
- [x] **Веха 3.** Виртуальная память: Sv39-пагинг, direct map RAM + W^X ядра, переход на трансляцию. См. [[sv39-paging]].
- [x] **Веха 4.** Kernel heap: free-list аллокатор + `#[global_allocator]`, арена из `frame::reserve`, `alloc` работает. См. [[kernel-heap]], [[memory-regions]].
- [x] **Веха 5.** Многозадачность: контексты + кооперативный round-robin планировщик. См. [[scheduling]].
- [x] **Веха 5.5.** Вытеснение (preemption) по таймеру: переключение из trap'а, состояние прерываний на задачу, атомарный вывод. См. [[scheduling]].

## Фаза 1 — стержень (тут начинается VOID)
- [x] **Веха 6.** Объектная модель в RAM: неизменяемые значения по хэшу + дедуп + изменяемые корни/история версий. См. [[object-model]], [[persistence-and-volatility]].
- [x] **Веха 7.1.** Драйвер virtio-blk: чтение/запись секторов (virtio-mmio, split virtqueue, опрос). См. [[virtio-blk]].
- [x] **Веха 7.2.** Персистентный store: суперблок + A/B индекс + append-only объекты; корень переживает перезагрузку. См. [[persistent-store]].
- [x] **Веха 8.** Capability: непод­делываемые дескрипторы (слот+поколение), c-space на домен, аттенуация при grant, отзыв. См. [[capabilities]].
- [x] **Веха 9.** Async-executor: future-задачи + waker + async-канал поверх объектного store. См. [[async-executor]].

> **Фаза 1 закрыта:** все три ингредиента ADR 0002 (персистентность · контент-адресация · capability) + async-модель исполнения над ними собраны и работают в QEMU.

## Фаза 2 — наружу
- [x] **Веха 10.1.** U-mode + граница syscall (`ecall`): страницы `U`, переключение стека через `sscratch`, SYS_WRITE/SYS_EXIT, вход/возврат через `context_switch`. См. [[user-mode]].
- [x] **Веха 10.2a.** Процессы со своим `satp` (клон корня ядра + приватный стек) + кооперативное планирование (SYS_YIELD/EXIT), `enter_user_frame`. См. [[processes]].
- [x] **Веха 10.2b.** IPC (RECV/CALL/REPLY, синхронный rendezvous) + первый userspace-сервер (удвоение) и клиент. См. [[ipc]].
- [x] **Веха 11.** Драйвер блоков как userspace-сервер: IPC с передачей буфера (CALL/REPLY), шлюз `SYS_BLK_READ`, сервер+клиент читают сектор. См. [[block-driver]].
- [x] **Веха 12.** Capability-защищённые IPC-эндпоинты: домен на процесс, `CALL` по cap на эндпоинт (`SEND`), `BLK_READ` по cap на устройство (`READ`) — доступ к серверу/железу только по дескриптору. См. [[ipc-endpoints]].
- [x] **Веха 13.** Сервер объектного store в userspace: `CALL` с буфером запроса + шлюзы `OBJ_PUT`/`OBJ_GET` под cap на `Store`; клиент кладёт/читает объекты по IPC, не касаясь store. См. [[object-store-server]].
- [x] **Веха 14.** Именованный корень как capability: `OBJ_SET_ROOT`/`OBJ_GET_ROOT` по IPC под store-cap; объект, привязанный к корню, переживает перезагрузку (persistence через userspace-сервер). См. [[persistent-root-ipc]].
- [x] **Веха 15.** reply-capability: `RECV` выдаёт одноразовый reply-cap (`Target::Reply`), `REPLY` требует его и отзывает — нельзя ответить тому, кто не звал/подделать. См. [[reply-capability]].
- [x] **Веха 16.** Вытеснение процессов: `sie.STIE` вкл на сессию, таймерный trap из U = переключение процесса (`preempt_tick` + `next_runnable`), ядро с `SIE=0` не вытесняется. См. [[process-preemption]].
- [x] **Веха 17.** `BLK_WRITE`: шлюз записи сектора под правом `WRITE` на устройство; блок-протокол кодирует сектор+флаг записи в `op`. Клиент пишет и читает сектор обратно через сервер. См. [[block-driver]].
- [x] **Веха 18.** Слой совместимости — POSIX-персоналия как сервер (под-вехи 18.1–18.4, **закрыта**).
    - [x] **18.1.** Сервер-персоналия + POSIX-shim: open/write/close/read, namespace в RAM сервера, без изменений ядра. См. [[posix-personality]].
    - [x] **18.2.** Персистентность файлов через store: содержимое под корнем-именем (роты хранилища = директория), переживает перезагрузку. См. [[posix-personality]].
    - [x] **18.3.** `stat`/`unlink`/`readdir`, режимы open (`O_APPEND`/`O_TRUNC`), смещения на дескриптор; персистентный индекс каталога `.dir`; шлюз ядра `OBJ_DEL_ROOT` (честный unlink — корень уходит в GC). См. [[posix-personality]].
    - [x] **18.4.** Программа `mini-sh` на чистом POSIX-shim (libc-заглушка `sh_open/read/write/close/readdir`, `mini-cat`/`echo`, stdout=fd 1 → консоль): в теле программы ни `ecall`, ни op-кодов, ни capability — прозрачность личности. См. [[posix-personality]].

## Фаза 3 — самостоятельность (см. [[0003-phase-3-exec-by-hash]])
Центральный примитив фазы: **программа = контент-адресуемый объект, exec по ContentId** — как derivation в Nix, прямое следствие ADR 0002.
- [x] **Веха 19.** Программа как объект store: ELF-крейт `programs/hello` → байты в store под корнем `bin/hello` → минимальный ELF-загрузчик (PT_LOAD, W^X) → `spawn_elf` по ContentId; на втором запуске ELF грузится с диска. См. [[exec-from-store]].
- [x] **Веха 20.** UART-ввод по прерыванию (кольцевой буфер, вычерпывание на тиках) + `SYS_READ`/`SYS_EXEC` (право `EXEC`, foreground-ожидание) + интерактивный `vsh`: `ls`/`cat`/`echo > f`/`run bin/hello`/`exit`; смена корня из userspace = атомарный чекпойнт. См. [[interactive-shell]].
- [x] **Веха 21.** Cap-transfer по IPC (grant-в-сообщении, право GRANT; `CAP_DERIVE` — аттенуация) + персистентный c-space (`.cspace` в store, чекпойнт на каждую передачу, restore с точными поколениями) — capability переживают перезагрузку, тезис ADR 0002 полный. См. [[ipc-cap-transfer]].
- [x] **Веха 22.** Куча процесса (`SYS_MAP`, ленивые страницы, доотображение под шлюзы); user page fault убивает процесс, а не ядро; лимиты POSIX-персоналии сняты (16 файлов × 4 КиБ, метаданные в куче). См. [[process-heap]].

> **Фаза 3 закрыта:** система самостоятельна — программы загружаются из store по content-id,
> есть живой shell с вводом, capability передаются по IPC и переживают перезагрузку вместе с
> c-space, у процессов настоящая ленивая память и честные фолты.

## Фаза 4 — мультиархитектурность и пакеты (см. [[0004-void-pkg]])
Цель: «поставил на устройство и пользуешься» — ядро на двух архитектурах из одного дерева
(`cargo build --target …`, код разводится модулем `arch/` по узкому контракту), программы —
из настоящих пакетных баз через резолвер void-pkg (A→B→C). NixOS доказала стабильность этой
модели поверх чужого фундамента; у VOID фундамент (контент-адресуемый store) — родной, в ядре.
- [x] **Веха 23.** Userspace целиком в ELF из store: крейт `programs/user` (либа syscall-шимов + 13 бинарей), сев по хэшу под корни `bin/<имя>` (актуально/посеяно/обновлено), секция `.user` похоронена (мины memset/jump-таблиц сняты — ядро на `opt-level=2`), все шлюзы доотображают ленивые кучи. См. [[elf-userspace]].
- [x] **Веха 24.** Граница архитектур: `arch/{riscv64,x86_64}` за узким контрактом (ADR 0005) — оба таргета из одного дерева, ноль предупреждений; x86 — заглушка (COM1 + примитивы прерываний настоящие, остальное `unimplemented!` с обязательствами bring-up). См. [[arch-boundary]].
- [x] **Веха 25.** x86_64 оживает: PVH direct boot (вместо Limine — VA==PA и `cargo run` без внешних загрузчиков), трамплин 32→64, IDT, PML4 W^X, LAPIC-вытеснение, контексты — ядерная половина демо на обоих таргетах. См. [[x86-bringup]].
- [x] **Веха 26.** Userspace x86_64: ring3 (GDT/TSS) + `int 0x80` + iretq, `restart()`/`ARCH_NAME` в контракте, PDPT-клон пространств, ввод опросом на тиках, программы под обе архитектуры (модуль `abi`), корни `bin/<arch>/<имя>` + миграция. Демо-паритет (кроме диска). См. [[x86-userspace]].
- [x] **Веха 27.** Устройства x86_64: транспорт virtio в контракте arch (mmio/pci), virtio-blk-pci + MSI-X, IOAPIC для консоли — персистентность на обеих архитектурах, один диск с бинарями и файлами двух архитектур. См. [[x86-devices]].
- [x] **Веха 28.** Микробенчи и отчёт памяти против Linux-гостя в том же QEMU; корневой README («это уже система», цифры, не-претензии). Заодно закрыла Bench-веху из «Когда-нибудь» (crash-тест A/B случился внепланово ещё в Вехе 27).
- [x] **Веха 29.** Мост host→store: `libs/void-store` (формат как библиотека, `BlockIo`), `void-store-import` (put/nar/ls/cat), NAR-импорт `nix-store --dump` → корни store; форк rust сабмодулем под std-порт. См. [[store-bridge]].
- [x] **Веха 30.** Контракт запуска (ABI v2): argv в SYS_EXEC, env + стартовые capability наследуются (`cap::endow`), SYS_ARGS/SYS_STARTCAP; posixfs seek/rename; vsh run-с-аргами/mv/tail. См. [[process-contract]].
- [x] **Веха 31.** std-порт: таргеты *-unknown-void + pal в форке rust; тулчейн void из stage1; hello-std обычным cargo — argv/env/куча/HashMap/exit-код на обеих архитектурах. См. [[std-port]].
- [x] **Пакетная дорожка (бэкенд A) закрыта.** Веха 30 (контракт запуска) → Веха 31 (std-порт из `vendor/rust`) → Веха 32 (uutils) → Веха 36 (nixpkgs-cross через void-libc); профили/поколения/откат — свойства store, не менеджера.
