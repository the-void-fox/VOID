# Области памяти программы: стек, куча и не только

Справка о том, где вообще «живут» данные во время работы программы. Возникла из вопроса
по [[kernel-heap|куче ядра VOID]]; примеры привязаны к нашему ядру, но идея общая.

## Карта: адресное пространство
У запущенной программы есть **адресное пространство** — набор адресов, которые она может
трогать. Оно поделено на области с разным назначением и разными правами. Классическая
раскладка (снизу вверх по адресам):

```
высокие адреса
  ┌───────────────┐
  │     стек      │  ← растёт ВНИЗ (sp уменьшается)
  │      ↓        │
  │               │
  │      ↑        │
  │     куча      │  ← растёт ВВЕРХ (по запросу)
  ├───────────────┤
  │ .bss / .data  │  статические/глобальные данные
  ├───────────────┤
  │    .rodata    │  константы (только чтение)
  ├───────────────┤
  │    .text      │  код (чтение + исполнение)
  └───────────────┘
низкие адреса
```

Стек и куча растут навстречу друг другу — так исторически делили свободное пространство
между «автоматической» и «динамической» памятью.

## Стек
LIFO-стопка кадров (frames). На каждый вызов функции сверху кладётся **кадр** с её
локальными переменными, аргументами, адресом возврата; при выходе — снимается.

- **Управление:** автоматическое, компилятором. Ты не пишешь «выделить/освободить».
- **Скорость:** максимальная — выделение это просто сдвиг указателя стека (`sp`).
- **Время жизни:** строго по области видимости (scope). Вышли из функции — данные исчезли.
- **Размер:** маленький и фиксированный (обычно от десятков КиБ до пары МиБ на поток).
- **Ограничение:** нельзя вернуть указатель на локальную переменную «наружу» — она умрёт.
  Размер должен быть известен и невелик (большой массив на стеке = переполнение).
- **Провал:** *stack overflow* — залезли за границу стека (глубокая рекурсия, огромный массив).

В VOID: указатель стека `sp` мы задаём в [[traps-and-timer|entry.s]] значением `_stack_top`,
а сам стек (64 КиБ) зарезервирован в [linker.ld](../../Code/kernel/linker.ld). На trap'е
[[traps-and-timer|мы сохраняем регистры именно на стек]].

## Куча (heap)
Область для данных, чьё **время жизни не совпадает с областью видимости** и/или чей **размер
известен только в рантайме**. Памятью управляет **аллокатор**: программа просит «дай N байт»
(`malloc`/`Box::new`) и потом «верни обратно» (`free`/`drop`).

- **Управление:** явное (в C — руками; в Rust — через владение: выделяет конструктор, `free`
  делает `drop`). GC — третий вариант (не наш случай).
- **Скорость:** ниже стека — аллокатору надо *найти* подходящий свободный кусок.
- **Время жизни:** любое. Можно выделить в одной функции, освободить в другой.
- **Размер:** большой и гибкий (ограничен физической памятью).
- **Проблемы:** **фрагментация** (свободная память раздроблена на мелкие куски, большой
  запрос не влезает), утечки (забыл освободить), накладные расходы аллокатора.
- **Провал:** *OOM* (out of memory) — аллокатор не нашёл места, вернул null.

В VOID: `Box`, `Vec`, `String` — всё это куча (см. [[kernel-heap]]).

## Стек vs куча — одним взглядом
| | Стек | Куча |
|---|---|---|
| Кто управляет | компилятор (авто) | аллокатор + программа (явно) |
| Выделение | сдвиг `sp` (мгновенно) | поиск свободного блока |
| Время жизни | по scope (LIFO) | произвольное |
| Размер | мал, фиксирован | велик, гибок |
| Фрагментация | нет | есть |
| Типичный провал | stack overflow | OOM / утечки |
| В Rust | локальные переменные | `Box`/`Vec`/`String`/`Rc`… |

## Статическая память (.data / .bss)
Глобальные и `static`-данные. Существуют **всю жизнь программы**, адрес и размер известны на
этапе компиляции.
- `.data` — инициализированные ненулём (`static X: u32 = 5`). Значения лежат в образе.
- `.bss` — инициализированные нулём (`static mut BUF: [u8; 4096]`). В файле не хранятся (это
  была бы куча нулей), только резервируется адрес; **обнуляет их код старта**.

В VOID: `.bss` мы зануляем в [[traps-and-timer|entry.s]] перед `kmain`. Наш `static ALLOCATOR`
и счётчик тиков таймера живут именно здесь.

## Код (.text) и константы (.rodata)
- `.text` — сами инструкции. Права: чтение + исполнение, **без записи** (иначе программа могла
  бы переписать свой код — это и делают эксплойты).
- `.rodata` — константы и строковые литералы: только чтение.

В VOID это и есть **W^X** из [[sv39-paging]]: код `R+X`, константы `R`, данные/стек/куча `R+W`.

## Что помимо стека и кучи
Да, есть и другое — часть это отдельные области, часть — механизмы поверх:

- **Отображения памяти (mmap).** ОС может «отобразить» в адресное пространство файл или просто
  выдать анонимные страницы. Кучи в больших системах *построены поверх* mmap: аллокатор берёт
  у ОС большие куски и нарезает их. В VOID роль «выдать RAM под арену» играет
  [[kernel-heap|frame::reserve]].
- **MMIO — память-как-устройства.** Регистры железа отображены на адреса: пишешь по адресу —
  управляешь устройством. В VOID UART на `0x1000_0000` — запись байта туда = вывод символа.
  Это не RAM, но обращаемся как к памяти.
- **Thread-local storage (TLS).** «Статика, но своя у каждого потока». Появится, когда будут
  потоки.
- **Guard pages.** Специально не-отображённая страница на краю стека: наступил на неё —
  сразу fault, вместо тихой порчи соседней памяти. Дешёвая защита от stack overflow.
- **Регистры процессора.** Формально самый быстрый «уровень хранения», ниже стека. Не память в
  привычном смысле, но данные живут и там (их мы сохраняем в TrapFrame на trap'е).
- **Кэши CPU (L1/L2/L3).** Прозрачное аппаратное ускорение доступа к RAM — не отдельная
  область для программиста, но важны для производительности.

## Важно: область памяти ≠ стратегия аллокации
Часто путают. **Куча — это область**; а *как* по ней раздавать память — это **стратегия
аллокатора**, и их много:
- **bump / arena** — просто двигаем указатель вперёд; освобождение — всё разом. Быстро, но без
  точечного free. (В VOID так работает [[kernel-heap|аллокатор фреймов]].)
- **free-list** — список свободных блоков, ищем подходящий. (Наша куча ядра.)
- **pool / slab** — заранее нарезанные блоки фиксированного размера; O(1), без фрагментации,
  но только под один размер.
- **buddy** — деление на степени двойки; хорош для страниц.
GC (сборка мусора) — отдельная тема: аллокатор + автоматическое освобождение.
