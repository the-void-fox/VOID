# Как пережить выключение питания: энергозависимость vs персистентность

Возникло из вопроса: если RAM энергозависима и теряется при выключении, как VOID собирается
«ничего не забывать»? Это ядро тезиса проекта — см. [[0002-persistent-content-addressed-capability-core]].

## Сначала честно: физику не обманываем
DRAM действительно теряет содержимое без питания (заряд в конденсаторах утекает за миллисекунды).
Мы **не** делаем RAM энергонезависимой. Идея другая:

> Держим долговечную копию данных на **энергонезависимом носителе** (диск/SSD/NVMe), а RAM
> используем как **кэш** этой копии. Новизна не в «вечной RAM», а в том, что сохранение и
> восстановление — **автоматические и прозрачные**: у программиста нет ручного save/load.

То есть «ОС не забывает» = «состояние системы всегда есть на диске, а RAM лишь ускоряет доступ».

## Что вообще энергонезависимо
- **HDD / SSD / NVMe** — блочные носители, переживают выключение. Основной кандидат.
- **Persistent memory (Optane, CXL-память с батарейкой)** — байт-адресуемая non-volatile
  память: почти «RAM, которая не забывает». Именно её появление снова сделало идею живой.
- **Battery/flash-backed RAM** — RAM с батарейкой/сбросом во flash при пропаже питания.
- **ПЗУ/flash прошивки** — только чтение, не для рабочего состояния.

VOID начнёт с обычного блочного диска (в QEMU — virtio-blk), позже можно смотреть на PMEM.

## Наивный способ: снапшоты (checkpointing)
Периодически писать на диск полный слепок всей живой памяти. На загрузке — прочитать обратно.
Так делали KeyKOS/EROS (чекпойнт раз в несколько минут).
- **Плюс:** просто.
- **Минус:** дорого (пишем всё подряд) и теряем всё, что после последнего снапшота.

## Наш способ: контент-адресация → диск это истина, RAM это кэш
VOID хранит **неизменяемые значения, адресуемые по хэшу** (см. [[memory-regions]] про области, и
объектную модель Вехи 6). Это меняет всё:

- Значение неизменяемо, а его адрес = хэш содержимого. Значит его достаточно записать на диск
  **один раз** (append), и оно там навсегда, под своим адресом. Перезаписывать нечего.
- RAM держит только «горячие» объекты; если объекта нет в RAM — подгружаем его с диска по хэшу
  (как промах кэша). Диск — источник истины, RAM — кэш.

**Прямая аналогия — git.** Объекты лежат в `.git/objects`, адресуются по SHA, неизменяемы.
Твоя рабочая копия в памяти — лишь вид; «настоящее» на диске. VOID делает это моделью всей ОС.

## Где живёт «текущее состояние»: корни и атомарный коммит
Неизменяемые значения — половина дела. Изменчивость выражается **маленьким набором изменяемых
корней (ячеек)**, которые *указывают* на неизменяемые значения (в git это ветки/refs).

Обновление состояния = переключить корень на новое значение:
1. записать новые неизменяемые объекты на диск (они не конфликтуют со старыми — у них другие хэши);
2. **атомарно** обновить корень, чтобы он указывал на новую версию.

Пока корень указывает на старую версию — на диске консистентная старая картина; после атомарного
переключения — консистентная новая. Промежуточного «полусохранённого» состояния не видно.

## Главная опасность: сбой посреди записи (crash consistency)
Если питание пропадёт в середине записи — можно получить мусор. Защита:
- **Неизменяемость снимает бОльшую часть проблемы:** старые объекты никто не перезаписывает,
  портиться нечему. Опасен только момент обновления корня.
- **Атомарное переключение корня** (одна запись сектора / запись-с-барьером / журнал WAL) делает
  переход «всё-или-ничего». Не успели — остаёмся на прошлой версии.

Именно поэтому в [[0002-persistent-content-addressed-capability-core|ADR 0002]] сказано: контент-адресация
делает персистентность **безопасной** — она чинит ровно ту причину, на которой спотыкались старые
персистентные ОС.

## Цена долговечности: барьеры и окно потери
- У дисков/контроллеров свои **энергозависимые кэши**. «Записал» ≠ «долетело до пластин».
  Нужны команды сброса/барьера (`flush`/FUA), иначе при сбое потеряешь то, что зависло в кэше.
- **Компромисс скорость↔надёжность:**
  - сбрасывать на каждый коммит — надёжно, но медленно (каждая правка ждёт диск);
  - сбрасывать периодически — быстро, но при сбое теряешь работу за последние N мс/секунд.
  Базы данных всю жизнь живут в этом компромиссе (fsync, group commit, WAL).

Абсолютной «нулевой потери» без синхронной записи каждой мутации не бывает — это фундаментальный
предел, а не недоработка.

## Как это ляжет в VOID (Вехи 6–7)
- **Веха 6 (сейчас):** объектная модель **в RAM** — контент-адресуемые значения + изменяемые
  ячейки/корни. Пока всё волатильно; это фундамент.
- **Веха 7:** долговечный контент-адресуемый store на диске (virtio-blk). RAM ← кэш; корень
  системы обновляется атомарно; на загрузке читаем корень и лениво подгружаем объекты по хэшу.

Так «ОС не забывает» становится не магией, а следствием трёх вещей: **диск как истина**,
**контент-адресация** (дёшево и безопасно) и **атомарный корень** (crash-consistency).
